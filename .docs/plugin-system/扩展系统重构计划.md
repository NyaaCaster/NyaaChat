# NyaaChat`扩展`系统重构计划
## 方案初衷
重新规划NyaaChat的整个 `扩展` 系统
- 不再考虑sillytavern扩展兼容方式直接放置sillytavern扩展代码文件来加入sillytavern的原生第三方扩展
- sillytavern的扩展均为前端插件，并有sillytavern自己的UI结构，与NyaaChat的UI结构差异很大，前端逻辑也不一致
- 应该在NyaaChat内独立建立一套脚手架，例如全部归到一个plugin树下（项目内新建plugins目录）
- NyaaChat的扩展本身也不开放给用户治理，全部由开发侧逐一开发
- 所以接下来应该是在逐一开发每个扩展功能（plugin模块）时，逐渐完善扩展框架的
- 对sillytavern的扩展，不应是粗暴兼容，而是移植、重写，参照sillytavern扩展的源代码，以最适合NyaaChat项目结构的方式重写
	- 只是在NyaaChat中重写sillytavern扩展时，sillytavern扩展的统一规范结构可以在NyaaChat的移植流程中建立相对统一的规范。

## `扩展`系统UI重构
NyaaChat的扩展UI需要重新设计，使用NyaaChat的通用界面设计样式
- 用户点击 `扩展` 入口按钮后，应采用 `对话模型供应商` 界面的UI/UX设计样式
- PC横板模式下为左右结构，左侧为扩展列表，右侧为扩展详情配置界面
- 手机竖屏模式下为二级界面结构，第一级为扩展列表，第二级为扩展详情配置界面
	- 开发每个扩展时，详情配置界面内容排版也要合理考虑PC横板和手机竖版两种模式的区别设计
- 扩展界面不需要 `对话模型供应商` 界面的 `添加自定义供应商` 这样的添加按钮，用户是无法治理添加扩展的
- 每个扩展沿用 `对话模型供应商` 界面的 启用/停用 功能和扩展列表的状态表现
- 扩展列表需要保值支持icon，但也允许不提供icon（无具体要求时使用扩展入口的图标）

## `扩展`配置加入用户设置转移体系
用户的对每个扩展的启用/禁用设置，以及对每个扩展的详细配置，要并入用户设置的导入导出上传下载中

## 首个sillytavern扩展移植任务
以刚才被移除的sillytavern扩展 https://github.com/NyaaCaster/st-Quote-TTS 为第一个NyaaChat移植扩展，这是我自己写的扩展，方便坚决问题，而且这个扩展功能简单、刚才你的检查和删除过程相当于也遍历过一遍旧扩展方案实现过的 st-Quote-TTS 的前端、后端全链路，方便作为第一个样例。
