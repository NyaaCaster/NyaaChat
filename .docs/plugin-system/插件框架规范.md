**三条铁律**：

1. **插件实现只依赖 `src/plugins/types`（契约）**，需要宿主能力时走**上下文注入**（`ctx.config` / `ctx.callBackend`）或**叶子模块**（`src/plugins/hostContext`）。不要 import 宿主的组件、store、App 内部函数 —— 那些不在契约里，随时会变。
2. **插件不要从 `runtime` / `backend` / `src/plugins/index` 取「值」** —— 会构成 `plugins/registry → plugin → … → src/plugins/registry` 的**模块环**，入口顺序会让注册表拿到半初始化的绑定，插件静默消失（§7.1 第 24 条）。
3. **`plugins/registry.ts` 是全仓唯一的插件注册入口**，也是插件集合的唯一权威（见 §3.5）。增删插件只改这一个文件。

### 1.2 构建模型：为什么没有运行时加载器

`plugins/**` **只能**通过 `plugins/registry.ts` 进入 Vite 依赖图 —— 而 `plugins/registry.ts` 被 `src/plugins/registry.ts` 静态 `import`（`src/plugins/registry.ts` **L17**：`import { plugins as registeredPlugins } from "../../plugins/registry";`），后者又被打进 `index.html → src/main.tsx` 这条主链。

因此：

- **没有运行时加载器**、**没有动态 `import()`**、**没有"允许加载哪些 id"的白名单机制**；
- 插件契约是 TypeScript 接口，**编译期即校验**（`tsc --noEmit` 覆盖 `plugins/**`，见 §1.3）；
- 没有"加载任意 JS"这一攻击面，与"插件只由开发者装入、不开放用户治理"的定调天然一致。

**代价**（已知且接受）：新增/移除插件必须**重新构建**并重建 dev 容器，不能热插拔。

> ⚠️ 反面教材：不要为了让 UI"看起来有东西"而在 `plugins/registry.ts` 里塞占位插件。列表只由该数组产生 —— 塞进去的就是"真实存在的插件"。

## 2. 插件契约逐字段说明

### 2.1 契约源文件（逐字，与磁盘一致）

以下为 `src/plugins/types.ts` 的**完整内容**（**111 行 / 4492 B**；已逐字比对，字节相同）。**这是插件作者唯一需要阅读的类型文件。**

```ts
/**
 * NyaaChat 插件系统 V1 —— 契约类型（SSOT §2.2）。
 *
 * 本文件是**全部**对外契约的唯一定义处，逐字对应 `.docs/plugin-system/开发计划-SSOT.md`
 * §2.2。除 `normalize.ts` / `runtime.ts` / `registry.ts` / `backend.ts` 暴露的
 * 小函数外，插件系统的对外面就是这些类型。
 */
import type * as React from "react";
import type { Message } from "../types";

/** 插件静态元信息（注册表可见，无需实例化插件即可用于列表渲染）。 */
export interface PluginMeta {
  /** 稳定 id，kebab-case，全仓唯一；同时是配置持久化键。 */
  id: string;
  name: string;
  description?: string;
  version: string;
  author?: string;
  /** lucide-react 图标名；缺省时 UI 回退到「扩展」入口图标。 */
  icon?: string;
  /** 列表排序，升序；相同则按 name 字典序。 */
  order?: number;
}

/** 单用户维度的插件持久化状态（AppState.plugins 的值类型）。
 *  ⚠️ 实际声明位置在 `src/types.ts`（因为 `AppState` 需要它，而 `src/types.ts`
 *  不依赖任何插件模块，可避免循环依赖）；`src/plugins/types.ts` 从那里 re-export，
 *  插件作者只需从 `src/plugins/types` 导入。 */
export type { PluginState, PluginStateMap } from "../types";

/** 消息文本装饰。
 *
 *  ⚠️ **区间空间**：宿主**逐块**调用装饰器（`p` / `li` / `blockquote` / `h1`~`h6` /
 *  `td`），`start` / `end` 是**当前块的纯文本**内的字符偏移 —— 不是"整条消息的渲染后
 *  纯文本"（那是 SSOT §2.6 初稿的 rehype 方案，2026-09-15 经用户复核改为逐块方案，
 *  两个偏移空间互不通用）。详见 SSOT §2.6。 */
export interface TextDecoration {
  start: number;
  end: number;
  /** 同一消息内唯一，作为 React key。 */
  key: string;
  /**
   * 渲染这个装饰节点。⚠️ **语义是「在片段旁边加东西」，不是「替换片段」** ——
   * 被标注的原文由宿主**始终原样输出**，本函数的返回值**追加在它之后**。
   * 因此 `render: ({ text }) => <Btn text={text} />` 的结果是 `原文` + `按钮`；
   * **不要**在这里重复输出 `text`，否则页面上会出现两份原文。
   * 抛错时宿主只保留正文并 `console.warn`，不拖垮整条消息。
   */
  render: (props: { text: string }) => React.ReactNode;
}

export interface MessageDecorationContext {
  pluginId: string;
  /** 当前插件配置的只读快照。 */
  config: Record<string, unknown>;
  messageId: string;
  role: Message["role"];
  /** user → 当前用户角色名；assistant → 当前角色名。 */
  senderName: string;
  callBackend: PluginBackendCaller;
}

export type MessageTextDecorator = (
  /** 当前**块**的纯文本；返回的区间必须落在本字符串内。 */
  text: string,
  ctx: MessageDecorationContext,
) => TextDecoration[];

export type PluginBackendCaller = <T = unknown>(
  capability: string,
  payload?: unknown,
) => Promise<T>;

export type PluginEventName = "message:received" | "session:changed" | "character:changed";

export interface PluginContext {
  meta: PluginMeta;
  getConfig: () => Record<string, unknown>;
  /** 写入必须经宿主注入的 writer（§2.4），不得只改内存快照。 */
  updateConfig: (patch: Record<string, unknown>) => void;
  callBackend: PluginBackendCaller;
  /** 返回取消订阅函数。 */
  on: (event: PluginEventName, handler: (payload?: unknown) => void) => () => void;
}

export interface PluginSettingsPanelProps {
  pluginId: string;
  config: Record<string, unknown>;
  updateConfig: (patch: Record<string, unknown>) => void;
  callBackend: PluginBackendCaller;
}

/** 边车能力声明：能力名 → 实际路径。前端不得调用未声明的能力。 */
export interface PluginBackendDeclaration {
  capability: string;
  /** 形如 /api/ext-host/plugins/quote-tts/speech */
  path: string;
  method: "POST" | "GET";
  description?: string;
}

export interface NyaaPlugin {
  meta: PluginMeta;
  /** 缺省配置；归一化时深合并到用户配置之下。 */
  defaults?: Record<string, unknown>;
  /** 启用时调用一次；返回的函数在停用/热更新时调用。 */
  setup?: (ctx: PluginContext) => void | (() => void);
  SettingsPanel?: React.ComponentType<PluginSettingsPanelProps>;
  decorators?: { messageText?: MessageTextDecorator[] };
  backend?: PluginBackendDeclaration[];
}
```

### 2.5 宿主运行时 API（实测签名 + 行号）

`src/plugins/index.ts`（**50 行 / 2151 B**）是聚合出口：`export * from "./types"` + registry/runtime/hostContext/normalize/backend/decorators（详见本节末的条目清单）。
> ⚠️ **但插件作者不要从它（或 `runtime` / `backend`）取「值」** —— 该文件 L4-11 的注释写明：`plugins/registry → plugin → … → src/plugins/registry` 会构成**模块环**，入口顺序会让注册表拿到半初始化的绑定、插件静默消失。插件需要的宿主能力走两条路：**装饰/面板上下文注入**（`ctx.config` / `ctx.callBackend`）或**叶子模块** `src/plugins/hostContext`（§7.1 第 24 条）。

```ts
// ── src/plugins/registry.ts ────────────────────────────────────────────────
export const PLUGIN_ID_PATTERN = /^[a-z0-9][a-z0-9-]*$/;          // L20
export const PLUGIN_BACKEND_PATH_PREFIX = "/api/ext-host/plugins/"; // L23

export type PluginRegistryIssueKind = "id" | "meta" | "backend";   // L25
export interface PluginRegistryIssue {                            // L27
  /** 出问题的插件 id；`meta` 完全缺失时为空字符串。 */
  pluginId: string;
  kind: PluginRegistryIssueKind;
  /** `error` 阻断该插件可用；`warning` 只是建议（例如 description 缺失）。 */
  severity: "error" | "warning";
  message: string;
```

### 3.2 归一化规则（`normalizePluginStates`，`src/plugins/normalize.ts` L52-73）

### 3.4 两条**互不相关**的版本轴（最容易搞混的地方）

| 轴 | 常量 | 位置（实测行号） | 语义 | 本阶段 |
|---|---|---|---|---|
| **本地存档轴** | `SCHEMA_VERSION = 12` | `src/App.tsx` **L118** | 只描述 localStorage 里 `nyaachat_settings` 的**形状**；**不参与任何导入/导出校验**。旧形状由 `migrate()` 链就地升级（L120-159） | 11 → 12，新增 `migrateV11ToV12()`（L230-236） |
| **导出存档轴** | `EXPORT_VERSION = 9` | `src/lib/settingsBackup.ts` **L39** | 写进归档的 `_version`；导入时由 `SUPPORTED_IMPORT_VERSIONS = new Set([2,3,4,5,6,7,8,9])`（**L40**）**严格校验**，不在集合内 ⇒ **直接拒绝导入** | **保持 9**，不变 |

两者的兼容语义**完全相反**：

- `SCHEMA_VERSION` 上调是**安全的**：旧存档被 `migrate()` 就地升级。
- `EXPORT_VERSION` 上调是**单向破坏性的**：老版本读到 `10 ∉ {2..9}` 会直接报「不支持的导出版本」拒绝导入。`settingsBackup.ts` L37-38 的既有注释写死了这条策略（"上调版本号只会**单方面**让老版本拒绝新存档"）。

因此 V1 的插件配置**以增量字段的形式**挤进 `EXPORT_VERSION = 9` 的归档：老版本读到 `plugins` 原样忽略（不报错、不拒绝），新版本读到无 `plugins` 的老档回填 `{}`。**三向兼容**（新→新、新→老、老→新）。

> 给插件作者的直接含义：**你的插件配置不是"新版本才能读的存档"**，别指望靠版本号做兼容分支。

### 3.5 插件集合的唯一权威是**代码**（`plugins/registry.ts`）

SSOT §2.8.4 / 审计报告 D3 补充把它定成三条硬规则：

1. **列表来源**：扩展 modal 的列表**只**由 `getRegisteredPlugins()` 生成（`ExtensionsModal.tsx` **L78**），**从不**遍历 `AppState.plugins` 的键。
2. **入口归一化**：localStorage 加载 / 本地导入 / 云端下载三条入口全部经 `normalizePluginStates()`，未知 id 一律丢弃 ⇒ 已下线插件的配置**进不了**活跃状态。
3. **出口防御**：`buildExportPayload()` 对 `plugins` 再过一次归一化 ⇒ 新版本导出的归档里**不可能**残留已不存在插件的配置。

**后果（开发者必须理解）**：

| 场景 | 会发生什么 |
|---|---|
| 你在新版本里**删掉**一个插件 | 用户界面立刻看不到它（列表来自代码），无需任何迁移代码、无需用户操作 |
| 用户此前配过这个插件 | 其配置既进不了活跃状态，也不会被新版本导出 |
| 用户把新版本导出的存档拿去**老版本**导入 | 归档里根本没有该插件的配置 ⇒ **配置已丢失**。这是"以代码为权威"的必然结果，属**已知且接受**的行为 |
| 你在 `AppState.plugins` 里手塞未知 id | 被入口/出口归一化丢弃，UI 不会多出一行 |
| 用户改了插件在代码里的 `meta.id` | 等价于"删旧插件 + 加新插件"，旧配置不会被继承 |

## 4. 消息装饰使用说明

> **读前必看**：SSOT §2.6 的**初稿**方案是 **A 方案**（自研 rehype 插件插进 `rehypePlugins`、区间在"整条消息的渲染后纯文本"空间）。**用户 2026-09-15 复核时改为 B 方案**，SSOT §2.6 随后**已就地改写为逐块契约**（含 A/B 对比表），磁盘实现是 `src/plugins/decorators.ts`（**221 行 / 9356 B**）。
> 本节**完全按 B 方案写**。若你手上是改写前的 SSOT 旧稿，注意 A/B 在"rehype 顺序"和"区间空间"上的结论**相反**，一律以本节与代码为准（沿革见 §8 D-1）。

### 4.1 契约（`src/plugins/types.ts`，逐字）

```ts
/** 消息文本装饰。
 *
 *  ⚠️ **区间空间**：宿主**逐块**调用装饰器（`p` / `li` / `blockquote` / `h1`~`h6` /
 *  `td`），`start` / `end` 是**当前块的纯文本**内的字符偏移 —— 不是"整条消息的渲染后
 *  纯文本"（那是 SSOT §2.6 初稿的 rehype 方案，2026-09-15 经用户复核改为逐块方案，
 *  两个偏移空间互不通用）。详见 SSOT §2.6。 */
export interface TextDecoration {
  start: number;
  end: number;
  /** 同一消息内唯一，作为 React key。 */
  key: string;
  /**
   * 渲染这个装饰节点。⚠️ **语义是「在片段旁边加东西」，不是「替换片段」** ——
   * 被标注的原文由宿主**始终原样输出**，本函数的返回值**追加在它之后**。
   * 因此 `render: ({ text }) => <Btn text={text} />` 的结果是 `原文` + `按钮`；
   * **不要**在这里重复输出 `text`，否则页面上会出现两份原文。
   * 抛错时宿主只保留正文并 `console.warn`，不拖垮整条消息。
   */
  render: (props: { text: string }) => React.ReactNode;
}

export interface MessageDecorationContext {
  pluginId: string;
  /** 当前插件配置的只读快照。 */
  config: Record<string, unknown>;
  messageId: string;
  role: Message["role"];
  /** user → 当前用户角色名；assistant → 当前角色名。 */
  senderName: string;
  callBackend: PluginBackendCaller;
}

export type MessageTextDecorator = (
  /** 当前**块**的纯文本；返回的区间必须落在本字符串内。 */
  text: string,
  ctx: MessageDecorationContext,
) => TextDecoration[];
```

**纯函数要求**：`messageText` 在**每个文本块**的渲染中都会被调用。不要在里面发网络请求、不要改全局状态、不要依赖调用顺序 —— 只做"文本 → 区间"的纯计算。

### 4.2 实现路径：**逐块装饰**，rehype 完全**不参与**（B 方案）

装饰**不进** `rehypePlugins`。它复用 `MessageItem.tsx` 里既有的**逐块引号渲染扩展点**（实测行号）：

```
Markdown 渲染（remark/rehype，含 sanitize）—— rehypePlugins 未改动（L66）
   → components 映射：p / li / blockquote / td / h1~h6（L743-752、L774-783）
       → renderTextWithQuotes(children, decorationInput)      ← L145-154
           → decorateAndHighlight(text, decoration)           ← L159-175
               → renderPluginDecorations(text, decoration)    ← L163 调用 / decorators.ts L110 定义
                   → 插件 messageText(text, ctx)  →  区间
                   → 切分 → 混合数组（字符串 + React 节点）
               → 对剩余的纯字符串再跑 highlightQuotes()（既有引号高亮）
```

#### 4.2.1 ⚠️ **两级输出**：正文必须是**顶层 string**，装饰节点另起**带 key 的 Fragment**（正确性要求，不是风格）

宿主 `decorators.ts` 对每个被接受的装饰输出**两个同级节点**（`decorators.ts` **L199-215**，逐字）：

```ts
// ① 正文：顶层字符串节点
nodes.push(slice);
// ② 装饰：独立、带 key 的 Fragment，只承载插件返回的 render 产物
nodes.push(
  React.createElement(
    React.Fragment,
    { key: `${decoration.pluginId}::${decoration.key || index}` },
    rendered,
  ),
);
```

**为什么必须是两级**：宿主 `MessageItem.decorateAndHighlight`（L159-175）**只对 `string` 型 children 做引号高亮**（`.quote-highlight`）。把 `slice` 与 `rendered` **同置一个 Fragment**，会让被装饰的引号**丢掉 `.quote-highlight`** —— 文本与按钮都还在，但高亮计数变 0。

> ⚠️ **照「slice 与 rendered 同置 Fragment」改，会把 R2 打回来。** 这不是假设：`verify` 在 t7 第一次就报的正是这个（`.quote-highlight` 运行时计数 0，见《验证报告-P1-P5》§0.1 C-1 与 §4 的 R2），captain 把实现改成上面这两行之后，真实 dev 服上计数恢复为 **2**。
> 该文件 L199-205 的注释把这条因果写在代码里了；**改动 `decorators.ts` 时不要"顺手合并"这两行。**

#### 4.2.2 契约语义：**装饰 = 在片段旁边加东西**，不是替换片段

被标注的那段原文**始终原样输出**，`render` 的返回值**追加在它之后**。所以 `render: ({ text }) => <QuoteTtsButton text={text} />` 的结果是 `原文` + `🔊`，而**不是**只剩 `🔊`。

> ⚠️ **这是 t7 的一个 blocker**：本模块初版实现只 push `render` 的返回值、丢掉了原文，导致引号文字从消息里**整个消失**（`猫娘: 「第一条引用」` → `猫娘: 🔊`，`verify` 复现并登记）。修复后 `decorators.ts` L26-36 专门写了「契约语义」一节，`src/plugins/types.ts` L42-49 也把同一句写进 `render` 的注释里 —— **两处都在提醒：不要按"替换"理解这个契约。**

渲染上下文在组件主体里构造（**L488-493**）——注意两个刻意的取舍：

```tsx
// L488：必须先订阅运行时快照（本组件是 React.memo，props 引用稳定时不会因父级渲染重跑）
React.useSyncExternalStore(subscribePluginRuntime, getPluginRuntimeSnapshot);
const decorationInput: DecorationRenderInput = {
  messageId: message.id,
  role: message.role,
  senderName: message.role === "user" ? resolvedUser : resolvedChar,

```

- **必须订阅快照**（L475-485 的注释写明了原因）：扩展 modal 里启用/停用插件或改配置只改运行时快照、不改本组件 props；不订阅的话已渲染消息的装饰要等到它因别的原因重渲染才更新。
- **上下文对象不做 `useMemo`**（L483-485 注释）：它每帧都要按最新快照重算，而 `components` 映射本来就是每帧新建的内联字面量，memo 它买不到收益；且把快照塞进 `useMemo` 依赖会被 `react-hooks/exhaustive-deps` 判为多余依赖。

**顺序不可颠倒**（`decorateAndHighlight` L155-157 的注释）：先插件装饰、后引号高亮 —— `highlightQuotes` 只吃 `string`，装饰产物里的 React 节点会原样透传。

**因此 SSOT §2.6 初稿里"装饰插件必须排在 `rehypeSanitize` 之后"这条要求，在 B 方案下已不适用**（装饰器根本不生成 HAST 元素，也就没有"被 sanitize 掉"的可能；SSOT §2.6 现已同步为 B 方案，见 §8 D-1）。`MessageItem.tsx` 当前的 rehype 管线仍是原样（**L65-66**）：

```ts
const markdownRemarkPlugins: PluggableList = [remarkMath];
const markdownRehypePlugins: PluggableList = [rehypeRaw, rehypeKatex, [rehypeSanitize, sanitizeSchema]];
```

**不要为了装饰去改这两行。** B 方案的设计意图正是把"顺序写反 ⇒ 含原始 HTML 的消息整段丢装饰"这个静默失效（审计报告 R1）从**要靠纪律守住**变成**结构上不可能发生**。

安全侧：装饰产物是 **React 节点**（`React.createElement`），不是 HTML 字符串；**不使用** `dangerouslySetInnerHTML`；插件无法通过装饰注入 HTML。

### 4.3 区间空间 = **当前块的纯文本**（不是整条消息）

`renderPluginDecorations(text, input)` 的 `text` 参数就是**当前块的纯文本**；返回的 `start` / `end` 是**该块内**的字符偏移，区间为 `[start, end)`。

对 `decorators.ts` 的调用方（`MessageItem`）而言，`text` 是 `renderTextWithQuotes()` 拿到的那个字符串（如某个 `<p>` 的纯文本 children）。

**为什么这样定义**（`plugins/quote-tts/quoteScan.ts` L7-11 的注释说得很明白）：

- A 方案要求"整条消息的渲染后纯文本"，需要三趟遍历 HAST 收集文本节点累计偏移 —— markdown 折叠（`**x**` → `x`）会让偏移换算出错（审计报告 R2）；
- B 方案的 `text` **就是要切分的那段字符串**，插件直接在上面跑正则，**空间定义天然一致**，不存在换算。

> ⚠️ **因此**：`TextDecoration.start/end` 是**块内**偏移，**不是**整条消息偏移。`plugins/quote-tts/quoteScan.ts` L24-34 的 `QuoteMatch` 也是这样注释的。
> ⚠️ 也不要再按"原始 markdown 字符串"算偏移：`text` 已经是 markdown 折叠**之后**的纯文本。

### 4.4 非法区间与重叠区间的处置（代码逐条，`decorators.ts`）

**合法性校验** —— `isValidDecoration()`（`decorators.ts` **L93-102**），不满足即**丢弃该装饰并 `console.warn`**：

| 检查 | 要求 |
|---|---|
| 是对象、`start`/`end` 是 `number` | 必须 |
| `Number.isFinite(start)` / `Number.isFinite(end)` | 必须（挡 `NaN` / `Infinity`） |
| `Number.isInteger(start)` / `Number.isInteger(end)` | 必须（**比 SSOT 初稿更严**：小数也丢弃。SSOT §2.6 L273 已同步写明） |
| `0 ≤ start < end ≤ text.length` | 必须（挡越界 / 空区间 / 反向区间） |
| `typeof render === "function"` | 必须 |

> `text.length` 用的是 **UTF-16 code unit** 长度（与 JS `string.length` 一致），不是 Unicode 码点数。代理对（emoji 等）占 2 —— 用正则 `match.index` 得到的偏移天然一致，**不要**手工按"字符数"换算。

**重叠处置** —— `decorators.ts` **L162-175**：

1. 全部收集到的装饰按 `start` 升序排序，**`start` 相同则取 `end` 更小者**（即更短的那个）优先：`collected.sort((a, b) => a.start - b.start || a.end - b.end)`（L163）；
2. 贪心扫描，维护 `cursor`；**任何 `start < cursor` 的装饰被判重叠、丢弃并 `console.warn`**（L166-175）；
3. 因此"多插件在同一区段各出一个装饰"时，结果是**排序后的先到者胜**（`verify` 在 t7 用两个合成插件实测确认：**先注册者胜，`meta.order` 不决定优先级**），而不是"注册表里靠前的插件胜"。**不要依赖插件顺序**。

**零开销路径**（L114-117 / L160 / L177）：`text` 为空、或没有已启用插件声明装饰器、或全部无命中 ⇒ **原样返回入参字符串本身**（调用方可据此跳过任何额外处理）。

### 4.5 异常处置：**降级，不抛错**

| 异常 | 处置 | 代码 |
|---|---|---|
| 插件 `messageText` **抛错** | `console.warn` 后**跳过该装饰器的本次调用**，其它插件/其它装饰器继续 | L133-144 |
| 插件 `messageText` 返回**非数组** | 静默跳过 | L145 |
| 插件返回**非法装饰** | `console.warn` + 丢弃该条 | L147-156 |
| 插件 `render` **抛错** | `console.warn` 后 `rendered = null` ⇒ **该装饰节点消失，正文照常保留且不重复**（正文已在 L206 单独输出）。⚠️ **不得**用 `slice` 顶替 —— 那会让正文出现两份（L190-196 的注释写明了） | L187-197 |

**`render` 的硬约束（插件作者必读）**：**只输出"装饰节点"本身，不要再渲染 `text`。**

- 被标注的原文由**宿主**以顶层文本节点输出（§4.2.1）；`render` 的返回值**追加在其后**。
- 若在 `render`（或其返回的组件内部）再渲染 `text`，页面上会出现**两份原文**（`原文` + `原文` + `🔊`）。
- 契约原文见 `src/plugins/types.ts` **L42-49**（`render` 的注释）与 `decorators.ts` L26-36。

> **关于 SSOT §2.6 初稿的"取不到 `render` 时渲染 `null`"**：那是 A 方案的产物 —— A 方案要靠 `data-dec-key` 从模块级 `Map` 回查 `TextDecoration`（rehype 元素只能带字符串属性，无法携带函数），回查失败时渲染 `null`。
> **B 方案下不存在这个环节**：`render` 是插件返回对象上的函数，在 `decorators.ts` 里**闭包直调**（L188 `decoration.render({ text: slice })`），没有注册表、没有回查、没有 `data-dec-key`、没有 `nyaachat-plugin-decoration` 元素。
> 现行对应语义是：**`render` 抛错 ⇒ 只保留正文、丢掉这个装饰节点**（上表末行）。

## 5. 后端能力接入流程

### 5.1 四段链路总览

插件要调外部服务，必须串起四段，**缺一段就调不通**：

```
① 插件声明           NyaaPlugin.backend: PluginBackendDeclaration[]
        ↓  （能力名 → 同源路径；加载期校验前缀，调用期再次兜底）
② 浏览器             callBackend(capability, payload) → fetch("<path>")
        ↓  （同源！浏览器从不直连上游）
③ nginx              精确 location = /api/ext-host/plugins/<id>/<capability>
        ↓  proxy_pass http://ext-host:3099/plugins/<id>/<capability>
④ ext-host 边车      POST /plugins/<id>/<capability>
        ↓  （上游 URL / 模型 / 鉴权只从 process.env 读）
   真实上游（Edge-TTS 兼容端点等）
```

**关键安全设计**：上游地址、模型、鉴权**全部由服务端 `process.env` 决定**，请求体**无法**影响它们。被删除的 `/openai/custom/generate-voice` 之所以危险，正是因为它的上游地址来自 **body 的 `provider_endpoint`**（任意 URL 转发 = SSRF 面）。**该形态不得以任何理由重建。**

### 5.2 ① 插件声明（`PluginBackendDeclaration`）

```ts
/** 边车能力声明：能力名 → 实际路径。前端不得调用未声明的能力。 */
export interface PluginBackendDeclaration {
  capability: string;
  /** 形如 /api/ext-host/plugins/quote-tts/speech */
  path: string;
  method: "POST" | "GET";
  description?: string;
}
```

约束：`capability` 全仓唯一；`path` **必须**以 `/api/ext-host/plugins/<你的 meta.id>/` 开头；`method` 只有 `"POST"` / `"GET"`。

### 5.3 ② 浏览器侧调用（`src/plugins/backend.ts`，L71-113）

1. **查表**：`getPluginBackendDeclaration(pluginId, capability)`；**未声明 ⇒ 直接 throw**（`[plugins] 插件 "x" 未在 backend[] 中声明能力 "y"，调用被拒绝`）；
2. **前缀再校验**：`declaration.path` 不以 `/api/ext-host/plugins/<id>/` 开头 ⇒ 同样 throw（L83-88）。这是安全红线在**运行时的兜底** —— 加载期校验只在开发期 `console.error`；
3. **构造请求**：
   - `POST`：`headers: { "Content-Type": "application/json" }`，`body: JSON.stringify(payload ?? {})`；
   - `GET`：payload 里的键值转成 query string（`undefined` / `null` 跳过；非字符串值 `JSON.stringify`）；
4. **响应解析**：`content-type` 含 `json` ⇒ 解析 JSON；`text/*` ⇒ text；否则 ⇒ **`Blob`**（音频走这条）；非 2xx ⇒ throw，错误文案带上游 `error`/`message` 字段或响应体前 300 字符。

**用法**：

```ts
const blob = await ctx.callBackend<Blob>("speech", { input: "你好", voice: "zh-CN-XiaoxiaoNeural" });
```

### 5.4 ③ nginx：只加**精确匹配** location

`nginx.conf` 现状（L213-226，逐字）：

```nginx
    # quote-tts 插件语音合成（受控 TTS 代理）。上游 URL / 模型 / 鉴权只在
    # ext-host 容器的 process.env 里；浏览器只能打这一个精确路径。TTS 合成
    # 可能耗时十几秒（ext-host 侧默认上游超时 60s），故读写超时取 120s。
    location = /api/ext-host/plugins/quote-tts/speech {
        proxy_pass http://ext-host:3099/plugins/quote-tts/speech;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header User-Agent "NyaaChat";
        proxy_redirect off;
        proxy_connect_timeout 5s;
        proxy_send_timeout    120s;
        proxy_read_timeout    120s;
        proxy_buffering off;
    }
```

规范：

- 一律用 **`location =`（精确匹配）**，与既有 `location = /api/ext-host/t2i-agent/chat`（L187）、`location = /api/ext-host/health`（L202）同风格；
- **禁止**恢复 `/api/ext-host/` 通配前缀 —— `nginx.conf` L199-201 的注释明确该前缀已在早前清理中删除（安全红线 SSOT §7.4）；
- 长耗时路由要给足 `proxy_send_timeout` / `proxy_read_timeout`（现有 TTS/T2I 路由取 120s / 300s），并开 `proxy_buffering off`；
- `dev-server/nginx/default.conf.template` 的 `dev-ext-host:3099` 版本要**同步镜像**（L197-208）。

> ⚠️ **dev 模板现存的两处偏差**（写作时实测，dev-only，**不是**本次插件改动引入）：`dev-server/nginx/default.conf.template` L210-219 仍有 `location /api/ext-host/ { proxy_pass http://dev-ext-host:3099/; }` 通配前缀，L221-230 仍有 legacy 的 `location = /api/openai/custom/generate-voice`。两者都由 dev 容器仓库的首个提交 `303f8e2` 引入（`git log -S "location /api/ext-host/"` 实测），**早于**本次插件工作；生产 `nginx.conf` **没有**这两个 location。见 §8 D-9。

### 5.5 ④ ext-host 路由

`ext-host/src/server.js` 现为 368 行 / 13995 B（`route()` 在 L324-342）。路由表：

| 方法 | 路径 | 处理 |
|---|---|---|
| GET | `/health` | `{ ok: true, service: "nyaachat-ext-host" }` |
| GET | `/status` | `statusPayload()`（L307-322），含 `plugins.quoteTts.configured` |

**新增一条插件路由时要照抄的骨架**：

```js
// ① 配置只在模块顶层从 env 读一次（不要在请求处理里读）
const X_UPSTREAM_URL = (process.env.PLUGIN_<ID>_UPSTREAM_URL || "").trim();

// ② 未配置 ⇒ 503 + 结构化错误（不是 500）
if (!configured) return errorResponse(503, "<id>_not_configured", "...");

// ③ 只读白名单字段，其余一律忽略
const input = typeof payload.input === "string" ? payload.input.trim() : "";

// ④ 上游请求体由服务端拼装，body 不可覆盖
const upstreamBody = { model: MODEL_FROM_ENV, input, voice, response_format: "mp3" };

// ⑤ 连接失败/超时 ⇒ 502，且不把上游原始响应体回给浏览器
// ⑥ 成功 ⇒ 透传音频字节流 + 上游 content-type
```

**错误码约定**（现有实现）：`quote_tts_not_configured`(503) / `quote_tts_input_required`(400) / `quote_tts_input_too_long`(400) / `quote_tts_invalid_voice`(400) / `quote_tts_upstream_unreachable`(502) / `quote_tts_upstream_error`(502)；`readJson` 请求体超限 ⇒ 413、非法 JSON ⇒ 400（L22-45）。

### 5.6 env 命名规范

| 变量 | 默认值 | 位置 | 说明 |
|---|---|---|---|
| `PLUGIN_QUOTE_TTS_UPSTREAM_URL` | 无（**未配置 ⇒ 503**） | ext-host 容器 | Edge-TTS 兼容端点**基地址**；ext-host 自行追加 `/v1/audio/speech`（`server.js` L119）。**非密钥** |
| `PLUGIN_QUOTE_TTS_MODEL` | `tts-1-hd` | ext-host 容器 | 上游模型 id |
| `PLUGIN_QUOTE_TTS_API_KEY` | `none` | ext-host 容器 | 上游鉴权。**默认值必须仍发出非空 `Authorization: Bearer none`**（上游 schema 要求非空） |
| `PLUGIN_QUOTE_TTS_TIMEOUT_MS` | `60000` | ext-host 容器 | 上游超时；代码内置钳制区间 `[1000, 600000]`（`clampInt`，L60 / L191-194） |

命名规范：`PLUGIN_<PLUGIN_ID 大写、连字符换下划线>_<KEY>`。**每个新插件的新变量必须同步写进两处 `.env.example`**：

- `.env.example`（L57-72，真实值形态，`PLUGIN_QUOTE_TTS_UPSTREAM_URL=http://your-tts-host:0000`）
- `dev-server/.env.example`（L45-52，**故意留空** upstream URL 以便验证 503 分支）

**布置到容器的路径**：`docker-compose.yml` 的 `ext-host` 服务用 `env_file: [.env]`（L43-44）+ `environment: [TZ, PORT=3099]`（L45-47）；dev 侧是 `dev-server/docker-compose.yml` 的 `dev-ext-host`（L44-53，`env_file: [.env]`，`PORT=3099`）。⇒ **加一个 `PLUGIN_*` 变量不需要改 compose**，写进 `.env` 即生效。

### 5.7 安全红线（不可协商）

1. **上游 URL / 模型 / 鉴权只能来自 `process.env`**。请求体出现 `provider_endpoint` / `baseUrl` / `model` / `api_key` 等字段一律**忽略**，绝不透传。这是被删除的 SSRF 面的反面，**不得重建**。
2. 前端**不得**调用未在 `backend[]` 中声明的能力（`callBackend` 查表失败即抛）。
3. `backend[].path` 必须落在 `/api/ext-host/plugins/<pluginId>/` 前缀下（加载期校验 + 调用期兜底，双重）。
4. nginx 只加**精确匹配** location，**不恢复** `/api/ext-host/` 通配前缀。
5. **任何密钥不入库**：新增 env 只写 `.env.example`，真实值进 `.env`（两处均已 gitignore）。
6. 上游非 2xx / 不可达 ⇒ **502 + 结构化错误**，**不把上游原始响应体**直接回给浏览器（可能回显凭证材料）；现有实现连 `upstream.body` 都显式 `cancel()` 掉（L155-159）。
7. 输入必须**限量**：`input` 长度上限（quote-tts 为 1000 字符）、`voice` 白名单（14 个 Edge-TTS zh 音色，非法值 400）、request body 字节上限（`readJson(request, 64 * 1024)`）。

## 6. 新增一个插件的完整步骤清单

以插件 `foo-bar` 为例。**分五步，缺一不可。**

### 步骤 1 —— 建插件目录与实现

```
plugins/foo-bar/
  plugin.tsx          # export default 一个 NyaaPlugin 对象（没有 definePlugin 辅助函数）
  （可选）XxxSettings.tsx / XxxButton.tsx / 常量表等
  （可选）README.md    # 该插件的说明/移植记录
```

`plugins/foo-bar/plugin.tsx` 骨架：

```tsx
import type { NyaaPlugin } from "../../src/plugins/types";
// 若需要 SettingsPanel：
// import { FooBarSettings } from "./FooBarSettings";

const plugin: NyaaPlugin = {
  meta: {
    id: "foo-bar",              // kebab-case，与目录名一致，全仓唯一
    name: "Foo Bar",
    description: "一句话说明这个插件干什么",
    version: "1.0.0",
    author: "…",
    icon: "Puzzle",             // lucide-react 图标名，可省
    order: 10,                  // 可省，缺省 0
  },
  defaults: { enabledVoice: "zh-CN-XiaoxiaoNeural" },
  // setup: (ctx) => { …; return () => { /* 清理副作用 */ }; },
  // SettingsPanel: FooBarSettings,
  // decorators: { messageText: [myDecorator] },
  // backend: [{ capability: "speech", path: "/api/ext-host/plugins/foo-bar/speech", method: "POST" }],
};

export default plugin;
```

要点：
- `import type { … } from "../../src/plugins/types"` —— 相对路径回到仓库根下的 `src/plugins/types`；
- **没有 `definePlugin`**，直接对象字面量，靠 `tsc --noEmit` 校验形状；
- `setup` 返回的函数是 disposer（停用时调用）。

### 步骤 2 —— 注册（唯一入口）

`plugins/registry.ts`：

```ts
import type { NyaaPlugin } from "../src/plugins/types";
import fooBar from "./foo-bar/plugin";

const registered: NyaaPlugin[] = [fooBar];   // ← 只改这一处
```

**不注册 ⇒ 插件不存在**：UI 列表、配置归一化、`getPluginById` 全部看不到它。

### 步骤 3 —— 工程配置

| 文件 | 要不要改 |
|---|---|
| `eslint.config.js` | ❌ **不用改**：`files` 已是 `["src/**/*.{ts,tsx}", "plugins/**/*.{ts,tsx}"]`（L38），通配已覆盖 |
| `tsconfig.json` | ❌ **不用改**：无 `include`，全仓纳入，`plugins/**` 自动进 `tsc --noEmit` |
| `vite.config.ts` | ❌ **不用改** |

**但必须跑一遍**：`npm run lint`（= `tsc --noEmit && eslint .`）。

### 步骤 4 —— 若需要消息装饰 / 条目文本渲染器 / 后端能力（否则跳过）

**装饰**：在 `plugin.tsx` 里填 `decorators.messageText: [myDecorator]`，遵循 §4 的全部约定 —— 特别是**区间以"当前块纯文本"为坐标系**，返回合法整数区间。

**条目文本渲染器**（§2.5.1）：在 `setup(ctx)` 里 `const dispose = registerPromptTextRenderer(renderer)`，
并把 `dispose` 放进返回的清理函数；`renderer` 需要 `pluginId` / `matches(text)`（同步、廉价）/
`render(text, ctx)`（可异步），可选 `takeWrites()`。要点：

1. **只允许 `import type` 自 `src/plugins/types`**，其余走叶子模块（`src/plugins/promptText`）——
   值导入 `src/plugins/{index,runtime,registry,backend}` 会构成模块环、插件**静默消失**（§7.1 第 24 条）。
2. `matches()` **必须廉价且同步**（它在组装期的分组判定里被问，也在 pre-pass 里被问）；
   它抛错会被宿主按"不匹配"处理（判据不能因为一个坏渲染器把整个请求炸掉）。
3. `render()` 的**降级语义见 §2.5.1 K3**：要丢弃就返回**空串**（不是 `undefined`、不是抛错），
   抛错也会被宿主按条目降级，但**日志/来源会不同**（见该节的说明）。
4. 需要写变量时：在本轮缓冲里收集 `PromptTextWrite[]`，由 `takeWrites()` 交出；
   **不要**自己调宿主的变量 API（宿主在 pre-pass 末尾统一提交，幂等键 = `turnId`）。

**后端能力**：

1. `plugin.tsx` 的 `backend[]` 声明 `capability` + `path`（前缀必须是 `/api/ext-host/plugins/foo-bar/`）+ `method`；
2. `nginx.conf` 加一条 `location = /api/ext-host/plugins/foo-bar/speech { proxy_pass http://ext-host:3099/plugins/foo-bar/speech; … }`；
3. `dev-server/nginx/default.conf.template` 同步镜像（`dev-ext-host:3099`）；
4. `ext-host/src/server.js` 的 `route()` 加分支，按 §5.5 骨架实现；若需要新的配置位，在 `/status` 的 `plugins` 段加 `fooBar: { configured: … }`；
5. `.env.example` 与 `dev-server/.env.example` 补 `PLUGIN_FOO_BAR_*`（真实值不入库）；
6. **不需要改 `docker-compose.yml`**：ext-host/dev-ext-host 都是 `env_file: [.env]`。

## 7. 常见错误与自查表

### 7.1 高频错误

| # | 症状 | 根因 | 处置 |
|---|---|---|---|
| 1 | 插件在扩展列表里**完全不出现** | 忘了在 `plugins/registry.ts` 里加 import 与数组项 | 注册表是唯一权威，UI 从不读 `AppState.plugins` 的键 |
| 2 | 控制台 `[plugins] id (xxx): meta.id "…" 不匹配 …` | `meta.id` 不是 kebab-case / 有大写 / 以 `-` 开头 | 必须匹配 `/^[a-z0-9][a-z0-9-]*$/` |
| 3 | 控制台 `backend capability "x" 已被插件 "y" 声明` | 两个插件用了同一能力名 | 能力名全仓唯一，改名 |
| 4 | 控制台 `backend path "…" 必须以 "/api/ext-host/plugins/<id>/" 开头` | 路径没锁定在自己的命名空间 | 前缀必须是 `/api/ext-host/plugins/<你的 id>/` |
| 5 | 配置改了、刷新就丢 | 直接改了 React state / 自己存了内存变量，没走 `updateConfig` | 写入**必须**经 `ctx.updateConfig` / `SettingsPanel` 的 `updateConfig` |
| 6 | `[plugins] 配置 writer 尚未注册（App 未挂载？）` | 在 App 挂载前就调了 `updateConfig` | 用 `setup`（启用后才调）或用户交互触发 |
| 7 | `[plugins] updateConfig 被未知插件调用：x` | 用了错的 `pluginId`（与 `meta.id` 不一致） | 两者必须一致 |
| 8 | `[plugins] 插件 "x" 未在 backend[] 中声明能力 "y"，调用被拒绝` | 忘了声明，或能力名拼错 | 在 `backend[]` 里声明 |
| 9 | 控制台反复 `[plugins] 插件 "x" 返回了非法装饰区间，已丢弃` | 返回了 `NaN` / 小数 / `start ≥ end` / 越界 | 只会丢那一条，不会崩；按 §4.4 修 |
| 10 | 控制台 `装饰区间 [a, b) 与已接受区间重叠，已丢弃` | 同一块里两个装饰重叠（可能来自两个插件，也可能自己重复） | 排序后的"先到者胜"，**不要依赖插件顺序**；自己先去重 |
| 11 | 装饰位置整体偏了几个字符（粗体/链接处尤其明显） | 偏移按"原始 markdown"或"整条消息"算，而不是**当前块纯文本** | 见 §4.3 |
| 12 | `“引用”` 被包在 `<strong>` 里时没有装饰 | `renderTextWithQuotes` 只转换 string children，嵌套元素原样透传 | **既有行为**，不是 bug（§4.7） |
| 13 | 控制台 `[plugins] 插件 "x" 的装饰 render 抛错，该片段仅保留正文` | `render` 实现里抛了 | 修 `render`；宿主已做降级（正文照常输出、只丢装饰节点），**正文不会丢**。⚠️ 若你把降级改成"用 `slice` 顶替 rendered"，正文会变成两份（§4.5） |
| 14 | 加了新插件后 `npm run lint` 报 react-hooks 错误 | 插件里有 hooks 违规（**这正是 lint 接线要达到的效果**） | 修代码，不要绕过 lint |
| 15 | 停用插件后事件还在跑 | 没用 `on()` 返回的取消函数 | 虽然运行时会兜底清理，但请自己退订；`setup` 里注册的其它副作用放进 disposer |
| 16 | 改插件配置导致整屏消息重渲染 | 订阅者用了新对象而非运行时快照 | 用 `useSyncExternalStore(subscribePluginRuntime, getPluginRuntimeSnapshot)` |
| 17 | 老版本导入新版本导出的存档，插件配置"没了" | 老版本不认识 `plugins` 字段（`EXPORT_VERSION` 保持 9 的已知代价） | 预期行为；写进你的插件 README/交接即可 |
| 18 | 期望"用户装过的插件一直都在" | 插件集合以**代码**为权威，不以存档为权威 | 这是定调，不是 bug（§3.5） |
| 19 | 想把上游地址做成"用户可填" | **安全红线**：上游只能由服务端 env 决定 | 需要多个上游就加环境变量，不要开 body 通道 |
