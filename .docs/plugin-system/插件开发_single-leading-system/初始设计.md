## 1. 结论与本轮范围

本次报错的直接机制已经确认：**bw4090 上该模型的 Jinja 模板，只允许消息数组第 0 项为 `system`；NyaaChat 当前会将静态协议锚点、人设、永久世界书拆成多条 `system`。** 第二条 `system` 即可触发 `System message must be at the beginning.`，并不需要很长的世界书。

使用服务器实际模板的本地对照渲染，已复现相同异常。将静态 system 合并、动态规则折入最新 user 后，合成请求可通过模板渲染。这确认了结构冲突与结构修复方向，**尚不等于真实角色、多轮生成和输出质量已验收通过**。

**开发前真实请求验证已完成（2026-10-18，§2.9）：** 拟定的消息转换已在当前 Ollama 模型上通过静态混排、动态规则、RosettaStone 四种开关组合、历史、多模态内容及连续工具调用的最小合成测试；只完成静态合并或只完成尾规则折叠都会继续触发原异常。没有发现新的模板位置异常，但发现一次测试输出上限导致的 thinking 截断，已单独记录。此验证证明方案在目标部署上的可行性，不替代尚未实现的插件和真实复杂角色回归。

不宜将问题归因于“去审查修剪后失去了复杂世界书能力”：实际模板与 Qwen 官方基础模型发布的模板完全一致。量化、去审查权重和模板角色限制是不同层面，目前证据指向后者。

**工具能力结论（2026-10-18更新）：用户已在 NyaaChat 中实测确认，该模型通过 `tool_calls` 调用当前接入的 NyaaChat-MCP 工具全部成功。** 工具调用已具备应用内实际成功证据，本次改造应保持这项能力并做回归验证，无需将“是否支持已接入工具”继续列为待确认问题。详细记录见§2.7。

**附件能力结论（2026-10-18更新）：用户已在 NyaaChat 对话中实测确认，该模型的图片和文档附件识别均通过测试。** 两类附件的当前应用链路已获得用户验收，后续提示词兼容改造须保持其行为并做回归。详细记录见§2.8。

根据用户在本次评估中的补充，实施前提固定为：

- 使用 `Qwen3.6-35B:Q4-K-M` 时，**AnswererFlagalac 保持关闭，推荐明确选择 `target=none`**。
- **不使用 RuleBreaker**。它当前通过按钮发送普通 user 文本，没有独立总开关；本次不为其设计兼容能力。
- **RosettaStone 的“字数控制”“语言约束”必须保留**，支持独立开关、自定义模板及同时启用。
- 复杂 World Info、变量宏、已启用的 EJS 模板功能，继续遵循当前实现的组装语义。
- 本轮只产出评估，不执行实现、提交推送、模型重建或服务重启。

**已确认架构方向（D1）：在现有出站处理层增加通用的“消息结构兼容策略”，由模型配置选择是否启用「仅首条系统消息」（`single-leading-system`）；不建立独立的 Ollama 消息规范化器。** 静态前缀与动态尾部的具体处理方案见§5，其中尚未确认的语义取舍继续等待用户逐项决策。

**已确认交付形态与思考设置（D2，修订后）：`single-leading-system` 作为独立扩展插件开发；模型 thinking 模式开关放在该插件系统的 UI 内，默认开启，由用户决定是否关闭。** 默认开启的依据是 NyaaChat 长期兼容 SillyTavern 角色卡、世界书及多步工具的复杂使用场景。D2细化D1的实现归属与配置入口，不改变其通用出站适配方向。具体插件接口与挂载方案需在实施设计时核对，尚未开始实现。

**已确认兼容前提提示（D3）：插件设置界面以现有扩展插件 UI 规范中的高亮警告文本块，提示用户关闭 Bypass（绕过机制）中的 AnswererFlagalac。** 本次不新增发送前提示、确认或拦截机制，关闭操作由用户自行完成。

**已确认适用范围声明（D4）：插件设置界面的说明首先声明，插件适用于目前已核验的 Qwen3.6 / Qwen3.5 官方模型的聊天模板约束。** 适用范围不限定于通过 Ollama 接入的 HauhauCS 模型；通过其他供应商接入这些模型时，同样可以使用该消息结构兼容策略。

**已确认截断处理（D5）：采用“截断识别＋保留工具结果的有限恢复”。** 本次不设置、推算或自动增加 `max_tokens`、上下文长度和输出预算配额；保留用户部署侧的限制与配置。

### 2.2 模型发布信息与上游模板

已直接读取用户指定的 HauhauCS 模型卡及 HF 仓库元数据：仓库 revision 为 `f12a584fecbeb5f20001130d8ecd66c9327ae685`。模型卡标注基础模型为 `Qwen/Qwen3.6-35B-A3B`，列有 Q4_K_M GGUF、思考/非思考建议参数、视觉投影文件以及 262K 原生上下文。上述为发布者说明，不代表本地部署全部启用。

HauhauCS GGUF 仓库没有单独的 `tokenizer_config.json`；该地址返回 404。本轮另行读取 Qwen 官方基础模型的 `tokenizer_config.json`：其中 `chat_template` 的长度及 SHA-256 与 bw4090 `/api/show` 返回值完全相同。

模板关键约束：

```jinja
{%- for message in messages %}
    ...
    {%- if message.role == "system" %}
        {%- if not loop.first %}
            {{- raise_exception('System message must be at the beginning.') }}
        {%- endif %}
    ...
```

异常位于模板第 85 行，与用户报错行号、异常文本吻合。这里的 `loop.first` 指消息数组首项，**并非“历史开始前的多条 system 都允许”**。

模板还要求至少存在真实 user，支持 user/assistant/tool 分支，拒绝 system 中的图片/视频。它包含工具与 thinking 的格式化逻辑，不代表 NyaaChat 当前所有相关功能都已适配。

### 2.4 特性归属断言：属于哪一类模型

**断言：本次异常源自已核验的 Qwen3.6 / Qwen3.5 官方模型的聊天模板约束，目标 HauhauCS 模型沿用了该约束。它不是所有 Qwen 模型的通用特性，不是 HauhauCS 系列的专有特性，也不是当前这一个量化模型的特殊情况。**

这里的“特性”专指“只有数组第一条消息可以是 system”的**模板校验行为**，不能推导成模型权重无法理解多层规则或复杂世界书。

### 2.9 开发前最小命令测试：真实 Ollama 请求与策略消融

2026-10-18，应用户要求，在正式开发前对拟定策略进行真实请求验证。目标为当前通过隧道接入的 `Qwen3.6-35B:Q4-K-M`，Ollama `0.33.1`；工具经 dev `/api/mcp` 调用实际 NyaaChat-MCP。

#### 测试方法与边界

- 使用一次性 Python 原型，按明确的静态前缀、历史、最新 user、动态尾部边界执行转换；没有修改 NyaaChat、插件、模型模板或持久化配置。
- 静态 system 按原相对顺序拼成一条；静态 assistant 备注保留角色并移到首 system 后；动态尾部只追加到最新 user 的 text part。
- 合成场景包含用户 / 角色人设、静态世界书、assistant备注、借阅历史、动态场景 / 变量 / 模板设定，以及字数和语言约束。变量 / EJS 使用的是**已渲染结果的合成文本**，没有运行应用插件的宏展开或EJS引擎。
- 大部分请求保持模型默认thinking，确认收到非空reasoning；另有一组 `reasoning_effort=none` 对照。思考正文不写入报告。
- 常规请求测试上限为2048输出tokens；工具汇总复测与预算耗尽场景上限为8192。没有给应用写入这些限额。
- 请求总计22次：6次故意构造的不兼容请求均返回预期模板500；其余16次HTTP200，其中1次因输出预算耗尽而未产出正文。不能将本轮概括为“全部请求都成功”。

#### A. 原异常定位与消融结果

所有负例均返回相同的模板第85行异常 `System message must be at the beginning.`，耗时约20—60ms。

| 用例 | 发送角色序列 | 结果与位置 |
| --- | --- | --- |
| B0 基准 | `system → user` | HTTP200，有正常正文 |
| E1 连续system | `system → system → user` | HTTP500；首个非法system位于索引1，即第2条 |
| E2 交错system | `system → assistant → system → user` | HTTP500；首个非法system位于索引2，即第3条 |
| E3 尾system | `system → user → system` | HTTP500；首个非法system位于索引2，即第3条 |
| E4 合成九条 | `system → system → system → assistant → system → user → assistant → user → system` | HTTP500；首个非法system位于索引1，后面还有索引2、4、8的system |
| E5 只合并静态区 | `system → assistant → user → assistant → user → system` | HTTP500；仍残留索引5的尾system |
| E6 只折叠动态尾 | `system → system → system → assistant → system → user → assistant → user` | HTTP500；首个非法system仍在索引1 |

索引均从0开始。位置判断由受控输入与模板顺序遍历中的 `loop.first` 条件共同确定；服务端错误本身没有输出消息索引。

**定位结论：** 对这组纯文本system输入，第一个索引大于0的system就会终止模板处理，后续非法system不会在同一次错误中逐一列出。因此现有代码只折叠尾部，并不能修复静态前缀多system。原始九条请求具体对应哪个人设或世界书仍未知，但这不影响确定故障机制和必需转换步骤。没有将合成九条请求冒充用户原始请求重放。

#### B. 完整策略正例

| 用例 | 实际验证结果 |
| --- | --- |
| N1 九条转为单首system | 输出角色为 `system → assistant → user → assistant → user`；HTTP200，正确回答角色名“青禾”、馆名“星河馆”、历史借阅“天文图鉴”和动态开放“二楼” |
| N2 更新动态规则 + 流式 | 静态前缀不变，仅把本轮开放楼层改为三楼；流式正常结束，回答更新为“三楼” |
| N3 同组合关闭thinking | 无reasoning字段，正常回答上述四项事实，无模板错误 |
| R 两项RosettaStone四组合 | 全关、仅字数、仅中文、两项同时开，均HTTP200并正常结束；启用项按预期位于最新user的output_constraints，样本输出符合简短中文要求 |
| V1 图片 + 文档文本 + 记忆 / 检索parts | 真实传入内存生成的红色PNG及已提取文档文本，正确回答“红色”和文档代号“蓝鹭”；原有content parts保持不变，仅追加尾约束 |

RosettaStone测试采用短字数约束以控制测试规模，没有验证默认1000—2000字长输出。中文用户问题本身也会引导中文回答，不能仅凭这些结果证明语言约束块的独立因果效果。V1测试证明消息转换保留了图片及文档文本传递，不是重新验收文件上传、文档解析或所有格式。

额外的原型本地断言通过：入参不被修改；动态规则变化不改变静态system及assistant备注；在明确边界下再次规范化已转换的消息不会重复追加文本；未分类的历史中段system不会被无条件提升到首system。上述是测试原型的不变量验证，正式插件仍需自己的测试。

#### C. 真实连续工具调用与输出预算边界

在同一合成人设 / 世界书 / 历史 / 动态规则基础上，使用服务真实返回的 `get_current_time` schema，不强制tool_choice，要求依次查询上海时间和UTC时间：

1. 模型返回 `get_current_time(timezone=Asia/Shanghai)`，dev MCP执行成功。
2. 回传对应assistant工具调用和tool结果后，模型再返回 `get_current_time(timezone=UTC)`，执行成功；这一轮使用流式解析。
3. 再次回传结果后，模型应汇总两个时间和馆名。**首轮测试在此处返回HTTP200、finish_reason=length、2048 completion_tokens，仅有reasoning而无正文。** 这属于测试设置的输出预算耗尽，不是Jinja异常或工具绑定失败。
4. 将同场景最终汇总上限提高到8192，重新执行上述闭环，最终流式返回两个真实时间及“星河馆”，finish_reason=stop；本次实际只生成1062 completion_tokens。由于重新生成具有随机性，不能宣称8192是必要上限，也不能声称已做了严格可复现的预算性能比较。
5. 另构造与当前应用一致的 `[tool_error] tool-call rounds exhausted; respond with what you know` 工具结果，并去掉tools列表，最终流式请求正常结束，明确回答两个时间均“未获取”、馆名为“星河馆”，没有编造时间。

工具消息的 `tool_calls`、`tool_call_id` 与结果对应关系保持完整，工具轮次不重复注入动态尾部。续轮没有额外回传reasoning字段，当前合成场景能够完成。新增发现是**thinking输出预算可能导致HTTP200但无正文**；NyaaChat当前普通请求不传本测试的2048上限，不能直接推定应用必现，也不因此擅自增加采样 / 输出限额配置。

#### D. 对开发决策的影响

**可以将当前方案作为后续插件实现的已实测可行起点。** 在目标部署上，必须同时处理静态多system / 混排和动态尾system；现有尾折叠可以复用，但不能代替静态规范化。已测试的完整转换没有出现新的模板位置异常。

仍保留以下边界：静态assistant重排的跨角色顺序变化尚待用户确认；真实复杂角色、完整EJS / 变量链、长上下文、全部工具及附件组合、插件启停 / 配置持久化、其他供应商均需正式实现后回归。HTTP200和少量事实命中不等于所有世界书语义无损，thinking预算截断也应作为诊断与回归观察项。

临时测试脚本在测试结束后删除；图片在内存中构造，无文件、账号或数据库测试数据。保留本节和服务正常访问日志作为证据，不修改或清理用户原有日志。

## 3. 当前真实提示词组装

架构规范 `.docs/llm-chat-prompt-architecture-standard.md` 的制定日期为 2026-06-10。本节以 `124c557` 的源码行为为准。

### 3.1 业务组装层

主要入口为 `src/lib/chatPipeline.ts:793` 的 `buildRequestMessages`。当前布局为：

```text
静态前缀（多条消息）
  system：Session Protocol 授权锚点，始终存在
  system：用户人设（若有）
  system：角色人设（若有）
  system / assistant：静态永久世界书，按条目顺序
历史（已过边界筛选，只取正常对话）
最新 user
  用户原文 / 图片等原有 parts
  memory_context（若有，volatile part）
  search_context（若有，volatile part；含合并后的检索参考资料）
唯一动态尾 system（若有内容）
  session_rules：关键词世界书、动态永久条目、模板设定、MCP使用规则
  output_constraints：RosettaStone 字数控制 / 语言约束
  session_conventions：有效的 AnswererFlagalac 载荷，本方案前提下不生成
```

注意：变量宏和 EJS 已使“永久条目必然静态”不再成立：

- 普通静态永久条目保留在前缀。
- 含变量宏的永久条目进入动态尾部“变量状态”。
- 本轮被渲染器实际接管的永久或关键词条目进入“模板设定”；启用状态和本轮结果共同影响分流，不能仅凭文本包含 EJS 就搬动。
- 关键词普通条目分为“硬约束”“场景设定”。动态区的 assistant 位置条目以 `[Assistant Note]` 标记存在于同一规则块，不会单独形成 assistant 消息。
- 插件异步 pre-pass 在组装之前执行，沿用占位符 → 变量宏 → 正则 → EJS 的处理链。兼容化阶段不能重新执行渲染，以免重复变量写入或改变本轮结果。

真正会形成“静态区 assistant 与后续 system 交错”的，是静态永久世界书的 `position=assistant`。只合并开头相邻 system，并不能覆盖这类角色。

### 3.2 OpenAI 兼容出站层

Ollama 通过 `providerToApiSettings` 进入现有 OpenAI 兼容路径，保留 `llmProviderKind='ollama'`，没有独立的 Ollama 消息规范化器。

`fetchOpenAI` 当前在第一次调用之前执行：

```text
有效 AnswererFlagalac 尾载荷 → 保留尾部真实 system
其他情况                    → 将唯一尾 system 折入最新 user
```

本次要求 AnswererFlagalac 关闭，因此走第二条。`foldTailSystemIntoLatestUser` 将尾文本追加为 user 的 volatile text part，保留原有内容和图片等 parts。它**没有合并静态前缀的多条 system，也没有处理交错 system**。

最终 `callOpenAIOnce` 仅去掉 content 中内部 volatile 标志，再发送消息。MCP 多轮会在消息末尾追加 assistant 的 tool calls 与对应 tool 结果，重试和工具预算耗尽也会再次发请求。

### 3.3 与旧规范的差异及本次影响

| 项目 | 当前行为 | 评估影响 |
| --- | --- | --- |
| 静态前缀 | 锚点、人设、世界书是多条消息，可夹有 assistant | 不能假设只有一条首 system |
| OpenAI / DeepSeek 等普通尾规则 | 当前共享 OpenAI 兼容实现默认折入 user | 不应照旧规范表格认定都原样发送尾 system |
| AnswererFlagalac | 有效载荷仍保留真实尾 system | 与目标模板冲突；按用户要求排除在本次支持范围外 |
| RosettaStone | 独立于 AnswererFlagalac，生成 output_constraints | 关闭 AnswererFlagalac 不能连带删除 RosettaStone |
| 变量宏 / EJS | 可将永久条目分流到动态尾部 | 不能把这些动态内容合并进首 system |
| 检索 / 记忆 | 作为最新 user 的参考数据 | 不能为修复模板而提升到 system |
| 请求日志 | 当前源码只记录地址、模型、工具名称，已不附带完整 renderedMessages | 用户旧日志不等于当前最终出站 payload；诊断应使用脱敏结构摘要 |

原有 Anthropic 适配有自己的 system 提取、尾规则处理及缓存逻辑，应保持其当前行为。源码部分注释仍沿用旧说法，实施时应同步校准相关文档与注释，不能据注释反推实际行为。

## 4. RosettaStone 必须如何保留

两项分别为 `settings.bypass.wordCount` 与 `settings.bypass.languageConstraint`；各有 `enabled` 与 `template`。当前模板支持 `{{user}}`、`{{char}}` 替换，按字数控制在前、语言约束在后的固定顺序组装。

正确目标布局为：

```text
system：仅静态锚点、人设和静态 system 世界书的合并内容
assistant：静态永久 assistant 备注（若有；处理取舍见第5节）
正常历史
最新 user 的 parts：
  用户发言 / 图片等原有内容
  记忆、检索参考资料（若有）
  <session_rules>动态世界书、变量、模板、MCP规则</session_rules>（若有）
  <output_constraints>字数控制、语言约束</output_constraints>（若有）
```

`output_constraints` 继续独立于 `session_rules`，不把输出风格约束提升为场景硬约束，也不更改其让位于用户当轮明确要求的现有定位。没有 World Info 时，RosettaStone 单独开启也必须被正确折叠；两个条目全关或模板为空时不生成空壳。

这部分**可以复用现有尾部折叠机制**，无需为该模型重写 RosettaStone，也不需要开启 AnswererFlagalac。字数与语言属于自然语言软约束：适配应保证传递完整、顺序正确和模型基本遵循，不能承诺每次精确计数字数或绝无其他语言。

按D2，该策略由独立扩展插件承载，thinking开关也在该插件系统UI中提供；不再将新增内置供应商设置页控件作为已定方案。插件如何接入现有出站链路、宿主是否需要补充通用扩展接口，需后续源码审计确认。

按D4，插件设置说明的**首段**应先交代适用范围，再展示功能说明和D3的高亮警告。建议首段文案：

4. **静态 assistant 备注**：推荐保留 assistant 角色及各备注之间的顺序，置于合并后的首 system 与真实历史之间。这样 system 设定仍是 system，assistant 备注仍是 assistant。**原本交错的 system 与 assistant 之间的相对位置会变化**，这是必须明确接受的语义取舍。
5. **动态尾部**：在本次 AnswererFlagalac 关闭的前提下，继续把唯一动态尾 system 整体折入最新 user，包括 `session_rules` 与 `output_constraints`，保留 volatile 标记到最终序列化前。不得重复追加或折叠。
6. **请求前验证**：检查第0项之后没有 system、至少有真实 user、未残留内部元数据等必要条件。遇到无法识别的历史中段 system，应给出明确错误，不能无条件上提或丢弃。规范化应为纯函数，不修改聊天记录与入参。
7. **统一覆盖每次发送**：普通请求、流式请求、MCP 工具后续轮次及预算耗尽后的最终请求都应满足相同不变量。可以在进入循环前规范化一次、每次发送前校验；若选择每轮规范化，必须证明幂等。

静态 assistant 的另一个选项，是将其以 `[Assistant Note]` 内容并入首 system。它省去混排，但会把原 assistant 内容提升到 system，故不推荐默认采用。若要求绝对保持原始角色及消息总顺序，则当前模板下无法原样兼容，需要另选模板或拒绝这一类世界书。

## 6. 不应与本次500混为一谈的后续事项

### 6.1 思考模式与响应解析

#### 6.1.1 源码考察：不消费原生思考字段，但服务端仍会思考

2026-10-18，针对用户的第二项决策问题重新检查主对话路径，结论如下：

| 环节 | 当前实现及影响 |
| --- | --- |
| 请求参数 | `src/lib/api.ts:695` 构建普通 OpenAI 请求，未传 `reasoning_effort`、`thinking` 或 `enable_thinking`；未主动关闭思考 |
| 非流式响应 | `api.ts:732` 读取 `message.content`、`tool_calls`、usage 和 finish_reason；不读取原生 `reasoning` / `reasoning_content` |
| 流式响应 | `api.ts:784` 累积 `delta.content` 与 `delta.tool_calls`；无原生思考字段消费分支 |
| 历史与工具续轮 | `ApiMessage` 未定义原生 reasoning 字段；`chatPipeline.ts:855` 由角色和正文构造历史；工具续轮只带 assistant 正文、tool_calls 与 tool 结果 |
| 对话业务 | 当前世界书、变量、附件、RosettaStone 和 MCP 调度不依赖解析原生思考文本；它们消费正文或结构化工具调用 |
| 能力标记 | `modelHealth.ts` 的 reasoning 能力提示属于模型标签，不会启动或消费原生 thinking |

**准确表述：NyaaChat 当前没有直接消费该模型原生 thinking 输出的业务逻辑，但用户收到的正文和 tool_calls 仍可能受模型服务端思考影响。不能将“不展示 / 不解析思考”解释为“思考对回答没有作用”。**

范围说明：AnswererFlagalac 有自定义 `bazett_think` 工具通道和思考标签处理，它不等同于 Ollama 原生 reasoning 字段，且按用户约定本模型不启用。RuleBreaker 相关模板也不使用。独立 `ext-host` 绘图代理另有其上游专用 reasoning 控制，不能据此认为普通聊天请求已经关闭 thinking，也不在本次改动范围内。

#### 6.1.2 目标服务实际对照

通过现有 `/v1/chat/completions`，以单条首 system 的合成提示请求“17乘23，只回答结果”，两次均限制 `max_tokens=512`，使用相同 temperature/top_p；仅第二次显式增加 `reasoning_effort: "none"`：

| 模式 | 响应字段 | completion_tokens | 正文 |
| --- | --- | --- | --- |
| 不指定思考参数（当前主对话行为） | `role`、`content`、`reasoning`；reasoning 长度603字符 | 253 | `391` |
| `reasoning_effort: "none"` | `role`、`content`；无 reasoning 字段 | 4 | `391` |

当前实际返回字段是 **`reasoning`**，不仅是其他兼容服务常见的 `reasoning_content`。本轮只统计思考字段长度，不将思考正文写入报告。

单次总耗时分别约14.72秒与0.28秒，但首请求可能包含冷加载、后请求可复用已加载模型及前缀，因此**不将这个耗时比值当作公平性能基准**。该对照足以确认：默认响应确有思考输出；此部署支持通过 `reasoning_effort: "none"` 实际关闭它。

另在两轮请求中都显式设置 `reasoning_effort: "none"`，使用 dev MCP 的真实 `get_current_time` schema：首轮正常返回 tool_calls，工具执行成功，回传结果后模型正常给出正文，两轮均无 reasoning 字段。**non-thinking 下的最小非流式工具闭环通过。** 此测试不覆盖所有工具、图片文档、复杂世界书或流式组合；用户此前的全面功能测试未记录显式思考参数，不能自动认定为 non-thinking 的全面验收。

#### 6.1.3 已确认：插件 UI 提供 thinking 开关，默认开启（D2修订）

**用户已决定默认开启 thinking，由用户根据具体需求决定是否关闭。** NyaaChat 长期兼容 SillyTavern 角色卡，复杂世界书与多步工具调用需要综合考虑模型的任务处理效果；客户端不展示或消费原生思考字段，不构成默认关闭服务端思考的充分理由。non-thinking 保留为用户可选模式，其可用性证据仍见§6.1.2。

模型 thinking 模式开关放在 `single-leading-system` 独立扩展插件系统的 UI 内，默认开启。思考控制与消息结构兼容是同一插件内的不同职责：前者影响生成行为，后者满足模板角色约束；不把“选择严格消息策略”视为模型不支持thinking。

插件对选定模型生效且thinking关闭时，应在每次实际出站请求中明确发送受服务支持的关闭参数，包括工具续轮；不靠删除响应字段、提示词里要求“不要思考”或隐藏 UI 来关闭。开启时应使用经过验证的启用方式。当前仅确认目标部署的关闭参数有效，不将其直接推广为所有供应商的通用参数。

复杂世界书的约束协调、多步工具选择、长文档分析等任务可能从服务端思考中受益，关闭后的质量变化尚未全面实测。已确认的开关允许用户恢复thinking，并非永久禁止。该决定不包含新增思考内容展示界面，现阶段也不据此引入原生思考正文的存储或回传契约。

关闭思考不会修复多 system 的模板异常，也不会自动扩大当前32K上下文。文档附件和世界书仍占输入预算；模型卡较长上下文建议应与实际预算及资源分开评估。采样参数同样是独立选择，本次未更改应用或服务的持久化参数。

### 6.2 上下文、采样与性能

模型卡推荐参数区分 thinking / non-thinking，且建议较长上下文。NyaaChat 当前普通对话请求体没有传入独立采样参数或 `num_ctx`；模型列表中的 `contextWindow` / `maxOutput` 元数据不能据此认定已经控制服务端运行参数。

复杂世界书可能在修复结构后暴露上下文裁剪、显存占用、首 token 延迟或输出长度问题。服务日志现已确认故障前实例使用32K上下文（§2.5），后续应结合代表性角色的实际输入预算验证是否足够，不能将模型卡建议直接当成本机必须设置值。本轮没有改服务端上下文、参数或启动配置。

### 6.3 工具、图片与网络

MCP 验收必须保留 `tool_calls`、`tool_call_id`、参数及结果的对应关系；不能把工具结果合并进首 system。外部检索与记忆仍是参考数据，不因兼容处理获得运营方权威。

用户已在 NyaaChat 对话中实测图片和文档附件识别通过（§2.8），后续以保持现有能力并做回归为目标。保留 user 的图片 parts，不把图片压成字符串；文档附件沿用现有处理与传递方式，不把参考内容提升到 system。尚未记录的格式、大小和多附件边界不视为已验收。

本次已返回具体 Jinja 500，说明请求已抵达推理服务；与先前 CSP / CORS / HTTP 地址放行是不同故障。HTTPS 页面访问 HTTP 局域网还可能受到浏览器混合内容策略影响，但那不是此次已复现异常的根因。

### 6.4 输出预算耗尽与空回复：截断识别与有限恢复（D5已确认）

2026-10-18，用户补充：此前在 NyaaChat 调用 `roll_coc` 时也曾出现一次类似现象。该历史请求尚未取得 finish_reason、usage 和完整结束状态，不能仅凭空回复认定其必然与§2.9的2048-token截断同因；网络中断、正常停止但正文为空、工具参数截断也需要区分。

#### 已核实的客户端缺口

`src/lib/api.ts` 的单次调用会返回 `finishReason`，但普通 `fetchOpenAI` 循环在 `toolCalls.length === 0` 时直接返回usage，没有将 `finishReason === 'length'` 当作截断处理。故HTTP200但只有reasoning、正文为空的响应可能被当作正常完成。工具预算耗尽后的最终调用也需要同样的结束状态检查。

主对话请求当前没有发送 `max_tokens`，而现场 `/api/show` 的parameters为空；这两点不能证明上游没有默认限额，也不能确认用户历史请求实际用了多少输出预算。测试中的2048限额由测试脚本设置，不能套到应用请求上。

#### 已确认的处理方案

1. **明确识别结束状态。** `length`、连接中断、`stop`但无正文分别处理；正常 `tool_calls` 且正文为空不是失败。使用现有发送后的错误 / 日志通道显示截断原因，不新增D3已排除的发送前提示机制。记录结束原因、usage、是否有正文、所在工具轮次等结构信息，不记录思考正文。
2. **保护工具执行。** 先检查响应是否完整，再执行工具。遇到 `length` 或未结束的流，不执行其中可能截断的tool_calls；工具参数JSON不完整时不能简单回落空对象后调用。
3. **保留已完成的工具结果。** 工具执行后汇总失败，只重试该次模型生成，继续携带原assistant工具调用及对应tool结果，不重新执行此前工具。`roll_coc`的本地源码会产生随机骰点，并已经返回最终数值、判定与阈值，重跑会改变检定结果。骰子结果必须原样复用，不能让模型为恢复回复再次掷骰。
4. **有条件、有限恢复。** 对“明确length且尚无已展示正文”的模型请求，保留原请求参数和完整工具结果，最多自动重试一次；不提高输出限额、不自动关闭thinking，也不重新运行提示词预渲染或此前工具。若仍截断则明确结束。若已经显示部分正文，应保留并标记截断，不直接把从头重试的文本拼在后面。重试只针对该次未完成的模型生成，不把整段对话流程从头重跑。
5. **不引入预算配额。** 用户自部署Ollama的实际限制由部署侧控制，NyaaChat当前健康检查不能可靠获得有效上下文与输出上限。按D5，本次不新增输出预算配置、不根据模型卡 / 名称 / usage推算配额、不注入 `max_tokens` 等限额参数，也不以8192作为默认值。usage仅用于诊断，不能当作剩余预算。服务端模型参数保持由部署者管理。

有限恢复是一次新的模型生成尝试，不是恢复服务端已经停止的思考状态，也不能保证相同预算下一定产出正文。恢复过程中必须防止已完成工具被再次执行；具体状态记录与重复调度处理在实施设计中明确，不能仅按工具名和参数全局去重，因为正常跑团也可能有多次相同参数的合法掷骰。

保持D2的thinking默认开启，不以自动关闭thinking作为无提示兜底。用户可手动关闭后重试，但同样应复用已经完成的骰子结果。提示模型简洁作答、减少重复说明只能辅助降低消耗，不能硬性保证thinking留出足够正文预算。

**方案定位：避免截断被当作正常空回复，并为未完成的生成提供一次恢复机会；不承诺消除服务端预算耗尽。** 消息结构兼容与thinking参数可归插件；结束状态识别、工具执行安全和恢复循环涉及宿主 `api.ts`，具体通用接口需与插件设计一并评估。本方案已形成D5，尚未修改代码或模型配置。

### 7.2 建议分期

- **P1：插件接入与适配核心验证。** 核对现有插件扩展契约，确认必要的宿主通用接口和静态 assistant 策略，在独立插件中实现边界明确的规范化，覆盖多 system / 混排 / 动态尾 / RosettaStone / 幂等与非目标回归。
- **P2：插件配置、截断恢复与诊断闭环。** 插件UI提供模型策略和默认开启、可由用户关闭的thinking开关，完成参数映射、持久化、启停边界、设置页AF高亮警告文本块、可读模板错误及不含提示词正文的结构诊断。按D5接入结束状态识别及保留工具结果的有限恢复，不引入token预算配置。不新增发送前提示或针对AF的拦截机制。现有 `ApiHttpError` 的显示只取正文前300字符，可针对模板异常提取简短原因，避免嵌套 JSON 截断关键结论。
- **P3：真实服务与角色验收。** 用户本机浏览器、目标模型、代表性复杂角色、多轮与 RosettaStone 四组合；对用户已验证成功的全部已接入 MCP 工具、图片和文档附件识别做兼容改造后的回归，覆盖thinking开关、需要的工具边界及流式组合。根据现场证据决定是否另立上下文与采样优化阶段。

每期应可独立验证和交付；具体 SSOT、实现计划与提交安排在用户确认方案后制定。真实测试使用合成或用户指定角色，不在文档中存放私人对话。若产生临时文件、数据或资源，验收后清理；数据库写入仍须先备份。

## 8. 决策记录与待确认事项

### D2：独立扩展插件与 thinking 开关（已确认，默认值已修订）
