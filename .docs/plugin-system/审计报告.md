## 3. 关键决策（已拍板）

> 以下六项均由用户逐一拍板确认，**采纳方案即"拍板结论"列**。

### D1 插件树位置与构建模型 → **采纳：构建期静态注册**

- **结论**：插件实现在**仓库根 `plugins/<pluginId>/`**；注册表为**手写的 `plugins/registry.ts`**（唯一的注册入口，import 各插件并以数组导出）；框架运行时放在 `src/plugins/`。插件随主应用一起被 Vite 打包，**没有运行时加载器**。
- **理由**：类型安全（插件契约是 TS 接口，编译期即校验）；开发期有 HMR；无运行时加载 ⇒ 无"加载任意 JS"这一攻击面，与"插件只由开发者装入"（诉求 B）天然一致。
- **代价**：新增/移除插件需要重新构建并重建 dev 容器（这本来就是本项目的既有节奏）。
- **被否方案**：`public/plugins/<id>/` 预构建 JS + 运行时动态 `import()` + 注册表 —— 更接近 ST 形态、免重建，但无类型保障、错误面在运行时、且需要一个"允许加载哪些 id"的白名单机制（等于把 ST 的问题重新引进来）。
- **配套（易漏项）**：`eslint.config.js` 的 react-hooks + browser globals 规则目前只覆盖 `files: ["src/**/*.{ts,tsx}"]`（L32）⇒ **P1 必须把 `plugins/**/*.{ts,tsx}` 加入该 files 列表**，否则插件里的 hooks 违规不会被 lint 拦下。

### D2 扩展 UI → **采纳：复刻供应商 modal 形态，复用 `.pv-*` 移动端分栏**

- **结论**：新建 `src/components/ExtensionsModal.tsx`，外壳用 `BaseModal`；PC（≥40rem）左列表右详情，手机（<40rem）两级（列表 ↔ 详情 + `返回列表`），**完全复用 `src/index.css` L223-233 的 `.pv-layout` / `.pv-pane-*` 类**，不新写断点。列表行 = 图标 + 名称 + 版本/状态 + 启用开关；**无新增按钮、无删除按钮**。详情面板 = 插件元信息 + 启用开关 + 插件自己的设置组件（无设置项时显示明确占位文案）。图标缺省回退到 `扩展` 入口图标（`Puzzle`）。
- **理由**：诉求 D 明确要求"使用 `对话模型供应商` 的 UI/UX"；`.pv-*` 已经解决了"移动端二级 + 不受样式加载顺序影响"这个最麻烦的部分，重写只会引入回归。
- **`ChatHeader` 接线**：`扩展` 按钮当前是 `type="button" aria-disabled="true" title="扩展（暂未开放）"` 且**无 handler**（`src/components/ChatHeader.tsx` 253 行）⇒ 本阶段改为 onClick 打开新 modal，并去掉 `aria-disabled` / 改写 title。这是**计划文档要求的 UI 重构的一部分**，不与该按钮"暂不挂功能"的历史约束冲突（那条约束属于上一阶段，本阶段已被诉求 D 取代）。
  **✅ 用户 2026-09-15 复核确认：正式接线。**
- **被否方案**：另起一套 modal 版式；用 `useMediaQuery` 在 JS 里判宽（与既有 CSS 方案重复且会闪）。

### D3 插件配置并入设置体系 → **采纳：并入 `AppState`，且不上调导出存档版本号**

- **结论**：
  - `AppState` 新增 `plugins: Record<string, PluginState>`，`PluginState = { enabled: boolean; config: Record<string, unknown> }`（`src/types.ts`）。
  - `DEFAULT_SETTINGS.plugins = {}`；加载路径（`App.tsx` L649 起逐字段构造）显式读取并归一化 `parsed.plugins`。
  - **localStorage 侧**：`SCHEMA_VERSION` 11 → 12，新增 `migrateV11ToV12()` 回填 `plugins: {}`（沿用现有"Bump SCHEMA_VERSION and add a branch in migrate"约定，`App.tsx` L96/L109）。
  - **导出存档侧**：`EXPORT_VERSION` **保持 9**，`SUPPORTED_IMPORT_VERSIONS` **不变**。`buildExportPayload()` 天然带上 `plugins`（`...settings` 展开）。导入时 `plugins` 缺失 ⇒ 回填 `{}`；存在 ⇒ **只保留注册表中已知的 id**，未知 id 丢弃（与 `RETIRED_TOP_LEVEL_KEYS` 的剥离思路一致：归档里可以有额外数据，但不许把宿主不认识的东西带进活跃状态）。
- **理由**：`settingsBackup.ts` L34-36 明确记录"上调版本号只会**单方面**让老版本拒绝新存档"⇒ 增量字段 + 不升版是兼容性最优解；老版本读到 `plugins` 会原样忽略，新版本读老档会回填。云端路径无需改动（服务端原样存 `ExportPayload`）。
- **被否方案**：B 上调 9→10（语义更显式，但老版本直接拒收新存档）；C 独立存储 + 独立导出键（设置转移出现两条路径、两套回填逻辑）。

#### D3 复核补充（用户 2026-09-15 复核后确认/加强）

- ✅ **确认**：未知插件 id **不保留、丢弃**。
- ✅ **确认并升格为硬规则**：**插件集合的唯一权威是代码（`plugins/registry.ts`），不是用户的本地设置存档。** 开发者在任何新版本里删掉一个插件，用户此后不应再看见它；新版本导出的存档里也不应再残留该插件的配置。落地三条：
  1. 列表只由注册表生成，**从不**遍历 `AppState.plugins` 的键；
  2. 入口归一化（localStorage 加载 / 本地导入 / 云端下载）统一丢弃未知 id；
  3. **出口防御**：`buildExportPayload()` 也对 `plugins` 过一遍归一化 —— 与既有 `RETIRED_TOP_LEVEL_KEYS` 的"Protection, not repair"注释同思路（手改过的 localStorage 仍可能夹带死数据，而 `...settings` 会把它复制进归档）。只守入口不守出口，无法满足"存档里不再有已下线插件"这一要求。
- ✅ **确认**：不迁移 ST 的 `settings.html` / `style.css`，设置面板用 React 组件 + 既有 Tailwind 风格重写，保持 NyaaChat 整体控件风格。
- ⚠️ **两条版本轴必须分清**（详见 SSOT §2.8.1）：`SCHEMA_VERSION`（localStorage 形状，`App.tsx` L109，本阶段 11→12）**不参与**导入/导出校验；`EXPORT_VERSION`（归档 `_version`，`settingsBackup.ts` L36，本阶段**保持 9**）由 `SUPPORTED_IMPORT_VERSIONS` **严格校验**、不在集合内即拒收。用户提到的"11→12 回填 `plugins: {}`"属于第一轴。
- **采纳理由（三向兼容）**：保持 9 时「新版本导出→新版本导入」「新版本导出→老版本导入（忽略 `plugins`，不拒绝）」「老版本导出→新版本导入（回填 `{}`）」三条全部可用；升到 10 会**单方面**让老版本拒收新存档。用户要求"优先确保新版本导出的新存档生效"两条方案都满足，故取更宽的兼容。
- **待验证风险**：云端**下载**后由 `SettingsModal` 应用存档，其字段归一化路径必须与本地导入共用同一函数，否则两条路径会分叉（SSOT §6 的 V5/V6/V16 已列为验证项）。

### D4 首个插件的后端路径 → **采纳：`ext-host` 受控代理**

- **结论**：在 `ext-host` 新增**插件专用**路由（如 `POST /plugins/quote-tts/speech`），上游端点、模型、鉴权**全部由服务端决定**（env `PLUGIN_QUOTE_TTS_UPSTREAM_URL` 等），请求体**只允许**携带 `{ input, voice, response_format }`；`voice` 校验白名单、`input` 长度上限。nginx 侧新增**一条精确匹配** location（`location = /api/ext-host/plugins/quote-tts/speech`），与既有 L187-203 的写法保持一致。
- **理由**：这是唯一能"重建能力而不重建漏洞"的路径 —— 被删掉的 `/openai/custom/generate-voice` 之所以危险，正是因为它从 body 取 `provider_endpoint`（任意 URL 转发）。同时复用既有的边车 + 精确 location 模式，避免新增服务面。
- **被否方案**：B 浏览器直连 Edge-TTS（受 CORS 限制、把上游暴露在浏览器侧、无法做白名单）；C 在主 app nginx 另建代理（多一层服务面，而 ext-host 本就是为这类旁路能力准备的）。

### D5 插件如何在消息里插入控件 → **采纳：React 消息装饰点 API**

- **结论**：框架提供**文本装饰契约**：插件对一段文本声明若干区间 `{start, end}`，并提供一个 React 渲染函数；宿主在消息渲染管线内把文本按区间切开、渲染成插件的 React 组件。**不注入 DOM、不做 HTML 字符串回写。**
  > 🔧 **2026-09-15 更正（用户复核后）**：本项初稿把"宿主实现方式"写死为**自研 rehype 插件 + 整条消息的"渲染后纯文本"空间**（A 方案）。复核时用户改为 **B 方案：复用 `MessageItem` 既有的逐块引号渲染扩展点（`renderTextWithQuotes`），区间是「当前块纯文本」内的偏移**。两个偏移空间**互不通用**；B 方案下 R1/R2 **结构性消失**。生效契约见 SSOT §2.6。下文"实现要点"保留仅为记录初稿思路。
- **理由**：诉求 A 禁止 ST 式兼容；摘除后已无 `.mes_text`，DOM 注入路径不存在。React 原生渲染可被组件测试覆盖，且装饰结果受 React 的转义保护。
- **被否方案**：B iframe/前端卡渲染（隔离好但每个装饰一个 iframe，体验与性能都差）；C 恢复类似 `.mes_text` 的 DOM 逃逸区（实现最快，但与本次结论自相矛盾）。
- **实现要点（⚠️ 已被本节 2026-09-15 的复核取代，仅存历史，勿照此实现）**：初稿方案要求在 `rehypePlugins` 末尾追加装饰插件（`[rehypeRaw, rehypeKatex, [rehypeSanitize, sanitizeSchema], nyaachatPluginDecorators]`）、把区间定义在整条消息的"渲染后纯文本"空间并做两趟遍历。**B 方案完全不需要任何 rehype 接线**：装饰不走 HAST，`rehypePlugins` 保持原样未改动。生效契约见 SSOT §2.6。

### D6 本阶段交付范围与阶段划分 → **采纳：框架 + UI + 设置 + 后端 + Quote-TTS 一个闭环**

- **结论**：V1 定为**一个可验收闭环**，六个 P：

  | P | 内容 | 依赖 |
  |---|---|---|
  | P1 | 插件树、注册表、框架契约与运行时（含 eslint/tsconfig 接线） | — |
  | P2 | `扩展` UI 重构（左列表右详情 / 手机两级）+ `ChatHeader` 接线 | P1 |
  | P3 | 插件配置并入设置导入导出与云端（含 SCHEMA_VERSION 11→12） | P1 |
  | P4 | `ext-host` 受控 TTS 代理 + nginx 精确 location | P1 |
  | P5 | `st-Quote-TTS` 移植为原生插件 `quote-tts` | P2, P3, P4 |
  | P6 | 文档：SSOT 收尾、框架规范、ST 移植规范、阶段交接、memory | P5 |

- **理由**：用户明确以 `st-Quote-TTS` 为第一移植任务；且 §2.3 已证明框架 V1 的能力面无法小于首个插件的需求，把插件后置只会让框架在"没被真实需求验证过"的状态下冻结。
- **被否方案**：先做框架 + 空壳示例插件，Quote-TTS 放 V2。

## 5. 不做清单（防止范围漂移）

- 不做插件安装/卸载/上传/市场等任何用户侧治理。
- 不做 ST `manifest.json` 兼容解析、不做 `extension_settings` 兼容读写。
- 不为插件新增独立后端服务或独立数据库表。
- 不在本阶段引入插件间依赖、插件权限声明、插件沙箱（V1 插件与宿主同信任级）。
- 不修改 `dev-server` 已有的 ST 遗留路由登记（属上一阶段的"已知非失败项"）之外的任何 dev 基建。
