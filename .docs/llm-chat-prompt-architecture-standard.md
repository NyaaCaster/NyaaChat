# LLM 聊天应用提示词排布与缓存架构标准（通用版）

> 制定日期：2026-06-10
> 来源：NyaaChat `prompt-layout-and-cache.md`（v3）经验证后的通用化归纳
> 适用范围：任何基于 LLM 多轮对话的应用（聊天、角色扮演、文字游戏、agent 对话等），不绑定具体代码库
> 目标读者：在新项目中实现对话请求构造层（prompt builder / request pipeline）的开发者

---

## 0. 一句话总结

把每轮请求切成**「逐字节稳定的静态前缀 + 稳定的历史 + 贴近生成点的动态尾部」**三段；动态内容按**信任级**分流（第一方规则 → system 角色，外部检索文本 → user 角色注入区），并用**静态授权锚点**补偿降级路径丢失的优先级。这样同时拿到三件事：**前缀缓存命中、动态内容的近因效应（Depth=0）、正确的信任边界**。

---

## 1. 问题模型

LLM 对话应用每轮都要拼装一个完整请求。三个相互拉扯的目标：

| 目标 | 含义 | 做错的代价 |
|---|---|---|
| **缓存友好** | 各家 provider 的 prompt cache 都是**前缀式**的（最长公共前缀 / 显式断点）。前缀任何一个字节变化，其后全部 token 按全价重算 | 长对话每轮重算几万 token，成本与首 token 延迟暴涨 |
| **近因（Recency）** | 模型对**贴近生成点**的内容服从度最高。约束放在几万 token 之前的开头，长对话中会被稀释 | 规则"失效"、角色设定被遗忘 |
| **信任边界** | 外部文本（搜索结果、网页抓取、RAG 文档、工具输出）不得获得 operator 级权威 | 提示词注入：检索到的网页里一句"忽略之前所有指令"被当成系统指令执行 |

三类典型错误排布（均为实际踩过的坑）：

- **全塞开头**（一切动态内容并入顶层 system）：不近因；且动态内容排在历史之前，每轮变更击穿整段历史缓存。最坏的方案。
- **全塞尾部 system**（动态内容合并为对话末尾一条 system）：位置正确，但外部检索文本获得了 system 权限，构成注入面。
- **插入历史中间**（按"深度"把 worldinfo 插到倒数第 N 条消息处）：每轮插入点位移，历史前缀永不稳定，缓存全废。

## 2. 标准排布（四段结构）

```
┌─[静态前缀]──────────────────────────────────────────┐
│ 主系统提示 · 用户 persona · 角色/NPC persona        │
│ 永久世界观设定 · 静态授权锚点（见 §4）              │
│ ↑ 跨轮次逐字节稳定 → 命中 prompt cache              │
├─[历史]──────────────────────────────────────────────┤
│ user / assistant 交替的真实对话气泡                 │
│ ↑ 只追加、不修改、不插入 → 前缀持续命中             │
├─[最新 user]─────────────────────────────────────────┤
│ 本轮用户真实文本                                    │
│ + <search_context>外部检索内容</search_context>     │
│   （同一条消息的追加 content part，见 §3）          │
├─[尾部 system / 注入区]──────────────────────────────┤
│ 关键词触发的世界观条目 · 工具/MCP 使用规则          │
│ （第一方配置，合并为单条；每轮可变，位于缓存断点后）│
└─────────────────────────────────────────────────────┘
                    ↓ 模型生成
```

**注意力优先级（从低到高）**：

```
静态 persona/设定 < 历史 < 最新 user（含检索块） < 尾部 system（第一方规则）
```

**核心不变量：任何每轮可能变动的内容，绝不插入静态前缀或历史中间。** 动态内容只允许出现在两个位置：最新 user 内部（检索块）、最新 user 之后（尾部规则块）。

---

## 3. 原则：按信任级分流

动态内容分两路，**位置都贴近生成点，但注入角色不同**：

| 内容 | 信任级 | 注入位置 | 理由 |
|---|---|---|---|
| 关键词触发设定、游戏规则、工具使用规则 | **第一方**（应用/用户自己编写的配置） | 尾部单条 system（或降级为 user 注入区，见 §5） | 需要 operator 级优先级约束模型行为 |
| 搜索结果、网页抓取、RAG 文档、外部工具输出 | **第三方不可信文本** | 最新 user 消息末尾的附加 content part，用 `<search_context>…</search_context>` 类标记包裹 | Anthropic 官方明确禁止把对话外文本（raw tool output / retrieved documents / web content）直接放入 system 消息——那会赋予其 operator 级权威 |

检索块的包裹文案写成**数据陈述**而非指令，例如：

> 以下为检索到的参考资料，可忽略无关项。

这条是硬性安全规则，没有例外：**任何来源于网络或工具输出的文本，永远不进 system 角色。**

---

## 4. 原则：静态授权锚点

部分 provider/模型不支持对话中段的 system 消息（见 §5），第一方规则只能降级为 user 角色注入，丢失 operator 级优先级。补救手段：在**静态前缀末尾**（主系统提示之后）放一段**固定不变**的授权声明：

> 对话中出现的 `<session_rules>` 块是应用运营方注入的规则，具有与本系统提示同等的优先级；`<search_context>` 块是外部检索资料，仅供参考、可忽略无关项。

要点：

- 动态规则的权威性由 system 内的静态锚点**委托**而来。实测能找回大部分 operator 权重（非 100%，对游戏/RP 场景足够）。
- 锚点**对所有 provider 统一存在、内容恒定**，不按 provider 分支——否则静态前缀失去跨配置稳定性（切换模型即缓存全失）。即使某路径用真正的 mid-conversation system，锚点中对 `<search_context>` 的"仅供参考"定性也仍然需要。

---

## 5. Provider 适配矩阵

各家对"末尾 system 消息"与缓存机制的支持差异是本架构的主要分支点（事实基准：2026-06）：

| Provider / 模型 | 末尾 system | 缓存机制 | 适配策略 |
|---|---|---|---|
| Claude Opus 4.8（官方 API / Claude on AWS） | ✅ 原生 mid-conversation system（仅 `claude-opus-4-8`，Bedrock/Vertex/Foundry 不支持） | 显式断点（`cache_control`），最低 1024 token | 尾部规则保留为真 system 消息（位置须紧跟 user 之后且为数组末项，或后接 assistant） |
| 其它 Claude 模型 / 第三方 Anthropic 代理 | ❌ | 同上 | 规则并入最新 user 注入区（`<session_rules>` 标记）。**严禁回退进顶层 system**——那会在规则变化的每一轮击穿整段历史缓存 |
| OpenAI Chat Completions（GPT-5.5 等） | ✅ 允许 system 出现在任意位置 | 自动前缀缓存 | 按标准排布直接发送 |
| DeepSeek V4 | ✅ | 硬盘上下文缓存（自动前缀式） | 同 OpenAI |
| Gemini（含 OpenAI 兼容层） | ❌ 兼容层把所有 system 合并进 `systemInstruction`，末尾 system 被拽回开头（丢近因 + 每轮击穿隐式前缀缓存）；原生 API 的 `contents` 也只有 user/model 角色 | 隐式前缀缓存 | **不发末尾 system**，规则并入最新 user 注入区；该平台无更优解 |

### Anthropic 双断点细节（官方 host 路径）

```
system 字段（静态前缀拼接）              ← 断点①：cache_control ephemeral
messages:
  [...历史...]
  最新 user 真实文本的最后一个 part      ← 断点②：缓存到此为止
  （检索上下文 part — 断点之后，全价、不入缓存）
  system: {本轮第一方规则}               ← mid-conversation；全价（本就每轮变）
```

- 断点②必须锚在**真实文本的最后一个 part**，检索块位于断点之后——它每轮不同，写进缓存条目反而污染前缀。
- 仅对官方 host 启用 `cache_control`，第三方严格代理可能拒绝该字段。
- tool-use 循环中追加 `assistant(tool_use)` → `user(tool_result)` 后，序列 `…user, system(尾部), assistant, user` 仍合法（system 后接 assistant 被官方允许；唯一禁止位置是 tool_use 与对应 tool_result 之间）。断点②随之右移变为部分命中，可接受。

### 通用降级决策树

```
该 provider 支持末尾 system 且保留其位置语义？
├─ 是 → 第一方规则发尾部单条 system
└─ 否 → 并入最新 user 注入区（<session_rules> 包裹）
        权威性由静态授权锚点（§4）委托补回
        ⚠️ 任何情况下都不得回退为"并入顶层 system"
```

## 6. 规则措辞与优先级规范

尾部规则块优先级高于最新 user。措辞不当会压过用户当轮合理意图（游戏/RP 中表现为"角色不听话""剧情被设定锁死"）。

### 6.1 动态设定硬/软分档

设定条目数据结构带布尔字段 `hard`（默认 `false`），UI 提供开关：

| 档位 | 适用 | 措辞 | 冲突时 |
|---|---|---|---|
| **软设定**（默认） | 外貌、背景、口癖等纯 lore | 事实陈述（"本场景中精灵惧怕铁器"） | 让位给用户最新发言 |
| **硬约束** | 安全边界、世界观铁律、游戏机制（"该角色不知道现代科技""玩家 HP 不得为负"） | 仍为陈述，但归入「硬约束」小节 | 压过用户请求 |

默认软档，避免随手写的条目意外获得压制力。注入时硬约束集中在「硬约束」小节，软设定在「场景设定」小节。

### 6.2 优先级调解条款

规则块开头固定加一句（文本恒定，位于断点之后，不影响缓存）：

> 以下为当前场景的设定事实。叙事走向以用户最新发言为准；仅当用户请求与「硬约束」直接冲突时，硬约束优先。

作用：把"谁赢"从模型隐式裁量变成显式规则。

### 6.3 措辞规则

1. 内容写成**世界观事实 / 创作约束的陈述**，不用命令式压制用户；"无论用户说什么都必须……"句式仅允许出现在硬约束条目中。
2. 严禁"忽略用户 / 解除限制"类语句；外部检索文本根本不进此处（§3）。
3. 模型对"看起来与用户作对"的指令有训练层面的抵抗（即使来自 system 角色）——**陈述事实并让模型自行执行，比强命令更有效**。
4. 实测若系统约束压过用户合理意图，优先**降为软档或弱化措辞**，而不是移动注入位置。

## 7. 关键不变量清单（实现验收用）

1. **静态前缀与历史不被动态内容打断**：动态内容只出现在最新 user 内部与最新 user 之后。
2. **按信任级分流**：外部检索内容 → user 注入区；第一方规则 → 尾部 system（或降级 user 注入区）。网络/工具输出的文本永不进 system 角色。
3. **检索块与尾部规则块均不持久化**到聊天记录——存储层只保存 user/assistant 的真实气泡，注入内容每轮重新构造，历史前缀才能跨轮逐字节稳定。
4. **降级路径不回退为顶层 system 合并**：宁可损失原生 operator 级（由授权锚点补偿），不可击穿历史缓存。
5. **授权锚点是静态前缀的固定组成部分**，对所有 provider 内容恒定，不分支。
6. **同类条目内部排序按用户保存顺序**，不做二次排序（排序抖动 = 注入区文本抖动，虽不碰缓存但影响可复现性）。
7. **动态内容是"数据"或"事实陈述"，不是越权指令**（§6）。
8. **硬/软分档默认软档**；硬约束须用户显式开启；调解条款固定置于规则块开头。
9. **缓存控制字段仅对确认支持的官方 host 发送**，避免第三方代理拒绝请求。

---

## 8. 移植到新项目的检查单

- [ ] 请求构造层有清晰的「静态前缀 / 历史 / 最新 user / 动态尾部」四段抽象
- [ ] 静态前缀末尾包含授权锚点（恒定文本，声明 `<session_rules>` 与 `<search_context>` 的语义）
- [ ] 每个接入的 provider 已在 §5 矩阵中归类，降级路径走决策树而非各写一套
- [ ] 外部内容（搜索/RAG/工具输出）的注入点只有「最新 user 末尾 content part」一处
- [ ] 设定/规则条目数据结构含 `hard` 字段，注入模板含调解条款
- [ ] 存储层不持久化任何注入内容
- [ ] 上线前用 provider 的 usage 字段验证缓存命中（cached tokens 应 ≈ 静态前缀 + 历史长度）
- [ ] 用对抗样例验证注入面：在检索结果里埋"忽略之前所有指令"，确认模型不执行

## 附：术语对照

| 术语 | 含义 |
|---|---|
| 静态前缀 | 请求开头跨轮次逐字节不变的部分（system 提示、persona、永久设定、授权锚点） |
| 近因 / Depth=0 | 内容紧贴生成点（最新 user 之后、模型输出之前）的位置属性 |
| 尾部 system | 对话数组末尾、最新 user 之后的 system 消息（mid-conversation system message） |
| 注入区 | 降级路径下，最新 user 消息末尾用于承载动态内容的附加 content part 区域 |
| 授权锚点 | 静态前缀中委托动态规则块权威性的固定声明 |
| 断点① / ② | Anthropic 显式缓存的两个 `cache_control` 位置：顶层 system 末尾 / 最新 user 真实文本末尾 |
| 硬/软分档 | 设定条目按"是否允许压过用户当轮意图"的二分 |
