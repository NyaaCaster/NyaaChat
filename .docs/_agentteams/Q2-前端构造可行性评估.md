# Q2：SPreset / SToolBook / SillyTavern 的技术内核能否只在 NyaaChat 前端构造

> **任务**：`nyaachat-flagalac-recon` / t2（考察员：runtime-scout）
> **考察方式**：只读源码与部署配置 + 对 macmini 上运行中的 NyaaChat 容器做只读 HTTP 实测。
> **本次考察未修改 NyaaChat 任何业务源码**（未新增/修改/删除任何 `src/`、`public/`、部署文件；仅在 `.docs/_agentteams/` 下写入本报告）。
> **证据标注**：✅ 源码/实测直接读到（`文件:行号`）｜🔶 推断（说明推断依据）｜❓ 未能证实（说明缺什么证据）。

## 0. 结论速览

### 0.1 一句话回答

**"服务端除媒体转发外不参与"这一约定，在 NyaaChat 现状中是成立的**（主对话请求由浏览器直接 `fetch` 到用户配置的 provider，NyaaChat 自有服务不含任何对话补全路由，已实测验证）。因此小猫之神方案所需的四类内核（出站 prompt 改写 / 工具循环 / 输出侧处理 / 位置注入）**都不需要服务端参与**。

但"不需要服务端"≠"零改造即可用扩展实现"。真正卡住复刻的是三点，且都不是服务端问题：

1. **钩子缺位**：NyaaChat 的事件总线里根本不存在 ST 的 `GENERATE_AFTER_DATA` / `CHAT_COMPLETION_PROMPT_READY` / `CHAT_COMPLETION_SETTINGS_READY`，`GENERATION_STARTED/ENDED` 只声明未发射；ST 的请求装配入口（`sendOpenAIRequest`）在 NyaaChat 的兼容层里被**明确封死**（warnOnce）。→ SPreset 那种"挂事件、就地改 `data.prompt`"的复刻路线不存在。
2. **扩展是构建期资产**：扩展要走 `public/extensions/registry.json` + `npm run build`（`extensions:registry` 脚本）才生效，**没有运行时装/卸**。→ "用户在浏览器里填一段 JS/导入一个预设就能生效"的形态在当前架构下不成立。
3. **与既有不变量冲突**：NyaaChat 有一条硬不变量——**动态尾部只有一条 system**，`foldTailSystemIntoLatestUser` 在"相邻两个 system"时拒绝折叠。absolute depth=0 注入、assistant 预填、第二条尾部 system 都会撞上它。

### 0.2 三分类清单（按"要动多少 NyaaChat 前端"划分；**无一项需要服务端参与**）

| 类别 | 机制 | 现状 / 改造位置 | 成本 |
|---|---|---|---|
| **可直接前端实现** | 7. 正则脚本层（对 AI 隐藏 CoT / 控制标签清理 / 思维链折叠） | **已具备**：ST 双管线正则引擎忠实移植 | 0（仅需撰写脚本） |
| **可直接前端实现** | 4. 输出侧处理（`\uXXXX` 流式解码 / `hold` 缓冲） | `onChunk` 已是逐块回调，加一层解码器即可 | 小 |
| **可直接前端实现** | 3. 工具注册与工具循环 | 循环机制已具备（`maxRounds=5`）；只需补一个**不进服务端的本地工具源**（见 §3.10(i)） | 小 |
| **需改造（前端核心）** | 1. 出站 prompt 数组改写（合并/前缀/不压缩标记/重新拆分） | 数据全在前端，但缺"装配后"钩子；需在 `fetchChatCompletion` 前加 hook 点 | 小 |
| **需改造（前端核心）** | 8a. 停止串（`stop` / `stop_sequences`） | 请求体里完全没有该字段 | 小 |
| **需改造（前端核心）** | 6. 位置类机制（absolute depth=0 / 置底最新回合） | 已有 `setExtensionPrompt` 注册位但**从未被消费**；接线即可，但内容必须并入同一条尾部 system | 小–中 |
| **需改造（前端核心）** | 4b. 工具调用参数镜像进正文（3.7f 的 `consumeToolCalls`） | 现有实现把 `tool_calls` 参数**静默累加、不进 `onChunk`**；落层取舍见 §3.10(ii) | 中 |
| **需改造（前端核心）** | 8b. `assistant_prefill` 类续写锚点 | 无 prefill 概念；追加尾部 assistant 会让尾部 system 折叠守卫失配 | 中（且须一并改不变量） |
| **需改造（前端核心）** | 2b. 原生 reasoning 采集（`reasoning_content` / `thinking`） | `Message` 无 reasoning 字段，流解析不认 reasoning delta，`regex_placement.REASONING=6` 无对象可作用 | 小–中 |
| **需改造（前端核心）** | 5. 无缝循环（多次 continue 合并成一条 assistant） | 无 `continue`、`GENERATION_ENDED` 不发射；只能靠 `TavernHelper.generate` + `createChatMessages` 做**旁路**循环 | 中–大 |
| **不建议 / 不可行** | 2a. 用户可执行 JS 后处理脚本（`eval`/`new Function`）作为常态功能 | 当前实测**主文档无 CSP，eval 不被拦**；但这与 `nginx.conf` 声明的 `script-src 'self'` 意图直接冲突，一旦 CSP 生效即刻失效；且 NyaaChat 自身零 eval | — |
| **不建议 / 不可行** | SPreset 那套"远程注入一份闭源 inject.js"的装载方式 | 主文档 `script-src 'self'`（意图）挡远程脚本；扩展装载是构建期资产 | — |
| **不建议 / 不可行** | 独立新增"第二条尾部 system" | 破坏 `foldTailSystemIntoLatestUser` 唯一性不变量 | — |

### 0.3 "浏览器前端独立完成"的边界

- **可以放弃**：SPreset 的"整份预设文件 = 可分享的可执行配置"这一形态；远程注入第三方 `inject.js`；`ToolBindings[].code` / `squashed_post_script` / `OutputPreprocessing.script` 这类**任意 JS 输入**。
- **可用等价物替代**：用户 JS 后处理脚本 → **ST 同源正则脚本**（已有）+ 受限 JSON 规则/DSL；absolute depth=0 注入 → **并入同一条尾部 system 的块**；服务端 MCP 工具 → **前端本地 executor 的"伪工具"**；`continue` 续写 → **前端侧再次调用 + 写回消息**（旁路，不进主轮）。
- **必须新增的最小核心改造**：一个"prompt 装配完成后、发出之前"的**前端钩子点**，外加请求体可注入 `stop` 的能力。这是把 8 项机制里 6 项盘活的**唯一单点依赖**。

## 1. 实证结论：对话请求到底怎么发出去、服务端是否参与

### 1.1 主对话请求：浏览器直接 `fetch` 到 provider（✅ 源码）

| 事实 | 证据 |
|---|---|
| 唯一的对话补全出口是 `fetchChatCompletion`，按 `apiFormat` 分派到 OpenAI / Anthropic 两条 | `src/lib/api.ts:299-311` |
| OpenAI 路径直接 `fetch(url, ...)`，`url = routeApiProxyUrl(normalizeBaseUrl(baseUrl), "chat/completions")` | `src/lib/api.ts:378-380`、`404-410` |
| Anthropic 路径同样直接 `fetch(url, ...)` | `src/lib/api.ts:820-822`、`901-907` |
| `routeApiProxyUrl` **只对 `opencode.ai`** 改写为同源 `/api/opencode-go/`，其余 baseUrl 原样（即跨域直连） | `src/lib/api.ts:248-262` |
| 请求体在前端内存中构造完毕后才发出：OpenAI = `{model, messages, stream, stream_options, tools}` | `src/lib/api.ts:382-392` |
| Anthropic = `{model, max_tokens:4096, messages, stream, system, tools}` | `src/lib/api.ts:857-881` |
| 唯一后端参与是"用户可自选"的，且只覆盖 opencode.ai 一家 | `nginx.conf:381-395` |

### 1.2 NyaaChat 自有服务暴露的路由：没有任何一条转发对话补全（✅ nginx.conf）

| 路由 | 用途 | 位置 |
|---|---|---|
| `/api/image-proxy/<scheme>/<host>/<path>` | 生成图媒体转发 + 缓存（带 host 白名单） | `nginx.conf:118-149` |
| `/api/mcp`、`/api/mcp/health` | MCP JSON-RPC 代理（**服务端注入 Bearer**） | `nginx.conf:160-183` |
| `/api/ext-host/t2i-agent/chat`、`/api/ext-host/*` | ext-host 边车（T2I agent / 扩展运行时 / TTS） | `nginx.conf:187-211`、`nginx.conf:216-225` |
| `/api/shared/*`、`/api/knowledge/expand-kb`、`/api/knowledge/*` | 共享角色库 / 账号 / 知识库（REST） | `nginx.conf:255-311` |
| `/api/comfyui/fixed/*`、`/api/comfyui/custom/...` | ComfyUI 反代（固定服务器 URL 与 token 只存在于服务端 envsubst） | `nginx.conf:325-372` |
| `/api/opencode-go/` | 仅 opencode.ai 一家的补全反代 | `nginx.conf:381-395` |
| `location / { try_files ... }` | SPA 静态资源 | `nginx.conf:397-399` |

后端路由面同样不含对话补全：

- shared-server：`/health`、`/account`、`/characters`、`/covers`、`/internal`（`shared-server/src/server.js:21-40`）
- knowledge-server：`/health`、`/auth-check`、`/embedding-config`、`/kb`、`/`、`/search`、`/memory`、`/internal`（`nyaachat-knowledge/src/server.js:23-48`）
- ext-host：`/health`、`/status`、`/runtime-metadata`、`/extension-field`、`/openai/custom/generate-voice`、`/t2i-agent/chat`（`ext-host/src/server.js:334-358`）
  - 其中 `/t2i-agent/chat` 确实是一次 LLM 调用，但那是"画图提示词生成"的**旁路功能**（`src/lib/t2iAgentApi.ts:14`），与用户对话流无关。
- 部署面：app（nginx 静态）+ ext-host 两个容器（`docker-compose.yml:1-50`、`docker-compose.publish.yml` 同构无额外服务）。

> **结论（✅ 事实）**：用户与 LLM 之间的对话补全流量，**只在浏览器 ↔ provider 之间**。服务端参与的是"媒体转发（image-proxy / comfyui）、工具协议代理（MCP）、账号与知识库 REST"。用户的设计约定与现状一致。

### 1.3 但这不等于"扩展可以在浏览器里做任何事"——两点关键约束

**(a) ST 的请求装配入口在 NyaaChat 兼容层里被明确封死（✅）**

- `public/scripts/openai.js:96-100`：`sendOpenAIRequest()` / `getStreamingReply()` 直接 `warnOnce` 并返回空串，注释写明 "request construction is not delegated to extensions, preserving NyaaChat's prompt layout/trust boundary"（`public/scripts/openai.js:1-5`）。
- `public/scripts/PromptManager.js:1-5`：只提供 `Prompt` / `PromptCollection` **数据容器**，"does not splice prompts into NyaaChat's main request pipeline"。
- 事件总线缺钩子：`event_types`（`src/compat/events.ts:18-41`）里**没有** `GENERATE_AFTER_DATA`、`CHAT_COMPLETION_PROMPT_READY`、`CHAT_COMPLETION_SETTINGS_READY`；有 `GENERATION_STARTED` / `GENERATION_ENDED` 两个键（`:31-32`），但**全仓无任何发射点**（对 `src/**` grep `GENERATION_STARTED|GENERATION_ENDED` 仅命中声明处）。
- `makeLast` 的实现就是 `on`（`src/compat/events.ts:65-67`）——NyaaChat 里它**不改变执行顺序**，无法像 ST 那样抢"最后执行位"。所以 SToolBook↔SPreset 那种"谁最后注册谁说了算"的机制在 NyaaChat 没有对应语义。

**(b) CSP：实测"主文档没有 CSP"，但这是 nginx 配置继承缺陷，与声明意图相反（✅ 实机实测）**

`nginx.conf:41` 声明的策略是严格的：

```
default-src 'self'; script-src 'self'; connect-src 'self' https: http://localhost:* http://127.0.0.1:*; ...
```

该策略**不含** `'unsafe-eval'`、`'unsafe-inline'`，也不含任何远程主机 → 若生效，将同时禁止 `eval`/`new Function`、内联脚本、blob: iframe、以及 CDN 远程脚本。

对 macmini 上运行中的 NyaaChat（`nyaachat-app-1`，宿主 127.0.0.1:3095）实测：

```
$ curl -s -D - -o /dev/null http://127.0.0.1:3095/          → 无 Content-Security-Policy
$ curl -s -D - -o /dev/null http://127.0.0.1:3095/index.html → 无 Content-Security-Policy
$ curl -s -D - -o /dev/null http://127.0.0.1:3095/extensions/JS-Slash-Runner/src/iframe/third_party_script.html
  → 有 Content-Security-Policy: default-src 'self'; script-src 'self'; ...
```

**原因（✅ 可从配置与实测一致地推出，🔶 归属为 nginx `add_header` 继承规则）**：`location = /index.html` 自己声明了 `add_header`（`nginx.conf:75-79`），而 `location /` 的 `try_files` 内部重定向到 `/index.html`；nginx 的 `add_header` 只在**当前层级没有** `add_header` 时才继承上层，于是 server 级 CSP 在主文档响应上被丢弃。其余走 `location /` 的同源静态文件（如上面的 JSR html）则正常带 CSP。

**这条实测对本次考察是决定性的**：

- "用户 JS 后处理脚本（`eval`）"在**当前部署下不会被浏览器拦**（主文档无 CSP）。
- 但它依赖的是一个"配置没按意图生效"的状态：NyaaChat 自己**从未使用** `eval` / `new Function`（对 `src/**` grep 零命中），而兼容层里承载"用户 HTML/JS"的路径恰恰是内联脚本 iframe（见 §3.2）。→ 任何"把 nginx 的 CSP 修好"的顺手动，都会连带打断这条路。

## 3. 逐机制可行性表（8 项）

每一项给出：ST/SPreset 实现要点 → NyaaChat 对应能力（有/无/部分）→ 判定 → 改造点与代价。

### 3.1 机制 1：出站 prompt 数组改写

| 项 | 内容 |
|---|---|
| ST/SPreset 要点 | `GENERATE_AFTER_DATA` 上用 `makeLast` 挂监听器（**最后**执行），就地改写 `data.prompt`：全量合并成一条 assistant（`ChatSquash.role`）、按角色插前缀/后缀、`<\|sep\|>` 标记的消息不参与合并（并删标记）、`conditional_tag` 命中即删除、`re_split` 把合并结果再拆回多条；关闭合并时改为跑"消息数组模式"后处理脚本（`SPreset-机制分析.md` §4.1） |
| NyaaChat 对应能力 | **部分**。装配结果就是**纯前端内存里的 `ApiMessage[]`**（`src/lib/chatPipeline.ts:525-530` 的返回值直接喂给 `src/lib/api.ts:299` 的 `fetchChatCompletion`），因此"改写数组"这件事本身没有任何服务端障碍。但**没有可以被扩展挂上的"装配后"事件**（§1.3(a)），且 `PromptManager` 是空容器、`sendOpenAIRequest` 被封。 |
| 判定 | **需改造（成本：小）** |
| 改造点 | 在 `fetchChatCompletion` 调用前（`src/components/ChatInterface.tsx:791-836` 之间）或 `src/lib/api.ts:299-311` 内部加一个**前端管道钩子**：`type PromptRewriter = (messages: ApiMessage[], ctx) => ApiMessage[]`。这同时也是 §3.3/§3.6/§3.8 的共同落点。 |
| 代价/风险 | 改写发生在 `foldTailSystemIntoLatestUser` **之前**最安全（否则被折叠语义与改写互相干扰）。若走"扩展 wrap `window.fetch`"的旁路（技术上可行：`src/lib/api.ts:404`/`901` 用的是全局 `fetch`），会绕开 §1.3(a) 的设计意图，并且拿不到 NyaaChat 的 volatile 标记语义（`VOLATILE_PART_FLAG`，`src/lib/api.ts:34`、`36-46`），不推荐作为正式方案。 |

### 3.2 机制 2：用户 JS 后处理脚本（`eval` / `new Function`）

| 项 | 内容 |
|---|---|
| ST/SPreset 要点 | `runPostScript` 直接 `eval(settings.squashed_post_script)`（`SPreset-机制分析.md` §4.1）；SToolBook 用 `new Function('api', code)` 把世界书条目里的 JS 变成工具（`SToolBook-机制分析.md` §1）；SPreset 用 `script` 闭包做流式解码（同上 §4.4） |
| NyaaChat 对应能力 | **无（不提供用户 JS 执行位）**，但同源"用户代码执行"先例存在：`src/compat/render/srcdoc.ts` 构造**同源、非 sandbox、内联脚本**的 iframe，并把 `window.parent.SillyTavern` / `TavernHelper` 桥进去（`srcdoc.ts:14-20`、`25-45`、`91-110`）；JS-Slash-Runner 的脚本 iframe 同样是内联 `<script type="module">` + 远程 CDN（`public/extensions/JS-Slash-Runner/src/panel/script/iframe.ts:5-22`）。 |
| CSP 实测 | 主文档无 CSP → 上述内联脚本当前可运行；**但同源 HTML 子文档会带上 `script-src 'self'`**（实测见 §1.3(b)），其中的 CDN 远程脚本与内联脚本会被拦。JSR 的 iframe 用 `blob:`/`srcdoc` 形态（`iframe.ts:9` 的 `<base>` 分支、`use_blob_url` 设置项 `src/type/settings.ts:66`）——🔶 推断：若主文档将来带上 CSP，`frame-src`/`default-src 'self'` 不含 `blob:`，整个脚本 iframe 会被阻断。 |
| 判定 | **不建议作为常态功能（安全边界问题）**；若要保留，则判定为 **需改造（成本：中，且必须同时定安全策略）** |
| 替代方案（推荐） | ①**正则脚本**（已具备，见 §3.7）承载文本级改写；②受限 **JSON 规则 / DSL**（声明式，可审计、可随设置导出）；③若确需图灵完备，则只在**构建期 bundle 的扩展**里写代码（= `src/compat/generate.ts` 那条路），而不是让用户在运行时输入 JS。 |
| 代价/风险 | 引入 `eval` 等于把"设置备份文件"变成可执行载荷：`settingsBackup.ts` 的 `EXPORT_VERSION = 7`（`src/lib/settingsBackup.ts:18-19`）说明设置/备份是**用户之间可分享**的（导出/导入校验 + 回填），一旦模板字段可执行，导入他人备份即任意代码执行。这与 NyaaChat 现状（全仓零 `eval`）是明确的架构级回退。 |

### 3.4 机制 4：输出侧处理（SPreset 包装 `window.fetch`）

| 项 | 内容 |

| ST/SPreset 要点 | 包装 `Response.prototype.json`（非流式）与 ST 的流式生成器/出站 `fetch`（流式）；脚本签名 `({buffer, chunk, hold, output, raw, final, stream, ...})`，返回字符串或 `{output, hold, state}`；`hold` 把跨块的 `\uXXXX` 转义接住；脚本报错则降级输出 `raw`（`SPreset-机制分析.md` §4.4） |

### 3.5 机制 5：无缝循环（多次 continue 自动续写并合并）

| 项 | 内容 |
|---|---|
| ST/SToolBook 要点 | `GENERATION_ENDED` → `onSeamlessGenerationEnded()`：有工具调用且未超 `SEAMLESS_LIMIT=10` 时**临时打开 `continue_prefill`**，等流清空后 `context.generate('continue', {automatic_trigger:true})`；整轮只落 **一条** assistant 消息（`SToolBook-机制分析.md` §3.1） |
| NyaaChat 对应能力 | **无**。①没有 `continue` 生成类型（`fetchChatCompletion` 只有"整轮"语义）；②`GENERATION_ENDED` **从不发射**（§1.3(a)），没有"生成结束"回调；③唯一的续写动作是 `handleRegenerate`（`src/components/ChatInterface.tsx:1379-1390`），它是"删掉旧回复重发"，不是续写。 |
| 等价物 | 扩展可用 `TavernHelper.generate` / `generateRaw` 发起**旁路**请求（`src/compat/generate.ts:101-126`，任意卡片自撰消息序列）并配合 `TavernHelper.createChatMessages` / `setChatMessage` 写回（`src/compat/tavernHelper.ts:106-150`）。但 `generate.ts:9-23` 的设计注释明确：这些是 **side request**，**不回写进主会话**、不参与主轮装配。 |
| 判定 | **需改造（中–大）** |
| 改造点 | 需要：`GENERATION_ENDED` 类事件发射点（`src/components/ChatInterface.tsx:822-860` 生成结束处）+ 一个"续写/继续"的生成入口（复用 `sendChat` 的装配但以"当前 assistant 消息为前缀"）+ 合并写回策略。 |
| 代价/风险 | 大。这是 Q2 里唯一需要动**主对话轮控制流**的机制；且与 NyaaChat 的"每次生成 = 一条 assistant 气泡"UI 模型、以及 `foldTailSystemIntoLatestUser` 的折叠语义相互纠缠。建议一期不做。 |

### 3.6 机制 6：位置类机制（absolute depth=0 注入 / 置底最新回合）

| 项 | 内容 |
|---|---|
| ST 要点 | `injection_position === ABSOLUTE(1)` + `injection_depth` 的条目被跳过主流程，改为按深度插进**聊天历史数组**；`depth=0` = "最新一条消息之后"（`小猫之神预设-...报告.md` §2.1）；4.0test 的 `a5e2b2b4`（`</小猫之神世界书处理>`，absolute d0）是该武器样板（同报告 §4.10）。SToolBook 的"置底最新回合"则是把整段 tool loop 搬到 prompt 最末尾（`SToolBook-机制分析.md` §3.3） |
| NyaaChat 对应能力 | **无绝对注入，但注册位已存在且未接线**：`src/compat/stContext.ts:57-81` 的 `setExtensionPrompt(key, value, position, depth, scan, role)` 只写内存 registry，`getExtensionPrompts()` **在全仓没有任何消费点**（对 `src/**` grep 仅命中定义处）。装配位置由 `buildRequestMessages` 固定：`[system 区] → [历史] → [单条尾部 system]`（`src/lib/chatPipeline.ts:439-464`、`525-530`）。 |
| 硬约束（关键） | NyaaChat 有一条**明写的不变量**：尾部只有**一条** system。`chatPipeline.ts:501-510` 注释："One trailing system message is an invariant api.ts depends on (foldTailSystemIntoLatestUser folds exactly one, and refuses when two systems are adjacent)"；守卫实现在 `src/lib/api.ts:58-62`（`if (last.role !== 'system' || prev.role === 'system') return messages;`）。 |
| 判定 | "absolute depth=0 作为一个**独立消息**" → **不可行**（破坏不变量）；"把内容**并入同一条尾部 system**的某个块" → **需改造（小–中）** |
| 改造点 | ①把 `getExtensionPrompts()` 接进 `buildRequestMessages`，按 position/depth 映射到"并入尾部块"或"并入最新 user 的 volatile part"；②对 SToolBook 的"**置底**"，NyaaChat 里**等价物天然存在**（历史按序装配、尾部固定最后），无需专门机制——反过来说，也就没有"与破甲条目抢位置"的问题。 |
