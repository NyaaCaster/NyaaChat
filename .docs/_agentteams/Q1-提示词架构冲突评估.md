## 0. 结论速览

**一句话**：NyaaChat 的拼装规则与「小猫之神」机制**不存在"整体不可行"的致命冲突，但存在 1 处原样移植即致命的冲突（伪 JSON / messages 层重写）和 3 处严重冲突（前导 system 通道、后置 system 条目、assistant 预填尾 + absolute 注入）**。这 4 条全部有最小可行的替代落点（见 §6），代价是把猫神预设的"**位置武器**"换成"**权威 / 通道武器**"。

四条最关键的结论：

1. **NyaaChat 的请求尾部只有一个 system 槽位，且这是一条被 `api.ts` 显式依赖的不变量** [事实]。任何"再追加一条后置 system 条目"的做法，会让 `foldTailSystemIntoLatestUser` 因为"相邻两个 system"而**直接放弃折叠**（`api.ts:62`），后果依 provider 而定：Gemini/OpenAI 兼容层丢近因、非 Opus 的 Anthropic 路径把尾部规则**回灌顶层 system**（正是规范明令禁止的降级方式）。
2. **NyaaChat 完全没有 assistant 预填能力，也没有停止串能力** [事实]。更危险的是：把预填放在尾 system **之后**（最直观的写法）会连带**整条尾部规则折叠失效**；只有把预填放在尾 system **之前**才能保住折叠（见 §5.1）。
3. **"systems 改写"的方向与酒馆相反** [事实 + 推断]。酒馆的 `convertGooglePrompt` 把非前导 system **降级为 user**（保位置、丢 operator 权威，猫神报告 §2.4）；NyaaChat 前端**不重写 system**，但它会（a）把唯一尾 system **折叠进最新 user**（`api.ts:535`），（b）在 Anthropic 路径把中段/残留 system **提升进顶层 `system` 字段**（`api.ts:728-733`）。所以猫神预设里"靠后置条目吃近因"的设计，在 NyaaChat 上会得到相反结果。
4. **现有 ClavisSalomonis 破甲的注入点是"静态前缀"**（`bypassTemplates.ts:71-78`：插到第一条 system 之后），**不是尾部** [事实]。这意味着 Gemini 侧破甲文本天然走"最高权威通道"（systemInstruction），恰好是 4.0test 想要的**反面**、3.7f 想要的**正面**。AnswererFlagalac 若复刻该注入点，必须显式选择"要权威还是要近因"。

**对后续开发的直接影响**：可做；但 **不能照搬预设结构**，必须以"尾部单条 system 内的新块"（推荐）或"尾 system 之前的 assistant 预填 + 尾部新块"（进阶）为落点，并且**任何新块名都必须写进静态授权锚点**（`chatPipeline.ts:311-314`）才能继承 operator 级权威——而锚点文本必须**无条件恒定**，否则开关该模块就会击穿前缀缓存（`chatPipeline.ts:435-438`）。

## 2. A. NyaaChat 拼装结果形态（逐项 + 证据）

### 2.1 消息数组由哪几段构成

`buildRequestMessages()` 的返回值（`chatPipeline.ts:525-530`）是 `injectBypassPrompts([...systemMessages, ...history, ...tailMessages], ...)`。展开后的**代码顺序**：

```
[静态前缀 system 区]
  idx 0         system    SESSION_PROTOCOL_ANCHOR（恒定，无条件存在）   chatPipeline.ts:311-314, 439-441
  idx 1..k      ⚠ injectBypassPrompts 在此插入（bypass.enabled 为真时） bypassTemplates.ts:71-78
                  依序为 identityReset(system) / scenarioFramework(system)
                  / aiSelfPersuasion(assistant) / roleplayInduction(assistant)
                  / safetyStatement(system) / creativeGuidance(system) / disclaimer(system)
  之后          system    [User Persona: …]（条件）                     chatPipeline.ts:445-450
  之后          system    [Assistant Persona: …]（条件）                chatPipeline.ts:451-456
  之后          system|[Assistant Note]  role 取决 rule.position:      chatPipeline.ts:457-464
                system  [World Info] …      （permanent 世界书条目）
[历史]
                user/assistant 交替（仅存储层气泡；过滤掉 role==='system'
                与 imageUrl/imagePrompt 的气泡）                          chatPipeline.ts:373-383
[最新 user]
  idx L         user      本轮真实文本（可含图片/附件 parts）
                + volatile parts（按序：memory_context → search_context）  chatPipeline.ts:400-415
[动态尾部]
  idx L+1       system    <session_rules>…</session_rules>
                          + "\n\n" + <output_constraints>…</output_constraints>
                          （**唯一一条**；两块都空时该消息整条不存在）      chatPipeline.ts:496-523
```

**[事实]** 三条要点：
- 前缀 system 区**恒有至少一条**（锚点无条件，代码注释明确写了"making it conditional would flip the prefix bytes between turns and break the cache"，`chatPipeline.ts:435-438`）→ **NyaaChat 不可能产出"无前导 system"的请求**。
- 尾部 system 区**最多一条**（`tailMessages` 是 `blocks.length ? [ {system} ] : []`，`chatPipeline.ts:520-523`）。
- bypass 注入位置是**静态前缀**，不是尾部（`bypassTemplates.ts:73-78`：`insertIndex = result[0].role === 'system' ? 1 : 0`，然后 `splice`）。

### 2.2 尾部 system 的唯一性与折叠规则

**[事实] 唯一性是显式不变量**，源码注释原文（`chatPipeline.ts:504-510`）：

> `One trailing system message is an invariant api.ts depends on (foldTailSystemIntoLatestUser folds exactly one, and refuses when two systems are adjacent) — emitting a second trailing system would break the non-Opus downgrade fold.`

`foldTailSystemIntoLatestUser(messages)`（`api.ts:58-95`）：
1. `messages.length < 2` → 原样返回（`:59`）；
2. `last.role !== 'system'` → **原样返回**（`:62`）← 末条不是 system 就不折叠（例如末条是 assistant 预填）；
3. `prev.role === 'system'` → **原样返回**（`:62`）← 末两条相邻都是 system 时**拒绝折叠**；
4. 取出末条文本（`:64-70`）、丢掉末条（`:71`）、找 `core` 里最后一个 `user`（`:74`），把文本作为一个 `{type:'text', [VOLATILE_PART_FLAG]:true}` part **追加到那条 user 的 content**（`:87-94`）；
5. 找不到 user 时（`lastUserIdx === -1`）会**新造一条 user 尾消息**（`:75-85`，注释说这不是今天的生产路径）。

**[推断] 第 3 条守卫的设计意图**：如果末两条都是 system，只折叠最后一条会留下一条"孤儿 system"成为新的末条，返回的数组**依然以 system 结尾**（对 OpenAI 协议仍是非法形状）。所以守卫选择"拒绝而非半途折叠"。源码注释没有明写这层推导，故标 **[推断]**。

**谁调用折叠**：
- `fetchOpenAI` — **无条件**调用（`api.ts:535`），覆盖所有 `apiFormat === 'openai'` 的 provider，其中就包括 **Gemini**（NyaaChat 的 Gemini 走 `https://generativelanguage.googleapis.com/v1beta/openai`，`providers.ts:127`；`fetchChatCompletion` 只按 `apiFormat` 分支，`api.ts:306-311`）。
- `prepareAnthropicPayload` — 仅当 `supportsMidConvSystem === false` 时调用（`api.ts:706`）；该标志 = 官方 Anthropic host **且** 模型名匹配 `claude-opus-4-8`（`api.ts:1068-1070`）。为 true 时保留末条 system 作为 mid-conversation system，并在转换完成后**追加到 messages 数组末尾**（`api.ts:747-752`）。

**[事实] 折叠后的净效果**：OpenAI/Gemini 路径上，尾部 `<session_rules>`/`<output_constraints>` 以 **user 角色的文本 part** 参与生成；发送前 `stripVolatileFlags` 摘掉内部标记（`api.ts:37-46`、`api.ts:384`）。

### 2.3 世界书 soft/hard 归属

**[事实]**
- `triggerType === 'permanent'` → **静态前缀**（`chatPipeline.ts:457-464`），角色由 `rule.position` 决定（`system` → `[World Info]` system；`assistant` → `[Assistant Note]` **assistant** 角色消息）→ **NyaaChat 已有"前缀里放 assistant 角色消息"的先例**。
- `triggerType === 'keywords'`（含永久之外的激活项）→ **尾部那一条 system**（`chatPipeline.ts:470-486`），按 `hard === true` 分入 `═ 硬约束 ═` / `═ 场景设定 ═`（`:478-485`），并在最前面加 `RULES_MEDIATION_CLAUSE`（`chatPipeline.ts:322-323`，触发条件 `keywordRules.length > 0`，`:472-473`）。
- 世界书文本会走 `{{user}}/{{char}}` 替换 + `regex_placement.WORLD_INFO(=5)` 的正则通道（`chatPipeline.ts:427-432`）。

**[事实] 结论**：世界书**没有"absolute depth=0 注入"通道**——它只有"前缀"和"尾部单条 system"两个落点。

### 2.4 `<output_constraints>` 与 `<session_rules>` 的关系

**[事实]**（`chatPipeline.ts:496-523`）
- 二者是**同一条尾部 system 消息内的两个并列块**，拼接顺序固定为 `session_rules` 在前、`output_constraints` 在后，中间 `"\n\n"`。
- `<session_rules>` 只在有 keyword 世界书或 MCP 规则时出现，且**内含**调解条款；`<output_constraints>` 承载 RosettaStone（`wordCount` / `languageConstraint`），**在 `<session_rules>` 之外**、**不带**调解条款（注释明说"not scene rules, so they stay out of `<session_rules>`"）。
- **[事实] 关键独立性**：RosettaStone 的开关判定是 `settings.bypass?.[key].enabled && template?.trim()`（`:511-516`），**与 `settings.bypass.enabled`（ClavisSalomonis 总开关）无关**。这就是"AnswererFlagalac 若要独立于 ClavisSalomonis，就不能复用 `injectBypassPrompts`"的现成先例。

### 2.5 reasoning / 思维链如何处理

**[事实]** —— NyaaChat **目前没有 reasoning 通道**：
- `regex_placement.REASONING = 6` 已定义（`compat/regex/engine.ts:25`），但**全库无任何调用点**：`chatPipeline.ts` 只在 `USER_INPUT`(1)、`AI_OUTPUT`(2)、`WORLD_INFO`(5) 三个 placement 上跑正则（`:380-382`、`:393`、`:430`），`MessageItem.tsx:243` 走显示通道；grep `regex_placement.REASONING` 零命中。
- OpenAI 流式解析只读 `delta.content` 与 `delta.tool_calls`（`api.ts:471-490`）；Anthropic 只处理 `text_delta` 与 `input_json_delta`（`api.ts:1003-1007`）。**`reasoning_content` / `thinking` 字段既不下发也不接收、不显示**。
- `ApiSettings`（`types.ts:48-58`）没有 `reasoning_effort` / `show_thoughts` 等字段。

**[事实] 推论**：猫神预设里
- **文本标签式 CoT**（`<think_nya~>…</think_nya~>`，4.0test 的核心）——在 NyaaChat 里就是普通正文字符串，可以被 `AI_OUTPUT` placement 的正则清理/转义，**[可控]**；
- **原生 thinking 通道**（3.7f 的 `reasoning_effort:high` + `reasoning` 预填）——NyaaChat **完全不支持**，[严重]。

## 4. C. 逐项对照判定

**NyaaChat 侧的对照事实基线**：`fetchOpenAI` 无条件折叠唯一尾 system（`api.ts:535`）；`prepareAnthropicPayload` 把**除 mid-conv 尾条以外**的所有 system 文本合并进顶层 `system`（`api.ts:728-733, 754-757`），并合并相邻同角色 user/assistant（`:739-744`）；OpenAI 路径**不**做任何角色改写或合并（`api.ts:384` 逐个 map 原样发）。

## 5. D. 两个高风险点核验

### 5.1 「尾部仅一条 system」不变量 + 「两个相邻 system 拒绝折叠」是否使"后置 system 破甲条目 + 末尾 assistant 预填"无法成立？

**结论：在"预填放在最末"这一写法下，**确实无法成立（判定：严重，接近致命）**；但如果把预填放在尾部 system **之前**，组合是成立的——只是要接受折叠目标改变。**

**写法 A（预填在最末：`[…, user, system(尾), assistant(预填)]`）——不可行** [事实 + 推断]：

1. `fetchOpenAI`（含 Gemini）先跑 `foldTailSystemIntoLatestUser`：末条是 assistant ⇒ `last.role !== 'system'` ⇒ **`:62` 直接原样返回**。尾部 system 留在数组里、紧跟在最新 user 之后、末条是那条 assistant 预填。
   - OpenAI 语义上：system 允许出现在任意位置（标准 §5 line 103），请求大概率不报错，但**尾部规则的近因位置丢失**（它不再贴着生成点，而是被预填"隔开"）；
   - Gemini：按 NyaaChat 自有规范，兼容层会把所有 system 合并进 `systemInstruction`（标准 §5 line 105，**[待验证]**）⇒ **尾部规则被拽回开头**，且关键字集合每变一次就击穿隐式前缀缓存；
   - Anthropic 非 Opus：`supportsMidConvSystem=false` ⇒ 先折叠 ⇒ 拒绝（同上）⇒ `prepareAnthropicPayload` 的循环把**残留的尾部 system 文本一起塞进顶层 `system`**（`api.ts:728-733`）⇒ 正是标准 §5/§7.4 明令禁止的"回退为并入顶层 system"，每轮规则变化击穿整段历史缓存；
   - Anthropic Opus 4.8：`tailSystem` 的检测条件是 `last.role==='system' && prev.role!=='system'`（`api.ts:708-715`），此时 last 是 assistant ⇒ **检测失败** ⇒ 同样落入上面的顶层 system 合并分支。
2. 而"后置 system 破甲条目"本身若再追加成**第二条**尾部 system，则末两条相邻都是 system ⇒ `:62` 同样拒绝（这一条与预填无关，是更基础的冲突）。

**写法 B（预填插在尾部 system 之前：`[…, user, assistant(预填), system(尾)]`）——可行** [事实 + 推断]：

- 折叠判定通过（last=system，prev=assistant）⇒ 末条 system 被折进 `lastIndexOf('user')` 找到的 **user 消息**（即预填之前那条最新 user）⇒ 结果 `[…, user(+session_rules part), assistant(预填)]`：**尾部规则保住了近因，预填也保住了**。
- 但三个连带代价：
  1. **尾部规则的位置从"数组最末"变成"预填之前"**——生成点之前多了一条 assistant，规则与生成点之间隔了一条消息（近因略降，但仍远好于被拽回开头）；
  2. **Anthropic Opus 4.8 路径**：tailSystem 会被 push 到预填**之后**（`api.ts:747-752`），变成 `[…, user, assistant(预填), system]`，预填不再是末条 ⇒ 预填语义丢失（标准 line 101/120 允许 system 为末项，但"从已表态处续写"这一决策点消除效果不再成立）；
  3. 若该轮**尾部 system 为空**（无关键字规则、无 MCP、RosettaStone 全关 ⇒ `tailMessages = []`），则写法 B 等同于写法 A（末条就是预填）⇒ 又回到折叠失效。**这一点很容易被漏掉**：预填是否安全**取决于本轮尾 system 是否存在**，属于"每轮可变"的隐式状态。

### 5.2 NyaaChat 是否对 system→user 做改写/合并，从而改变破甲文本的通道与优先级？

**结论：NyaaChat 前端不做 ST 那种 system→user 改写；但它做了更激进的方向相反的通道操作。猫神预设的"位置武器"在 NyaaChat 上会退化为"权威 / 通道问题"。**

[事实] 三条对照事实：

| 环节 | ST（`convertGooglePrompt`，猫神报告 §2.4） | NyaaChat OpenAI 路径（含 Gemini 兼容端点） | NyaaChat Anthropic 路径 |
|---|---|---|---|
| 前导 system | 抽进 `systemInstruction` | 原样发送（**Google 侧行为 [待验证]**） | 抽进**顶层 `system` 字符串**，`"\n\n"` 连接（`api.ts:717, 728-733, 754-757`） |
| 中段 / 后置 system | **改写为 user**（`prompt-converters.js:459-460`）并相邻合并 | 原样保留为 system；**仅末条**被折叠成最新 user 的文本 part（`api.ts:58-95, 535`） | 除 mid-conv 尾条外**全部**抽进顶层 `system`（`:728-733`） |
| assistant | 改写成 `model` | 原样 | 原样（角色保持 assistant） |
| 相邻同角色 | 合并（`\n\n`） | **不合并** | user/assistant 合并（`:739-744`） |
| stop | `data.stop`（且**仅当 `ChatSquash.enabled`**，SPreset 专项 §0 第 3 条） | 无字段 | 无字段 |

[推断 + 待验证] 因此：
- 猫神预设的"后置 system 条目"在酒馆里被**降级为 user 并贴紧生成点**（保位置、丢 operator 权威，靠 `role:"system"` 字样骗模型的先验）；在 NyaaChat 上，同一个"尾部"落点却是**被折叠成 user 文本 part**（位置保住了、权威靠静态授权锚点委托）——**机制不同但结果接近**，这是好消息。
- 而"多条目后置"与"预填在最末"两种写法会把尾部 system **提升/拉回顶层 `system`**（Anthropic 必现，Gemini 大概率）——这等于**保住了权威、彻底丢掉了近因**，与猫神方案的收益方向相反。这是本报告最需要下游设计注意的一条。
- 破甲文本通道的**优先级来源**在 NyaaChat 上是**静态授权锚点**（`chatPipeline.ts:311-314`），它当前只声明了三类块：`<session_rules>` / `<search_context>` / `<memory_context>`。
  **[事实 + 重要设计约束]** 若 AnswererFlagalac 用新的块名（例如 `<answerer_flagalac>`），**必须把该块名写进锚点**，否则它只是"用户在对话里说的话"，拿不到 operator 级权威；同时锚点文本必须**无条件恒定**——不能"模块开启才追加该句"，否则开关模块就会改变静态前缀字节、击穿缓存（同 `chatPipeline.ts:435-438` 的既有理由，标准 §7.5）。

## 6. E. 最小可行的替代落点（含代价与风险）

> 建议按 **E1 → E3 → E4 → E6/E7** 的优先级推进；E5 明确不建议。
> 所有方案都应在 `buildRequestMessages`（`chatPipeline.ts:345`）内部完成，**不要改 `api.ts` 的发送层**——因为 `fetchChatCompletion` 有 4 个调用点（`ChatInterface.tsx:822` 主回合、`ChatInterface.tsx:1680/1736` 图像提示词侧请求、`lib/memoryExtraction.ts:407` 记忆抽取、`compat/generate.ts:95` 卡牌侧请求），在 `api.ts` 里加对话特化逻辑会外溢到这些旁路请求。

### E1（推荐）★ 破甲载荷并入"尾部那唯一一条 system"的独立新块

- **做法**：在 `chatPipeline.ts:496-523` 组装 `tailMessages` 时，按 `settings.bypass.answererFlagalac.target` 取载荷，作为一个**独立块**（例如 `<answerer_flagalac>…</answerer_flagalac>`）与 `<session_rules>` / `<output_constraints>` 并列拼接进同一条尾部 system。
- **优点**：零结构改动、不触碰任何不变量；折叠路径不变；Gemini/OpenAI 最终落在最新 user 的 volatile part（近因最高）；内容随用户配置恒定 ⇒ 不击穿缓存（尾部本就在缓存断点之后，标准 §2/§5）。
- **代价 / 风险**：
  1. 权威级别在 Gemini 上是 **user 通道**，必须靠锚点委托 ⇒ **必须把新块名写进 `SESSION_PROTOCOL_ANCHOR` 且无条件恒定**（见 §5.2）；
  2. **不要塞进 `<session_rules>` 内部**：那会与 `RULES_MEDIATION_CLAUSE`（"叙事走向以用户最新发言为准"，`chatPipeline.ts:322-323`）同处一块，被调解条款主动削弱；也应与 RosettaStone 的先例一致——独立块、不进 `session_rules`（`:501-519` 的既有注释）；
  3. Anthropic 非 Opus / 第三方代理路径**本来就会**把尾部 system 回灌顶层 `system`（`api.ts:706, 728-733`）——这是既有降级行为，不是本方案引入的，但要知道 Gemini 的收益在 Anthropic 代理上不成立；
  4. **尾块为空时的边界**：`tailMessages` 为空时该消息整条不存在，载荷就没有落点 ⇒ 需要让"AnswererFlagalac 启用"本身成为"必须产出尾部 system"的条件（即 `blocks.length` 的判定要把该块算进去）。
- **顺带收益**：这条路径天然满足"独立于 ClavisSalomonis 的 `enabled`"（RosettaStone 已有先例，`chatPipeline.ts:511-516`），而 `injectBypassPrompts` 做不到（`bypassTemplates.ts:38` 早返回）。

### E2（不推荐，但有特定用途）载荷并入最新 user 的**真实文本**

- **做法**：把载荷拼进用户当轮文本，或作为非 volatile 的 text part。
- **代价**：语义上变成"用户说的"，模型可能按"用户注入"抵抗；且会改变 Anthropic 断点②的锚点位置（`api.ts:839-855` 锚在最后一个非 volatile part），需要重新评估缓存行为。
- **唯一适合的场景**：想复刻 RuleBreaker 那种"由用户发出"的交互（`BypassModal.tsx:240-245` 通过 `onSendMessage` 直接发文本）——那是**另一个模块**的既有模式，不适合 AnswererFlagalac 的自动注入。

### E3（进阶，可控）单独追加一条 **assistant 预填**，位置固定在尾部 system **之前**

- **做法**：在 `tailMessages` 之前插入 `{ role: 'assistant', content: '<think_nya~>\n…' }`，并**保证尾部 system 仍为末条**（当本轮尾部 system 为空时，要么禁用预填、要么人为产出尾 system）。
- **优点**：保住折叠（见 §5.1 写法 B）；复刻"从已表态处续写"的决策点消除效果（猫神报告 §4.6、§7.4）。
- **代价 / 风险**：
  1. 折叠目标从"最新 user"变成"预填之前的最新 user"，规则与生成点之间多隔一条消息；
  2. Anthropic Opus 4.8 mid-conv 路径会把尾条 system 推到预填之后（`api.ts:747-752`）⇒ 该路径预填语义失效；
  3. **本轮尾部 system 是否存在是可变的**，预填的安全性因此也跟着变——必须做成"要么永远有尾 system、要么不用预填"的硬约定；
  4. 预填 assistant 只存在于本次请求，**不入存储**（`ChatInterface.tsx` 的 messages 状态不感知它），因此重生成、编辑、显示都不受影响（可接受，但需要在实现里明确）。
- **[待验证]**：Gemini 兼容层是否接受"末条为 assistant"的请求并按其续写；Anthropic 是否接受 `[user, assistant(预填), system]` 这种形状。

### E4（可控，改造量中等）走"伪工具通道"

- **做法**：在 `ChatInterface` 的 MCP 装配之外，新增一个**纯前端本地工具源**（`LlmTool[]` + `executeTool` 直接在前端实现），`answererFlagalac.target !== 'none'` 时把 `game_content` 类的工具加入 `mcpToolUseOptions`；输出侧增加"消费型工具"语义（把工具参数内容当作正文输出、不再回灌 `role:'tool'`）。
- **优点**：这是 3.7f 的核心机制（猫神报告 §5.6）；NyaaChat 的工具循环已经在 `api.ts` 里实现完毕（`:541-624` / `:1084-1159`），且工具参数的流式 delta **本来就不会回调 `onChunk`**（`api.ts:475-489` 只累积、不显示），"参数不走文本流"这一点天然满足。
- **代价 / 风险**：
  1. `executeTool` 现有契约是"返回文本给模型看"（`ToolExecutionResult`，`api.ts:108-115`）；要"回收为正文"必须新增分支（等价于 SPreset 的 `consumeToolCalls`，SPreset 专项 §4.4），否则工具结果会以 `role:'tool'` 回灌（`api.ts:615-622`）——而这恰好会被模型看见；
  2. 需要保证本地工具**不污染** `assembleMcpRules`（`chatPipeline.ts:235-272`：未知工具名会带来 `[MCP 工具使用准则]` 头 + 失败降级规则）与 `ADVERTISED_TOOLS` 白名单（`mcpApi.ts:278-289`）；
  3. 需要 `ChatInterface.tsx:693-789` 之外的一条独立装配路径（当前 MCP 分支同时受 `settings.isMcpEnabled`、`anyToolEnabled`、模型 `capabilities` 三道门控，其中"模型能力探测"门控会误伤）；
  4. **[待验证]** Gemini 兼容端点对 `tools` + 流式工具参数的支持度。

### E5（**不建议**）复刻"伪 JSON / 单条 assistant 承载全上下文"

- **代价**：违反标准 §7.1/§7.2 与 §2 核心不变量；前缀缓存全废（历史每轮被重写）；历史正则 `depth` 语义（`chatPipeline.ts:376-382`）失效；`Message.content` 存储模型不承载伪 JSON；编辑/重生成/日志链路全部需要重新定义。
- **结论**：**致命冲突，不建议原样移植**。若确要实验，应做成"显式可选的实验模式"，并在 UI 明示"会关闭缓存、显著增加成本"。

### E6（可控，小改）停止串

- **做法**：在 `requestBody` 增加 `stop`（OpenAI 路径，`api.ts:382-392`）与 `stop_sequences`（Anthropic 路径，`api.ts:857-881`），由 AnswererFlagalac 目标决定是否挂 `<end>`。
- **风险**：停止串对**该会话所有模型**生效；正文里合法出现 `<end>` 会被提前截断。另外 3.7f 原版里这条**本来就没生效**（SPreset 专项 §0 第 3 条：`stop_string` 受 `ChatSquash.enabled` 守卫），所以它不是必需项。

### E7（可控）痕迹清理（CoT / disclaimer / 控制标签）

- **做法**：直接用 NyaaChat 已有的 prompt 正则通道（`AI_OUTPUT` placement=2 + `minDepth`），脚本形态与酒馆同源（`compat/regex/engine.ts:20-26`、`types.ts:219-243`）。`<think_nya~>` 是**文本标签**（不是原生 reasoning），因此这条路对 4.0test 的 CoT 隐藏是可行的。
- **风险 / 顺序陷阱**：正则是在 `chatPipeline.ts:378-383` 生成 history 时就跑掉的；如果 E1/E3/E4 的新逻辑在 `:525` 之后才改写 messages，**正则先于改写执行**，改写新引入的标记不会被本轮正则处理——实现时必须显式约定"正则 → 破甲改写"的顺序，或让改写层自行处理。

## 8. 给下游（Q0 汇总 / 后续开发）的硬约束清单

1. **尾部只能有一条 system**。任何新增后置内容必须并入这一条（E1），不得追加第二条（`chatPipeline.ts:504-510`、`api.ts:62`）。
2. **不要在尾 system 之后追加任何消息**（尤其 assistant 预填），否则整条尾部规则折叠失效，Gemini 丢近因、Anthropic 代理路径回灌顶层 system（§5.1 写法 A）。
3. **新增注入块必须登记进 `SESSION_PROTOCOL_ANCHOR`，且锚点文本无条件恒定**（`chatPipeline.ts:311-314, 435-438`；标准 §7.5）。
4. **AnswererFlagalac 载荷不要复用 `injectBypassPrompts`**（它受 `bypass.enabled` 门控且注入静态前缀，`bypassTemplates.ts:38, 71-78`）；应与 RosettaStone 同构，作为独立块、独立开关。
5. **所有破甲装配逻辑放在 `chatPipeline.ts`，不要放进 `api.ts` 的发送层**——`fetchChatCompletion` 有 4 个调用点，改发送层会外溢到图像/记忆/卡牌侧请求。
6. **不要重写历史**（伪 JSON / 历史合并），否则违反标准 §2/§7.1/§7.2 并废掉前缀缓存（致命）。
7. **预填的安全性依赖"本轮是否存在尾部 system"**——若走 E3，必须把这条做成硬约定，不能让它随手变（§5.1 写法 B 第 3 点）。
8. **reasoning / 原生 thinking 在 NyaaChat 完全不存在**（§2.5）；依赖 3.7f 原生思考通道的选项在 NyaaChat 上要么改成文本标签，要么不做（这条结论对 Q3 的选项取舍是硬约束）。
