# 详细设计：记忆生命周期与配额

> 覆盖空洞 G / H。归属仓库：`nyaachat-knowledge` + `shared-server` + `NyaaChat` 主仓
> 关联不变量：SSOT §11 第 6 条「禁止全量对账式孤儿回收」

---

## 1. 计量口径（空洞 H）

### 1.1 定案

**`usage` = 该 owner 记忆库下所有 chunk 的 `char_count` 之和**，跨全部 session 汇总。

```sql
SELECT COALESCE(SUM(char_count), 0) FROM chunks WHERE kb_id = <memoryKbId>
```

`quota` = `users.memory_char_max`，默认 `2000000`（字符，非字节）。

### 1.2 为什么用 chunk 字符和而不是原文长度

| 备选口径 | 否决理由 |
|---|---|
| `documents.size_bytes` 之和 | 是字节；CJK 一字 3 字节，中英混排时同样的"信息量"配额相差 3 倍，用户无法理解 |
| 新增 `documents.char_count` 存原文长度 | 需加列，且与 `knowledge_bases.char_total` 双口径并存，两个数字会对不上，日后必然有人问哪个对 |
| chunk 字符和 | `char_total` 已经是这个口径（`ingest.js:40`、`documents.js:31`），`GET /memory/usage` 与知识库用量显示同源 |

### 1.3 必须明说的重叠膨胀

`splitIntoChunks(content, 256, 25)` 的 step = 231，所以 chunk 字符和 ≈ 原文长度 × 256/231 ≈ **1.108 倍**。
即 2,000,000 的配额实际能装约 **1.8 MB 原文**。

这是可接受的，因为：配额是天花板而非计费单位，恒定系数不影响用户对"还剩多少"的判断；
而换成原文口径就要引入第二个数字。**UI 展示 `usage/quota` 时不做任何折算**，
直接显示服务端返回值 —— 折算会让"剩余"与超限触发点不一致。

### 1.4 配额扩容：V1 不做

V1 **不提供**付费扩容记忆配额。理由：扩容要在 NyaaAcount 的 `pricing.json` / `events.json`
登记计费项（跨项目改动，参照 `expand_chat_storage` 的实现面），
超出本 V1 范围。超限的出口是二次压缩（§3）。

`memory_char_max` 列仍然按 `chat_storage_max` 的形式加上（见 `设计-服务端API与数据模型.md` §1.2），
V2 加扩容端点时无需再动 schema。

## 2. 删除与回收（空洞 G）

三条回收路径，优先级从确定到兜底：

### 2.1 显式删除（主路径）

用户在 `ChatHistoryModal` 删除对话，或 `handleDeleteConfirm`（`ChatHistoryModal.tsx:128`）执行时：

```ts
// After the local session is removed, drop its server-side memory. Fire and
// forget with a logged failure: the TTL sweep is the backstop, so a transient
// network error must not block the local deletion the user asked for.
if (settings.isMemoryEnabled && token) {
  deleteSessionMemory(token, deletedId).then((r) => {
    if (!r.ok) console.warn("[memory] session cleanup failed, TTL will reclaim:", r.error);
  });
}
```

同样接在 `replaceAllSessions`（云端覆盖式下载）之后 —— 但**不**为消失的 session 逐个删除：
覆盖下载后本地 session 集合变了，逐个对账就是被禁止的全量对账。
交给下一次心跳 + TTL。

### 2.2 心跳（保活）

**频率**：
- 应用启动完成、且已登录、且 `isMemoryEnabled` 为真时，**一次**
- 之后每 **6 小时** 一次（`setInterval`，仅在页面存活期间）
- 节流：本地记录 `nyaachat_memory_heartbeat_at`（IDB via `idbStorage`），
  距上次 < **1 小时** 则跳过 —— 防多标签页与频繁刷新造成请求风暴

**载荷**：`loadSessions().map((s) => s.id)`，即**本地全部 session id**。
不做分页；上限 500 由服务端校验，超过则取最近 500 个（按 `createdAt` 降序）。

**空数组绝不发送**（客户端就地拦截，服务端也拦截 —— 双保险，这是不变量 6 的落点）。

```ts
// src/lib/memoryLifecycle.ts
const HEARTBEAT_INTERVAL_MS = 6 * 60 * 60 * 1000;
const HEARTBEAT_MIN_GAP_MS = 60 * 60 * 1000;
const HEARTBEAT_AT_KEY = "nyaachat_memory_heartbeat_at";
const MAX_HEARTBEAT_SESSIONS = 500;
```

### 2.3 TTL 清扫（兜底）

**TTL = 90 天**，可由环境变量 `MEMORY_TTL_DAYS` 覆盖（默认 90）。

90 天的理由：低于此值，一个用户换设备/长假回来就可能丢掉仍在用的对话记忆；
高于此值，被彻底遗弃的会话会长期占着配额。90 天足够长到不误伤，短到能实际回收。

#### 执行者：搭载在心跳请求上（机会式清扫）

knowledge 服务是纯 express 进程，**没有 cron、没有 worker**。方案定为：

在 `POST /memory/heartbeat` 处理完保活之后，**同一请求内**顺带执行一次该 owner 的清扫，
且满足全部前置条件：

```js
// Opportunistic TTL sweep, riding the heartbeat.
//
// Preconditions, all required:
//   1. sessionIds was non-empty — an empty list means "this client knows about
//      no sessions", which is exactly the state a logged-out or freshly-reset
//      browser is in. Sweeping then would delete memory for sessions that live
//      on another device. This is the invariant "never full-reconciliation".
//   2. This owner has not been swept in the last SWEEP_MIN_GAP_MS (24h) —
//      keeps the heartbeat cheap and bounds DB churn.
//   3. Only documents whose last_seen_at is older than the TTL are touched.
//      Anything the heartbeat just refreshed is by definition safe.
//   4. At most SWEEP_BATCH_LIMIT (200) documents per call, oldest first, so a
//      single request can never turn into a multi-second delete storm. The
//      remainder is picked up by the next heartbeat.
const TTL_MS = (Number(process.env.MEMORY_TTL_DAYS) || 90) * 24 * 60 * 60 * 1000;
const SWEEP_MIN_GAP_MS = 24 * 60 * 60 * 1000;
const SWEEP_BATCH_LIMIT = 200;
```

上次清扫时间**存内存**（`Map<owner, timestamp>`），不落库：进程重启后最多多扫一次，
代价是一次索引查询；为它加一张表不值得。

清扫 SQL：

```sql
SELECT id FROM documents
 WHERE kb_id = ?
   AND session_id IS NOT NULL
   AND last_seen_at IS NOT NULL
   AND last_seen_at < ?
 ORDER BY last_seen_at ASC
 LIMIT 200
```

`last_seen_at IS NOT NULL` 是硬条件：任何原因导致该列为 NULL 的行**永不被清扫**，
宁可占配额也不误删。（ingest 时必填，理论上不会出现。）

删除逻辑与 `DELETE /memory/session/:sessionId` 完全相同（同一个内部函数
`deleteMemoryDocuments(kbId, docIds)`，见 `设计-服务端API与数据模型.md` §4.3）。

响应扩展为 `{ ok: true, touched: number, swept: number }`。
前端不展示 `swept`，仅在 `swept > 0` 时 `console.info`。

#### 运维手动清扫

另加 `POST /internal/memory/sweep`（`internal.js` 的 shared-secret 鉴权），
body `{ owner?: string }`：无 `owner` 则遍历所有记忆库。
用途是排障与一次性回收，**不接入任何定时器**。

### 2.4 关闭开关时的处置

见 `设计-账号界面与设置存档.md` 空洞 Q 定案。生命周期侧只保证：
关闭开关后心跳停止发送 → 已有记忆最终由 TTL 回收。

### 2.5 已知限制（须写入交接文档）

用户 90 天内只在设备 A 用某会话、设备 B 从不下载云记录，
则设备 B 的心跳不含该 session id。但只要设备 A 在 90 天内心跳过一次即安全。
**两台设备都 90 天不打开该会话，记忆才会被回收** —— 与"遗弃"的定义一致。

## 3. 二次压缩（空洞 H 下半）

### 3.1 触发

`POST /memory/ingest` 返回 `409 memory_char_max_reached`，body 含 `{ usage, quota }`。
客户端此时**已经花过一次提炼 token**，压缩是为了让这批结果能存下去。

### 3.2 需要的两个附加端点

SSOT §6 列了 5 个端点，但"合并重提炼"需要把已存记忆读回客户端并原子替换，
SSOT 未指定传输方式。定案补两个：

#### `GET /memory/batches?sessionId=<id>`

```
响应 200 { ok: true, batches: MemoryBatch[] }
```

`MemoryBatch` 的客户端类型定义在 `设计-服务端API与数据模型.md` §5
（与 client 函数同处，`src/lib/knowledgeApi.ts`）。字段：`batchSeq` /
`charCount` / `uploadedAt`（epoch ms，取 `documents.created_at`）/ `content`
（由 chunks 重建，见 §3.3，**不保证**与原文逐字相同）。

- 按 `batchSeq` 升序
- `content` 由该 document 的 chunks 按 `seq` 重建（见 §3.3）
- 无记忆库 / 无该 session → 200 `{ batches: [] }`
- **仅返回调用者自己的记忆库内容**（owner 由 token 决定，与其他端点同）

#### `POST /memory/recompress`

```
请求 { sessionId: string, replaceBatchSeqs: number[], content: string }
响应 201 { ok: true, document: {...}, freedChars: number }
```

- `replaceBatchSeqs` 长度 ≥ 2，否则 400 `nothing_to_merge`
- 所有 seq 必须存在于该 session，否则 400 `batch_not_found`（不做部分执行）
- 单事务：删除被替换的 documents（复用 `deleteMemoryDocuments`）→ 插入新 document，
  `name = \`${sessionId}#${Math.min(...replaceBatchSeqs)}\``
- **先删后插**，所以新内容不与旧内容同时占配额；插入后仍超限则整个事务回滚，
  返回 409 `still_over_quota`，body 附 `{ usage, quota }`
- 幂等性不适用（内容由模型生成，每次不同）；请求失败时旧批次保持不动

### 3.3 chunk 重建算法

chunk 之间有 25 字符重叠且各自 `trim()` 过，故重建须消重叠：

```js
/**
 * Rebuild the original batch text from its chunks. Chunks overlap by
 * MEMORY_CHUNK_OVERLAP characters and were individually trimmed, so a plain
 * join would duplicate the seam. Strip the longest prefix of the next chunk
 * that the accumulated text already ends with, capped slightly above the
 * configured overlap so a trim-shifted seam still matches.
 */
const MAX_SEAM = 40; // MEMORY_CHUNK_OVERLAP (25) + slack for trimmed edges
function reconstructBatch(chunkContents) {
  let out = "";
  for (const piece of chunkContents) {
    if (out === "") { out = piece; continue; }
    let cut = 0;
    for (let k = Math.min(MAX_SEAM, piece.length); k > 0; k--) {
      if (out.endsWith(piece.slice(0, k))) { cut = k; break; }
    }
    out += piece.slice(cut);
  }
  return out;
}
```

重建结果**不保证与原文逐字相同**（trim 会吃掉边界空白）。这是可接受的：
重建产物唯一用途是喂给模型做合并，不是作为权威副本。

### 3.4 选取哪些批次合并

```ts
const RECOMPRESS_MIN_BATCHES = 2;
/** Merge the oldest half (rounded up), so each compression pass roughly halves
 *  the session's batch count instead of nibbling one batch at a time. */
function selectBatchesToMerge(batches: MemoryBatch[]): MemoryBatch[] {
  if (batches.length < RECOMPRESS_MIN_BATCHES) return [];
  return batches.slice(0, Math.ceil(batches.length / 2));
}
```

只有 1 个批次时**无法压缩**。此时提示用户：删除不再需要的历史对话以释放记忆配额
（`ConfirmDialog`，仅"知道了"一个按钮），并跳过本次入库 —— 本次提炼结果丢弃。
这条路径必须明确告知，否则用户以为存进去了。

### 3.5 压缩提示词

`src/lib/memoryExtraction.ts` 常量 `RECOMPRESS_SYSTEM_PROMPT`。
沿用 `EXTRACTION_SYSTEM_PROMPT`（见 `设计-提炼提示词与输出规约.md` §2）的
防注入声明与六小节格式，仅替换任务说明段：

```
你是一个记忆归档压缩器。你会收到若干份**已经归档过**的结构化事实条目，它们按时间先后排列。
你的任务是把它们合并成一份更紧凑的归档，保留全部有效信息，删除冗余。

【合并规则】
1. 同一实体的多条描述合并为一条，保留最终状态，并保留导致变化的关键事件。
2. 后出现的信息与先出现的冲突时，**以后出现的为准**，冲突本身不必记录。
3. 【未闭合】中已经在后续批次里被解决的条目，删除。
4. 输出总长度应不超过输入的一半。
5. 绝不发明输入中不存在的信息。
```

user 消息：

```
以下是 N 份按时间先后排列的归档，请合并压缩：

──── 归档 1 ────
<content>

──── 归档 2 ────
<content>
```

输出解析复用 `parseExtraction()`，规则完全相同。

### 3.6 完整流程与失败处置

```
ingest → 409 memory_char_max_reached
  ↓
GET /memory/batches → selectBatchesToMerge
  ↓ 只有 1 批 → 告知 + 丢弃本次结果，结束
  ↓
ConfirmDialog：告知需再调一次模型、预估 token、可取消
  ↓ 取消 → 丢弃本次结果，本轮不提炼（状态机置 skipped）
  ↓
runExtraction(RECOMPRESS_SYSTEM_PROMPT, 合并材料)
  ↓ 失败 → 丢弃本次结果，状态机置 failed（stage: recompress）
  ↓
POST /memory/recompress
  ↓ 409 still_over_quota → 告知配额仍不足，丢弃本次结果
  ↓ 成功
POST /memory/ingest（重试本次批次，batchSeq 不变 —— 幂等键未被占用）
```

**"丢弃本次结果"意味着用户白花了一次提炼的 token。**因此 §3.4 的确认弹窗必须
把这个代价讲清楚，且压缩不得自动发起 —— 与不变量 9（提炼绝不静默发起）同标准。

关键顺序约束：**先压缩腾空间，再重试原批次**。反过来（先删旧再存新）会在压缩失败时
把已有记忆删掉却没存进新的，净损失。

## 4. 验收清单

1. `GET /memory/usage` 的 `usage` 与手工 `SUM(char_count)` 一致
2. 存入 1000 字原文后，`usage` 约为 1108（±5%），验证膨胀系数已知且稳定
3. 空 `sessionIds` 心跳：`touched = 0`、`swept = 0`、DB 无任何删除
4. 把某 document 的 `last_seen_at` 手工改为 91 天前，携带其他 session 的非空心跳 → 该 doc 被清扫
5. 同上但心跳载荷**包含**该 sessionId → 该 doc 的 `last_seen_at` 被刷新、**未被**清扫
6. `last_seen_at` 置 NULL → 永不被清扫
7. 24 小时内第二次心跳不触发清扫（`swept = 0`）
8. 单次清扫上限 200，剩余在下次心跳继续
9. 删除对话后服务端该 session 的 chunks / chunks_fts 归零
10. 超配额 ingest 返回 409 且**不产生任何部分写入**
11. 二次压缩后 `usage` 下降，被替换批次消失，新批次 `name = <sessionId>#<minSeq>`
12. 压缩后仍超限 → 事务回滚，旧批次完好无损
13. 只有 1 个批次时超限 → 提示且不发起任何模型调用
14. `reconstructBatch` 对 3 个以上 chunk 的批次不出现重复接缝文本
