## 仍需继续验证 / 已知问题

| 项 | 说明 |
|---|---|
| 端到端闸门未实测 | 达阈值触发、提炼→检索召回、parseExtraction 各 case 均需 Docker 环境（`nyaachat-frontend` + `nyaachat-knowledge` 容器运行中）才能验证。纯函数（`parseExtraction`、`selectExtractionRange`、`computeContextBudget`）可离线单测，但 P3 未写单测文件 |
| `selectExtractionRange` 边界 case | 尾部全是 user 消息 + 无 assistant 边界时 → `return null`；仅 1 条超长消息占满上下文 → `MIN_EXTRACT_MESSAGES` 不满足 → 静默不触发。这两种 case 未实测 |
| `runExtraction` 的 temperature | 设计要求 0.3，但当前实现调用 `fetchChatCompletion` 时未传 `temperature`——取决于 API adapter 的默认值。若默认值偏高，提炼输出可能不稳定。P3 接受此限制 |
| `memoryExtraction.ts` 的 IIFE 类型断言 | `ConfirmDialog` 中 `extractionState.phase` 的 `as` 断言用了内联 `import()`——不够干净，但 TypeScript 编译通过。可在 P4 重构为独立变量 |
| `retryExtraction` 的 ingest 重试 | 设计要求「ingest 失败重试不调模型」但 P3 的 `failed` phase 不携带 `extracted` 文本——`failed` 类型需要扩展字段。当前 fallback 到重新提炼（调模型），P4 补 |
| 知识库服务端无需改动 | P3 全部改动在主仓，`nyaachat-knowledge` 零改动 |
