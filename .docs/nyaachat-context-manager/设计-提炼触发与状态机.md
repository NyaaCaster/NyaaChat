# 详细设计：提炼触发与状态机

> 覆盖空洞 A / C / K / L / R。归属仓库：`NyaaChat` 主仓

---

## 1. 触发前置条件（全部为 AND）

按判定成本从低到高排序，短路求值：

| # | 条件 | 不满足时 |
|---|---|---|
| 1 | `settings.isMemoryEnabled === true` | 静默跳过 |
| 2 | 已登录（`StoredAccount` 存在且有 token） | 静默跳过 + 见 §7 |
| 3 | 当前会话已保存（有 `session.id`） | 静默跳过（草稿会话无 sessionId，无处归属） |
| 4 | 无正在进行的提炼（`extractionState.phase === "idle"`） | 静默跳过 |
| 5 | 本会话本次达阈值尚未被用户「本次跳过」 | 静默跳过 |
| 6 | `computeContextBudget().overThreshold === true` | 正常发送 |
| 7 | 可提炼轮次数 ≥ `MIN_EXTRACT_TURNS`（见 §2） | 正常发送 + 见 §2.3 |

**判定时机：用户点发送后、`buildRequestMessages` 之前**。

不在「收到响应后」判定，因为那样这一轮已经用超额上下文发出去了，
下一轮才修正，等于永远晚一轮 —— 而"晚一轮"在 90% 阈值下就是撞 400。

## 2. 提炼范围：N 轮如何确定（空洞 C）

### 2.1 参数

```ts
/** Fraction of the *conversation* to hand over to extraction when triggered.
 *  0.4 leaves the recent 60% verbatim — enough that the model still has the
 *  immediate scene in full fidelity, while reclaiming a meaningful chunk. */
const EXTRACT_FRACTION = 0.4;
/** Never extract fewer than this many messages — a tiny batch costs a full
 *  model call for almost no reclaimed context. */
const MIN_EXTRACT_MESSAGES = 10;
/** Never hand more than this many characters to one extraction call. */
const EXTRACT_CHAR_CAP = 60_000;
```

### 2.2 选择算法

```ts
/**
 * Pick the oldest slice of history to extract.
 *
 * Constraints, in order of precedence:
 *  1. Never split a user/assistant pair — the boundary must land AFTER an
 *     assistant message, or the remaining history starts mid-exchange and the
 *     model sees an answer with no question.
 *  2. Never re-extract: start after the last existing memory boundary.
 *  3. Skip image bubbles — buildRequestMessages already filters them out of
 *     the request (chatPipeline.ts:364), so they are not consuming context and
 *     their content is a 2K-char image directive, not narrative.
 *  4. Respect EXTRACT_CHAR_CAP by trimming from the END of the slice (keep the
 *     oldest, which is what is about to fall out of context).
 */
export function selectExtractionRange(
  messages: Message[],
  lastBoundaryIndex: number,   // -1 when no extraction has happened yet
): { start: number; end: number; messages: Message[] } | null
```

实现步骤（照此实现，无需决策）：

1. `start = lastBoundaryIndex + 1`
2. `candidates = messages.slice(start)`，过滤掉 `role === "system"`、`imageUrl`、`imagePrompt`
   —— **过滤后保留原索引**（需要它来算 boundary）
3. `targetCount = Math.floor(candidates.length * EXTRACT_FRACTION)`
4. `if (targetCount < MIN_EXTRACT_MESSAGES) return null`（→ 前置条件 7 不满足）
5. 从 `candidates[targetCount - 1]` 往后找第一个 `role === "assistant"` 的元素，
   把 `end` 设为它的原索引。找不到（尾部全是 user）→ 往前找最后一个 assistant；
   仍找不到 → `return null`
6. 累加 `content.length`，若超 `EXTRACT_CHAR_CAP`，从 `end` 往前回退到上一个 assistant 边界，
   重复直到不超（或退到不足 `MIN_EXTRACT_MESSAGES` → `return null`）
7. 返回 `{ start, end, messages: <原索引区间内过滤后的消息> }`

### 2.3 「轮次不足」的静默处理

条件 7 不满足意味着：上下文已超阈值，但可提炼的内容太少（例如单条超长消息占满上下文）。
此时**静默正常发送**，不弹窗、不报错。理由：这种情况提炼帮不上忙，
弹一个"无法提炼"的窗只是打扰。

## 3. 状态机（空洞 A）

```
  idle ──达阈值──> prompting ──确认──> extracting ──成功──> ingesting ──成功──> idle
   ^                  │                    │                  │
   │                  ├─「本次跳过」───────┐│                  ├─409 配额满──> recompressPrompting
   │                  └─「关闭功能」───────┤│                  │                      │
   │                                      ││                  │            ┌─取消────┘
   └───────skipped(idle + 计数)<──────────┘│                  │            │
   │                                       │                  │            v
   │                                       │                  │      recompressing ──成功──> ingesting
   └────────────failed<────────────────────┴──────────────────┴────────────┴─失败──> failed
                  │
                  └─「重试」──> 按 stage 分派（见 §3.1）
                  └─「跳过」──> skipped
```

`recompressing` 成功后回到 `ingesting`，重发同一 `batchSeq`（幂等键未被占用）。

TypeScript 定义（放 `src/lib/memoryExtraction.ts`）：

```ts
export type ExtractionPhase =
  | { phase: "idle" }
  | { phase: "prompting"; range: ExtractionRange; estimate: TokenEstimate }
  | { phase: "extracting"; range: ExtractionRange; abort: AbortController }
  | { phase: "ingesting"; range: ExtractionRange; extracted: string }
  // Entered only from `ingesting` on 409 memory_char_max_reached. `extracted`
  // is carried through untouched: the user already paid for it and it must be
  // re-ingested after the recompression frees quota.
  // See 设计-记忆生命周期与配额.md §3.6.
  | { phase: "recompressPrompting"; range: ExtractionRange; extracted: string;
      batches: MemoryBatch[]; estimate: TokenEstimate }
  | { phase: "recompressing"; range: ExtractionRange; extracted: string;
      batches: MemoryBatch[]; abort: AbortController }
  | { phase: "failed"; range: ExtractionRange;
      stage: "extract" | "ingest" | "recompress"; message: string };
```

**`skipped` 不是 `ExtractionPhase` 的成员。** 时序图里画它是为了表达流转，
实现上它是一个与 phase 正交的独立字段（因为"已跳过"必须在 phase 回到 `idle`
之后继续生效，否则条件 4 一满足就会立刻重新弹窗）：

```ts
export interface ExtractionState {
  phase: ExtractionPhase;
  /** messages.length at the moment the user chose 「本次跳过」; null when not
   *  skipped. Reset rule in §3.3. Scoped to the session — cleared on switch. */
  skippedAtMessageCount: number | null;
}
```

时序图中的 `skipped` 状态 = `{ phase: { phase: "idle" }, skippedAtMessageCount: N }`。

### 3.1 各状态的 UI 与行为

**`prompting`** — 阻塞式 `ConfirmDialog`（`src/components/ConfirmDialog.tsx`，
props `{isOpen, title, message, confirmText, cancelText, destructive, onConfirm, onCancel}`）。

用户的这一轮消息**暂不发送**，等决策。文案见 §5。

三个出口：
- 确认 → `extracting`
- 取消（"本次跳过"）→ `skipped`，记录 `skippedAtMessageCount = messages.length`，
  立即正常发送本轮
- 对话框内第三个动作「不再自动提炼」→ 写 `settings.isMemoryEnabled = false`，
  立即正常发送本轮。**用 `ConfirmDialog` 的 `message` 里嵌一个链接式按钮实现**
  （该组件只有两个按钮，不改组件）

**`extracting`** — 非阻塞。关掉对话框，在输入框上方显示一条细进度条 +
「正在整理早期对话记忆…」+ 取消按钮（触发 `abort`）。用户此时**不能发送新消息**
（输入框禁用），因为提炼结果会改变将要发送的 history。

**`ingesting`** — 同上，文案改「正在保存记忆…」。此阶段不可取消
（网络已发出，取消会留下"提炼花了钱但没存"的最坏结果）。

**`recompressPrompting`** — 阻塞式 `ConfirmDialog`，两个按钮（文案见
`设计-记忆生命周期与配额.md` §3.4 / §3.6）。取消 → 丢弃 `extracted`，
置 `skippedAtMessageCount = messages.length`，`phase` 回 `idle`，立即正常发送本轮。

**`recompressing`** — 与 `extracting` 同款进度条，文案「正在压缩已有记忆…」。
可取消（`abort`）；取消等同上一条的取消出口。

**`failed`** — 输入框上方显示红色条 + 错误摘要 + 「重试」/「跳过本次」两个按钮。
**不自动重试** —— 每次重试都是一次付费模型调用。

「重试」按 `stage` 分派，三者代价不同，必须区分：

| `stage` | 重试动作 | 是否再调模型 |
|---|---|---|
| `extract` | 重新 `runExtraction` | 是 |
| `ingest` | 只重发 `POST /memory/ingest`，用 state 里的 `extracted` | 否 |
| `recompress` | 重新 `GET /memory/batches` + 重新压缩调用 | 是 |

### 3.2 并发保护

- `extractionStateRef` 与 `messagesRef` 同模式（`useRef` + `useState` 双写），
  在发送流程入口读 `ref` 而非 state，避免闭包读到旧值
- 多标签页：不做跨 tab 锁。服务端 `(sessionId, batchSeq)` 幂等（409）已兜住重复写入，
  重复提炼的浪费由用户承担且概率极低（需要两个 tab 开同一会话同时发送）

### 3.3 `skipped` 的重置条件

`skipped` 不是永久的。重置为 `idle` 的条件：**`messages.length` 比
`skippedAtMessageCount` 增加了 ≥ 10**（即又过了约 5 轮）。

理由：用户跳过一次后若继续聊，上下文只会更满，最终必须处理。
但也不能每轮都弹 —— 10 条消息的间隔是"不烦人但不放弃"的折中。

## 4. 提炼调用链路（空洞 K）

### 4.1 定案：新建独立函数，不复用 `fetchChatCompletion`

放 `src/lib/memoryExtraction.ts`：

```ts
/**
 * Run one extraction call against the user's current chat model.
 *
 * Deliberately NOT fetchChatCompletion: that function is built for the
 * conversation turn — it carries tools, streams into a message bubble,
 * applies bypass templates, and reports usage into the chat log. An extraction
 * call must carry none of that. In particular it must NOT advertise tools (an
 * MCP tool call mid-extraction would be meaningless and could be triggered by
 * text inside the material being extracted) and must NOT include
 * <session_rules> or any operator-level content — the material is untrusted
 * derived text and the call needs no operator authority.
 */
export async function runExtraction(args: {
  api: ApiConfig;            // same shape ChatInterface passes to fetchChatCompletion
  material: Message[];
  userName: string;
  charName: string;
  signal: AbortSignal;
}): Promise<{ text: string; usage: { prompt_tokens?: number; completion_tokens?: number } | null }>
```

实现要点：

- **非流式**（`stream: false`）—— 提炼结果不需要逐字展示给用户
- `temperature: 0.3`（低温：这是抽取任务，不是创作）
- `max_tokens`：`Math.min(entry.maxOutput ?? 4096, 4096)`
- 消息结构只有两条：`system`（提炼提示词，见 `设计-提炼提示词与输出规约.md`）+
  `user`（被提炼材料）
- **不带 `tools`**
- 复用现有 provider 适配（`api.ts` 中区分 OpenAI / Anthropic / Gemini 格式的那部分）。
  执行时须核对 `api.ts` 是否有可复用的非流式路径；若只有流式，则用 `stream: false`
  走同一 fetch 但不注册 onChunk

### 4.2 日志

提炼的请求/响应**写入日志面板**，`direction: "request"` / `"response"`，
`content` 分别为 `"Sending memory extraction request"` / `"Received memory extraction result"`，
`meta` 含 `{ model, materialMessageCount, materialChars, usage }`。

**`meta` 中不含被提炼的原文** —— 日志面板可能被用户截图分享，原文是对话隐私。
只记数量。

## 5. token 预估与文案（空洞 L）

### 5.1 预估算法

```ts
/** Rough tokens-per-character for the extraction material. Chinese under most
 *  BPE tokenizers lands near 1 token per 1.5 chars; mixed content skews lower.
 *  Deliberately conservative (over-estimates) so the number shown to the user
 *  is not smaller than what they will be billed for. */
const CHARS_PER_TOKEN = 1.5;

export interface TokenEstimate {
  inputTokens: number;
  outputTokens: number;
  totalTokens: number;
  /** True when the estimate is derived purely from character count because no
   *  usage data was ever reported for this conversation. */
  rough: boolean;
}

export function estimateExtractionCost(
  material: Message[],
  budget: ContextBudget,
): TokenEstimate {
  const chars = material.reduce((n, m) => n + (m.content?.length ?? 0), 0);
  // Prefer a ratio calibrated against this conversation's real usage: if the
  // provider reported prompt_tokens for a known character count, that ratio
  // beats the constant for this user's language mix and tokenizer.
  const inputTokens = Math.ceil(chars / CHARS_PER_TOKEN);
  // Extraction output is a condensed digest — empirically ~8% of input, capped.
  const outputTokens = Math.min(Math.ceil(inputTokens * 0.08), 4096);
  return {
    inputTokens,
    outputTokens,
    totalTokens: inputTokens + outputTokens,
    rough: budget.usedTokens == null,
  };
}
```

> 保留 `rough` 字段但 V1 的 `inputTokens` 一律走字符估算 —— 想用真实比率校准需要
> "字符数 ↔ prompt_tokens" 的配对样本，而 `Message.tokenCount` 记的是**整个请求**的
> prompt_tokens（含 system、世界书），不是该条消息的字符对应值，无法直接反推比率。
> 写明这一点，避免执行期误以为可以校准。

### 5.2 `prompting` 对话框文案（定稿）

```
标题：整理早期对话记忆

当前对话已占用约 {usedTokens} / {contextWindow} tokens（{pct}%），接近模型上限。

可以把最早的 {msgCount} 条消息提炼成事实摘要存入记忆，之后模型按需回忆，
早期逐字原文不再随每轮发送。

· 提炼使用你当前的对话模型「{modelName}」，消耗你自己的 API 额度
· 本次预计消耗约 {totalTokens} tokens（输入 {inputTokens} + 输出 {outputTokens}，为估算值）
· 提炼出的事实摘要以明文存储在服务器上（聊天记录本身仍为端到端加密）

[开始提炼]  [本次跳过]
                          不再自动提炼
```

`{contextWindow}` 若 `source === "fallback"`，值后加「（估算）」。

`{modelName}` 用 model id 原文 —— 用户认得自己填的 id，任何美化映射都可能错。

## 6. 提炼成功后的处理

顺序严格如下（任一步失败的处置见括号）：

1. 解析提炼输出（见 `设计-提炼提示词与输出规约.md`；解析失败 → `failed`，stage `extract`）
2. `POST /memory/ingest`（失败 → `failed`，stage `ingest`；**提炼文本保留在 state 里**，
   重试时不重新调模型，直接重试 ingest —— 这是把用户已付费的成果不浪费掉的关键）

   > 单一例外：HTTP 409 且 `error === "memory_char_max_reached"` **不进 `failed`**，
   > 而是转入 `recompressPrompting`（二次压缩，见 `设计-记忆生命周期与配额.md` §3）。
   > 其余 409（`batch_exists`）视为幂等成功，直接走第 3 步。
3. ingest 成功 → 在 `messages` 上写入记忆分界标记（见 `设计-记忆分界UI与消息模型.md`）
4. `saveSession()` 持久化
5. `extractionState` → `idle`
6. **继续发送用户原本那一轮消息**，此时 `buildRequestMessages` 的 `baseMessages`
   已排除被提炼区间

第 6 步的实现：把发送逻辑抽成一个可在提炼完成后调用的函数，
`prompting` 阶段暂存 `pendingSend`（用户输入 + 附件），提炼结束后用它继续。

## 7. 未登录用户（空洞 R）

**定案：静默跳过，不弹任何提示。**

理由：`isMemoryEnabled` 默认 false，用户要开启这个开关必须先进入账号界面，
而账号界面就是登录入口 —— 能开启开关的用户必然已登录过。
未登录且开关为 true 的唯一路径是"登录态过期"，此时用户已经会在别处看到登录失效提示，
在提炼路径上再弹一个是重复打扰。

对应地，`设计-上下文预算与覆盖入口.md` §4.4 的状态行在未登录时显示：
`持久化记忆需要登录后使用。`

## 8. 验收清单

1. 造 60 条消息的会话，阈值设 40%，确认达阈值时弹窗且**本轮消息尚未发出**
2. 「本次跳过」→ 本轮正常发出；此后 9 条消息内不再弹窗，第 10 条后再弹
3. 「不再自动提炼」→ `settings.isMemoryEnabled` 变 false 并持久化，本轮正常发出
4. `selectExtractionRange` 的边界始终落在 assistant 消息之后（构造 user 结尾的历史验证）
5. 图片气泡与 system 消息不进入提炼材料
6. 提炼中输入框禁用；取消后回到可输入且本轮消息未丢失
7. ingest 失败后点「重试」不产生第二次模型调用（用 network 面板确认只有一次 chat 请求）
8. 提炼成功后，下一轮请求 payload 的 history 中不含被提炼区间的消息
9. 日志面板中提炼记录不含被提炼原文
10. 未保存的草稿会话不触发提炼
11. 把 `memory_char_max` 手工调到刚好装不下下一批，确认 ingest 的 409
    进入 `recompressPrompting` 而非 `failed`；取消后本轮消息仍正常发出
12. 同上但只有 1 个批次 → 弹「无法压缩」单按钮提示，不进 `recompressing`
13. `failed` 且 stage 为 `ingest` 时点「重试」，network 面板确认无新的 chat 请求；
    stage 为 `recompress` 时确认有新的 chat 请求
