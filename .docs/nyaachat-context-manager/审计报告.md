## 1. 现状：完全没有上下文管理

`src/lib/chatPipeline.ts:337` `buildRequestMessages()` 的 history 来源是 `messagesRef.current`（`ChatInterface.tsx:1157`、`:1201`、`:1264`、`:1292`、`:1309` 共 5 处调用），**整段会话原样发送，无截断、无摘要、无预算检查**。

现存的两处裁剪属于副作用，不是设计：

- `chatPipeline.ts:364` 过滤 `m.imageUrl || m.imagePrompt` 的图片气泡（避免 ~2K 字符图片指令污染历史）
- `Message.content` 是 `string`，历史轮次的附件 base64 天然不重发

长对话的终局是**撞上游 400**，而非优雅降级。这是现网真实待修问题。

`ModelEntry.contextWindow`（`types.ts:281`）已存在，由 `modelHealth.ts:326` `inferLimits()` 正则表推导，但**仅在 `LlmProvidersModal.tsx:824` 展示，不参与请求组装**。

## 2. 为何不照搬 Claude Code 的摘要式压缩

Claude Code 能容忍有损摘要，是因为磁盘上有可重读的真相层：文件、git、测试。角色扮演对话**没有外部真相层，对话本身就是成品**。

| 维度 | 编码场景 | 角色扮演 |
|---|---|---|
| 丢失"报错堆栈" | 重跑一次即恢复 | — |
| 丢失"角色第 3 章的承诺"、场景原话、情绪铺垫 | — | **不可恢复**，且用户会理解为"角色崩了" |
| UI 与模型视野 | 历史已滚出屏幕，压缩隐形 | 用户**还能看到** 500 条气泡，模型只看到摘要 → 可见的不一致直接破坏沉浸 |

故本方案走**抽取后入库 + 按需检索**，用近似无损的检索替代有损压缩。基建已齐：KB 服务带 owner 隔离、`buildKbSearchContext`（`chatPipeline.ts:582`）注入链路、世界书 `linkedKbIds` 关联。

## 3. 三条硬约束

### 3.1 聊天记录端到端加密 → 提炼必须在客户端

`src/lib/chatCrypto.ts` 头注释：

> The server holds the key but never sees plaintext — all encrypt/decrypt happens client-side.

主存储是浏览器 IndexedDB（`sessionStorage.ts` → `idbStorage.ts`），云端仅加密备份。服务端解不开密文，**不可能做服务端摘要**。

衍生风险：记忆条目落到 KB 服务必然是**明文**（FTS5 要能搜）。攻破 KB 库虽拿不到逐字对话，但能得到"该账号与哪些角色互动、关系如何演进、有哪些设定"。→ **决策 ① 已拍板：接受，但必须 UI 显著披露 + 默认关闭 + 用户 opt-in。**

### 3.2 入库硬依赖嵌入，检索不依赖

检索侧已有降级 —— `retrieval.js:35`：

```js
if (vecTableExists() && embCfg) { ...dense... }  // catch 后 console.warn 继续
```

失败则只用 FTS5 BM25（`db.js:76` `tokenize='trigram'`，中文子串可用），RRF 单路融合。

入库侧硬失败 —— `ingest.js:52-55`：

```js
if (!embCfg || !embCfg.dim || embCfg.dim <= 0) {
  throw new Error("尚未配置嵌入维度，请先在「嵌入模型设置」中保存并获取维度");
}
```

→ **必要前置改动**：ingest 支持无嵌入配置写入（只写 `chunks` + `chunks_fts`，跳过 vec），否则"免维护、零配置、对所有登录用户开放"无法成立。

### 3.3 getVecDim 跨用户冲突 —— 不阻塞 V1

详见 `../nyaachat-KnowledgeBase-plan/修复计划-getVecDim跨用户向量表冲突.md`。V1 纯稀疏不写 `vec_chunks`，故不被阻塞；V2 补 dense 前必须完成该修复。

## 4. 成本估算

按 `routes/kb.js:13-16` 实际参数（chunk 512 字符 / overlap 50）。中文按 Qwen 分词器约 1 token ≈ 1.5 汉字。**前提：入库的是提炼后的事实条目，非原始对话，压缩率取 5–8%。**

### 4.1 嵌入侧（V2 才发生，V1 为零）

| 环节 | 单次量 |
|---|---|
| 写入（每批次） | ~1.8K tokens（40 轮≈32K 字符 → 提炼 ~2K 字符 → 5 chunk） |
| 查询（每轮触发） | ~250 tokens |

600 轮长对话：写 15 批 ≈ 27K + 查 600 次 ≈ 150K = **~180K tokens**，读写比约 5:1。

按 [cloudprice Qwen3-Embedding-8B 最低 $0.02/1M](https://cloudprice.net/models/alibaba-qwen3-embedding-8b) 与 [SiliconFlow embedding 档](https://www.siliconflow.com/models/embedding) 约 $0.05/1M：

| 口径 | token | 成本 |
|---|---|---|
| 单场 600 轮 | ~180K | $0.004 – 0.009 |
| 重度用户/月 | ~0.8M | $0.016 – 0.04 |
| 100 重度用户/月 | ~80M | $1.6 – 4 |

可忽略。**但存储更值得关注**：4096 维 × 4B = 16KB/chunk，长对话 75 chunk = 1.2MB，1000 场 = 1.2GB 挤在单个 SQLite。V2 应改 1024 维小模型 —— 4096 维是为用户上传专业文档的检索质量选的默认值，对自撰记忆条目属严重过配。

### 4.2 提炼侧（真正的成本，V1 即发生）

| 提炼模型 | 单批（22K 输入） | 重度用户/月（75 批） |
|---|---|---|
| 便宜小模型（[Qwen3-8B $0.06/M](https://custom.typingmind.com/tools/estimate-llm-usage-costs/siliconflow/qwen3-8b)） | ~$0.0015 | ~$0.11 |
| 对话主模型（Opus 级 $15/M） | ~$0.33 | **~$25** |

**约 220 倍差距。** 决策 ③ 选定用对话主模型 —— 成本落在用户自己的 key 上，逻辑自洽，用户对自己消费有完整知情权。但**必须配套**（写入 SSOT 不变量，非建议）：

- 提炼触发时给出可见提示 + token 预估，**绝不静默发起大额请求**
- 提供"本次跳过"与"关闭自动提炼"的即时出口
- 用户若在跑本地小模型，UI 需说明提炼质量是整个记忆系统的质量天花板

## 5. 信任边界审计

对标 `.docs/llm-chat-prompt-architecture-standard.md`。

记忆条目**派生自历史**，而历史中的 assistant 输出可能已吸收注入内容（检索块、MCP 返回、用户导入的角色卡文本）。若把它放进 `<session_rules>`（operator 级授权位），构成**从不可信历史提权到 operator 邻位**，违反标准 §7 不变量 2。

**结论：记忆块必须以数据身份注入**，与 `buildKbSearchContext` 同级 —— 作为 volatile content part 挂在最新 user 消息尾部，位于缓存断点之后。既有 recency，又无指令效力，且不污染前缀缓存。

标签取舍：`SESSION_PROTOCOL_ANCHOR`（`chatPipeline.ts:303-306`）目前只声明 `<session_rules>` 与 `<search_context>` 两类。新增 `<memory_context>` 需改锚点文本，而锚点是静态前缀固定组成（标准 §7 不变量 5）→ **所有用户所有对话的前缀缓存一次性全失效**。一次性成本，接受；但应与其他锚点改动合并发布。

选定 `<memory_context>` 而非复用 `<search_context>`：语义清晰值这一次 miss，且二者信任级虽同，来源与用途不同，混用会给后续审计留坑。

提炼提示词自身也须声明：被提炼材料中任何指令性文字仅为素材内容，不得执行。提炼调用不携带 `<session_rules>` 等 operator 级内容。

删除端点须**双守卫**：`session_id` 匹配 **且** kb 属调用者 **且** `kind='memory'`，防止构造 sessionId 删他人记忆或用户知识库。

## 6. 决策记录

| # | 决策点 | 结论 |
|---|---|---|
| ① | 记忆明文存服务端 | **接受**，但 UI 显著披露 + 默认关闭 + 用户 opt-in |
| ② | 嵌入策略 | **V1 纯稀疏**（FTS5 BM25 单路）；dense 留 V2 |
| ③ | 提炼模型 | **用户当前对话主模型**；须可见提示 + token 预估 + 可跳过 |
| ④ | 跨对话记忆 | **严格按 session 隔离**，不做跨对话召回 |
| ⑤ | 记忆库归属 | `kind='memory'` 特殊库：不列出、不占 `kb_max`、不可手动关联 |
| ⑥ | 批次粒度 | 一个 document = 一个提炼批次，**append-only**，绝不重嵌旧批次（否则成本随长度平方增长） |
| ⑦ | 孤儿回收 | 显式删除为主 + TTL 心跳兜底；**禁止全量对账**（空 IndexedDB 新设备会清空全部记忆） |
| ⑧ | 嵌入配置入口 | 账号界面「持久化记忆」行加图标按钮，复用知识库那份配置；V1 记忆侧不消费 |

### 关于 ⑧ 的内在张力（须在 UI 文案上处理）

决策 ② 定纯稀疏，决策 ⑧ 要求放嵌入配置按钮 —— 二者在 V1 共存但不联动：按钮打开的是与知识库共用的配置面板，保存/探测维度均正常工作，但**记忆检索 V1 不消费它**，是为 V2 预留的入口。

UI 文案须避免让用户以为"配了就会更准"。建议在该按钮 tooltip 或配置面板内注明作用范围。

## 7. 风险与遗留

| 风险 | 缓解 |
|---|---|
| `inferLimits()` 是 model id 正则匹配，自建 provider / 反代 / ollama 大概率落兜底或 `undefined`；分母错则机制失效 | 提供手动覆盖 `contextWindow` 入口；未知时用保守常量并标注为估算 |
| 提炼质量决定整个系统上限，而模型由用户选 | UI 说明；提炼输出走结构化 schema 降低对模型能力的依赖 |
| 提炼后 UI 气泡与模型视野不一致 | UI 加可见"记忆分界"标记，让用户知道模型看不到线以上的逐字内容 |
| 锚点变更导致全量缓存失效 | 与其他锚点改动合并发布，择时 |
| 记忆明文与聊天密文的隐私落差 | 默认关闭 + 开启前二次确认披露 |
