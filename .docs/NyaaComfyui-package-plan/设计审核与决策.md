# NyaaComfyui图包 — 设计审核与关键决策

> 本文档是对 `NyaaComfyui图包-初始设计.md` 的设计审核报告 + 关键决策记录。
> 决策已于 2026-07-06 与用户拍板确认，作为 `开发计划-SSOT.md` 的输入。

## 一、需求摘要

为 NyaaChat 增加付费项目 **NyaaComfyui图包**：用户使用生图供应商 **NyaaComfyUI 节点**（`comfyui-fixed` / `comfyui-custom`）生成图片时消耗的「可用次数额度」。

- 需登录后方可使用 ComfyUI 节点生图。
- 初始免费额度 **10 次**；扩容价 **5 猫粮 / +30 次**。
- 每次生成**成功**（返回图片）剩余次数 **−1**；**失败不扣**。
- 剩余次数 ≤ 0 时禁止使用 ComfyUI 节点生图，引导扩容。
- 双侧（NyaaChat + NyaaAcount）都要注册该付费事件。

## 二、架构分析

### 2.1 与现有 `kb_max` 扩容机制的关系

本功能与「知识库栈扩容（kb_max）」高度同构，**复用同一套跨项目付费骨架**：

```
[前端] 点扩容 → ConfirmDialog → sharedAccountApi
   → POST /api/shared/account/*  (Bearer session token)
[nginx] location /api/shared/ → nyaachat-shared:5107（去前缀）
[shared-server] account.js 端点（requireAuth）
   ① 本地额度前置校验
   ② nyaacount.consume(uid, action, cost, ref)  ← NyaaAcount 权威定价
   ③ 扣费成功 → 本地写额度；本地写失败 → rechargeBalance 退款补偿
[nyaacount-client] Nyaa-HMAC-XOR-V1 加密 body + Bearer <project token>
[NyaaAcount] /project/consume 按 pricing.json[nyaachat][action].amount 扣猫粮
```

### 2.2 与 `kb_max` 的**关键差异**（务必区分）

| 维度 | kb_max（知识库栈） | comfyui图包（本功能） |
|------|-------------------|----------------------|
| 语义 | **上限（ceiling）** | **可消耗余额（consumable balance）** |
| 变化方式 | 只增（扩容 +2），到硬顶 50 | 扩容 **+30**；每次生成成功 **−1** |
| 默认值 | 3 | **10（免费额度）** |
| 消耗动作 | 无（仅上限判定） | 每次生成成功后本地 −1 |
| DB 字段命名 | `kb_max` | `comfyui_pack_remaining`（余额，非 max） |

> 因此本功能除「扩容端点」外，还需一个**「消耗（−1）端点」**与一个**「读取剩余」端点**，这是 kb_max 没有的。

### 2.3 额度存储位置（决策一）

**决策：存 NyaaChat shared-server（对标 kb_max，业务额度存接入方）。**

NyaaAcount 只托管猫粮余额（`users.balance`）与消费流水（`recharge_log`），对「剩余次数」等业务语义无感知。剩余次数落在 NyaaChat 的 `shared-server` 共享数据库 `users` 表新增列。

### 2.4 扣减时机（决策二）

**决策：后端扣减。** 生图成功（前端确认拿到图）后，由前端调用 shared-server 的**消耗端点**，服务端**原子扣减**（`SET comfyui_pack_remaining = comfyui_pack_remaining - 1 WHERE ... AND comfyui_pack_remaining > 0`）并返回新剩余值。防止前端绕过；失败/中止不调用消耗端点即不扣。

生成**前**的 `> 0` 预检也以服务端读取值为准（读取端点或 profile），前端 gate 仅为体验优化，最终判定在服务端消耗端点的 `WHERE ... > 0` 守卫。

### 2.5 登录界面触发（决策三）

**决策：复用现有 `UserAccountModal`。** ComfyUI 节点启用开关、节点内生图入口、对话气泡生图入口在未登录时，均打开现成的 `UserAccountModal`（内含登录表单，自持会话状态），登录后返回。

## 三、技术选型

- 后端：沿用 `shared-server`（Express + better-sqlite3），`account.js` 加端点，`db.js` 加迁移列。
- 通信：复用 `nyaacount-client.js` 的 `consume` / `rechargeBalance`，**无需改动**该文件。
- 前端数据层：扩展 `sharedAccountApi.ts`（`AccountProfile` 加字段 + 新增 3 个 API 函数）。
- 前端 UI：`UserAccountModal.tsx`（共享账号条目）+ `ImageProvidersModal.tsx`（节点内「图包剩余」+ 扩容 + 登录 gate）+ `ChatInterface.tsx`（生图链路 gate + 扣减）。
- nginx：新端点挂 `/api/shared/account/*` 前缀，**走现成规则，无需改 nginx.conf**（比 kb 的跨服务劫持更简单）。
- NyaaAcount：`pricing.json` + `events.json` 登记新 action + 环境变量 token/key（该项目已注册 `nyaachat` project，**token/key 复用现有 nyaachat 项目凭证**，仅加 action）。

## 四、关键决策点（已拍板）

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| D1 | 剩余次数额度存哪侧 | **存 NyaaAcount（对标 kb_max）** → 实为存**接入方 shared-server**（业务额度惯例落接入方，见 §2.3 澄清） | 与 kb_max 完全同构；NyaaAcount 只管猫粮 |
| D2 | 生图成功 −1 的扣减位置 | **后端扣减** | 防前端绕过；`WHERE remaining>0` 原子守卫 |
| D3 | 未登录时登录界面 | **复用现有 `UserAccountModal`** | 改动最小，体验统一 |

> 用户答复原文对 D1 选择「存 NyaaAcount（对标kb_max）」。**澄清**：kb_max 的实际实现是「业务额度存接入方 shared-server，猫粮扣费走 NyaaAcount」。本功能**完全照此对标**——剩余次数落在 shared-server `users` 表，扣猫粮走 NyaaAcount `consume`。两位调研 agent 均确认此为平台的既定惯例。

## 五、计费模型确认

采用「**次数包（买断额度）**」模型：
- **扩容/购买**：走 `consume(uid, "expand_comfyui_pack", 5, ref)` → NyaaAcount 扣 5 猫粮 → shared-server 本地 `comfyui_pack_remaining += 30`。
- **每次生成消耗**：仅在 shared-server 本地 `comfyui_pack_remaining -= 1`，**不碰 NyaaAcount**（不是按次扣猫粮）。

## 六、风险识别

| 风险 | 缓解 |
|------|------|
| 前端绕过扣减 | 消耗端点服务端 `WHERE remaining>0` 原子守卫；额度以服务端为准 |
| 扣费成功但本地写失败 | 沿用 kb_max 的 `rechargeBalance` 退款补偿模式 |
| 并发重复扣减 | 生图受 `isLoading` 串行锁保护；消耗端点为单条原子 UPDATE |
| 剩余次数与 profile 展示不同步 | 消耗/扩容端点返回最新剩余值，前端即时刷新；节点 UI 提供独立读取端点 |
| pricing.json 未登记新 action | consume 返回 `unknown_action` → 部署前先在 NyaaAcount 登记并重启 |
| ComfyUI 节点「测试生成」是否扣次数 | **不扣**（测试生成是设置页调试，非对话产出）——见 SSOT §校验 |
