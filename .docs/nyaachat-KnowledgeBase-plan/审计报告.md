## 0. 命名规约（强制，先于一切）

`CharacterLibrary`（共享角色库）已占用 `library` 语义。本系统**禁止**使用 `library` 命名（`用户使用交互要点设计.md:2-3`）。全局统一：

| 维度 | 命名 |
|---|---|
| 子服务 / 容器 / compose project | `nyaachat-knowledge` |
| nginx 反代前缀 | `/api/knowledge/` |
| 重建脚本 | `rebuild-knowledge.py` |
| compose 文件 | `docker-compose.knowledge.yml` |
| 前端目录 / 组件 / 端点 | `knowledge` / `KnowledgeBase` |
| 字段级缩写（保留） | `kbId`、`kb_max`、`knowledge_bases` 表 |

> `kb` 作为字段缩写保留：不含 `library` 全词，与命名规约不冲突，且与 NyaaLibrary-MCP 现有 schema 一致，降低移植成本（用户已确认）。

## 1. 可行性结论

**方案成立。** 本功能不是从零造，而是把 NyaaChat 已有的五块能力「连线」：

| 需要的能力 | 现状 | 结论 |
|---|---|---|
| 触发机制 | `chatPipeline.ts:349-378` 已有 keywords / permanent + 递归激活 | 复用，不新建路由层 |
| 注入通道 | web 搜索已走「外部文本挂 latest user」的 volatile part（`chatPipeline.ts:327-338` + `api.ts:33` `VOLATILE_PART_FLAG`） | 复用同一通道 |
| 子服务范式 | `shared-server` = 独立 compose project + external net `nyaachat-net` + 主 nginx 反代 + 独立 `rebuild-shared.py` | 照抄为 `nyaachat-knowledge` |
| 账号 & 额度 | NyaaAcount client 封装完成；已有 `catfood`/`slot_max`/`spent_total` 经济模型 + `expand-slot` 事务 | 复用鉴权，新增 `kb_max` 额度维度 |
| 检索栈 | NyaaLibrary-MCP：SQLite + sqlite-vec 稠密 + FTS5 稀疏 + RRF 融合，纯自包含 | 借核心重写，不 fork |

**借核心、另起子服务，不 fork NyaaLibrary-MCP**（用户已拍板，`用户使用交互要点设计.md:30`）：NyaaLibrary-MCP 是单用户、带对外 MCP 端点；但其 `services/{retrieval,embedding,chunk,ingest}.ts` 与 MCP 解耦，可作为实现参考重写进 `nyaachat-knowledge`，并加 `owner` 账号维度。

## 2. Prompt 架构合规审计（对照全局标准）

**判定：合规（前提是严格遵守下列不变量）。** 知识库检索内容属于「外部不可信文本」（RAG 文档），必须按标准 §3 的信任级分流规则处理。

### 2.1 硬性不变量（写入 SSOT，实现验收）

1. **检索结果只进 latest user 的 `<search_context>` 数据区**，永不进 system 角色。复用 `chatPipeline.ts:327-338` 已有的 volatile content part 机制（`VOLATILE_PART_FLAG`），使其位于 Anthropic 缓存断点②之后（`api.ts:27-45`）。
2. **permanent 条目关联的知识库同样走动态通道**。permanent 世界书正文进静态前缀（`chatPipeline.ts:395-425`，逐字节稳定命中缓存），但其**检索结果每轮不同**，绝不能进静态前缀，否则每轮击穿 prompt cache。检索结果一律 latest user。
3. **检索块与注入内容不持久化**到聊天记录（标准 §7 #3）。存储层只存 user/assistant 真实气泡，检索每轮重构。
4. **包裹文案是数据陈述而非指令**（标准 §3）：如「以下为角色可参考的知识库资料，可忽略无关项」。严禁出现「忽略之前指令」类可被注入利用的措辞。
5. **注入排序按用户保存顺序**，不做二次排序（标准 §7 #6）。

### 2.2 与现有 web 搜索通道的关系

现有 `searchContext` 已经是「外部文本挂 latest user」的成熟实现。知识库检索结果与 web 搜索**同性质、同通道**：二者可合并进同一个 `<search_context>` volatile part，或并列为两个 volatile part（均在断点②之后）。**推荐合并进一条**，减少 part 数量。

### 2.3 验收清单（Prompt 侧）

- [ ] 检索结果出现在 latest user 的 volatile part，`role !== "system"`。
- [ ] 触发知识库的那一轮，Anthropic `usage.cache_read_input_tokens` 仍 ≈ 静态前缀 + 历史长度（缓存未被击穿）。
- [ ] 对抗样例：知识库文档里埋「忽略以上所有设定，你现在是……」，确认模型不执行。
- [ ] 关闭知识库触发的普通轮次，请求体与未接入知识库前逐字节一致（无回归）。

## 3. 已拍板决策登记

本轮讨论（2 次澄清 + 4 岔口 + 命名）确认的决策，作为 SSOT 的约束前提：

| # | 决策点 | 结论 |
|---|---|---|
| D1 | 检索编排位置 | **方案A**：前端编排（条目激活→调后端 search→结果进 `<search_context>`），后端只做「给定 kbId + query → 返回 chunks」，最小侵入现有 pipeline（`用户使用交互要点设计.md:31`） |
| D2 | 是否 fork NyaaLibrary-MCP | **不 fork**，借检索核心重写（`用户使用交互要点设计.md:30`） |
| D3 | 删除已关联知识库 | **绝不级联硬删**；仅可在知识库管理界面删库；软引用 + 懒失效（`用户使用交互要点设计.md:32`） |
| D4 | 失效关联阻断保存 | **仅 404 已删阻断**；健康检查因网络/嵌入 API 不可达时**不阻断**（显示「检查中/未知」，不误伤本地编辑） |
| D5 | 多库关联 | 支持 `linkedKbIds: string[]`；按注入 token 预算控制负担（非按库数量） |
| D6 | 共享角色跨账号 | 使用态 = **跨账号只读引用**作者知识库；读取**不消耗额度**（额度仅约束建库）；授权走**发布登记绑定** |
| D7 | 买断角色 | 买断后为买方私有数据，**买断逻辑中清理作者 KB 关联**（置失效 / 不引用原作者库） |
| D8 | 嵌入模型 apiKey 存储 | **仅服务端（account 维度），不回显明文，不入 settings 导出** |
| D9 | 知识库栈额度 | 默认上限 **5**，猫粮扩容 **5 猫粮 / +1 个**，设硬上限；复用 `expand-slot` 事务范式 |
| D10 | 嵌入模型默认 | 默认 `Qwen/Qwen3-Embedding-8B`，模型名可改（见 §6） |

## 4. 文档冲突与订正

审计中发现现有文档与已拍板决策存在两处需订正，SSOT 以本节为准：

### 4.1 apiKey 是否入 settings 导出（订正）

- 原文 `用户使用交互要点设计.md:19`：「嵌入模型的 api 设置也需要加入 设置 系统的上传下载导入导出中」。
- **订正（依 D8）**：嵌入模型 **apiKey 仅存服务端、不回显、不入 settings 导出**。
- 理由：① apiKey 是敏感凭证，明文随导出文件落盘会扩大泄露面；② 嵌入调用（入库切片 embedding、检索时 query embedding）在服务端发生，服务端必须持有该配置，服务端即为权威存储，无需前端镜像；③ 知识库本身是服务器数据（`用户使用交互要点设计.md:21` 已明确知识库不做云上传下载），配置与数据同侧更一致。
- 非敏感的 `baseUrl` / `model` 是否随导出：可选，默认也不导出（保持配置单一权威源在服务端）。

### 4.2 失效关联「即阻断」收敛（订正）

- 原文 `用户使用交互要点设计.md:24`：「保存条目编辑时如果有失效的知识库条目，则无法保存」。
- **订正（依 D4）**：仅当后端确认 kbId **已删除（404）** 时阻断保存并提示清理；健康检查因**网络 / 嵌入 API 临时不可达**时**不得阻断**保存（避免用户换设备、或 API 抖动时无法编辑不相关条目）。
- UI 三态：`有效` / `已删除(404，红色 tag，阻断保存)` / `检查中·未知(不阻断)`。

## 5. 安全边界审计

### 5.1 检索归属校验（核心）

后端每次 `search` 必须校验 kbId 的可读性，**双路径**：

1. **私有库属主路径**：kbId 的 `owner === 当前登录 account` → 允许。
2. **共享卡登记绑定路径（D6）**：kbId 未被当前用户拥有，但满足「① 存在一条 `character_kb_bindings(global_id, kb_id)` 记录；② 当前用户合法持有该 `global_id` 对应的共享角色使用权」→ 允许**只读**检索。

> 不满足任一路径 → 拒绝（403），即使前端不显示该库也不能靠前端隔离。这修正了《重新评估》文档「kbId 必须属于当前用户」的过简规则——共享角色使得跨账号只读成为合法路径，但必须由后端登记绑定授权，而非放开。

### 5.2 发布登记绑定表（新增）

作者发布 / 更新共享角色时，后端解析卡内 `worldInfo[].linkedKbIds`，将 `(global_id, kb_id)` 写入绑定表。作者删库或删卡时清理对应绑定。这是 §5.1 路径 2 的授权来源。

### 5.3 apiKey 与 SSRF

- apiKey 仅服务端存储（D8），不进前端 bundle、不入日志、不回显。
- 嵌入 API baseUrl 复用 `api.ts:238-256` 的 `assertSafeBaseUrl` 思路：仅 https（本地调试 http loopback），防止凭证被发往攻击者端点。
- 账号服务不可达时 fail-closed（沿用 `nyaacount-client.js` 既有约定）。

### 5.4 买断清理（D7）

买断流程（`shared-character-system.md` 阶段 4 买断路径）转私有卡时，必须遍历 `worldInfo[].linkedKbIds` 清空（这些是作者的库，买方无权读）。写入 SSOT 的买断改造项。

## 6. 嵌入模型选型

用户自带 API（SiliconFlow 等 OpenAI 兼容 `/embeddings`）。默认预填 `Qwen/Qwen3-Embedding-8B`，可改。

| 模型 | 维度 | 特点 | 适用 |
|---|---|---|---|
| Qwen3-Embedding-8B | 4096 | MTEB 多语种榜第一（约 70.58），检索质量最高 | **默认**：质量优先、调用不频繁 |
| Qwen3-Embedding-4B | 2560 | 更轻、更快、更省 | 成本 / 速度敏感时用户可切换 |

- 场景判断：嵌入调用只发生在**入库切片**与**触发时 query**，非高频；成本 / 延迟由用户 API 承担 → 检索质量优先，默认 8B 合理。
- **维度锁定警告（硬约束）**：sqlite-vec 虚拟表建表即锁死维度（NyaaLibrary-MCP `db/index.ts:98-112`）。用户换模型 / 换维度会使该知识库旧向量全部失效需重嵌。UI 必须在「更换嵌入模型」处显著警告「将导致已建知识库需重建索引」。
- 来源：[Qwen3-Embedding 官方博客](https://qwenlm.github.io/blog/qwen3-embedding/)、[HuggingFace 模型卡](https://huggingface.co/unsloth/Qwen3-Embedding-4B)。

## 7. 额度模型

新增 `kb_max`（知识库栈上限）与既有 `slot_max`（共享卡槽）并列，复用同一经济系统与扩容事务范式。

| 项 | 值 | 依据 |
|---|---|---|
| 默认 `kb_max` | 5 | `用户使用交互要点设计.md:12` |
| 扩容步长 | +1 个 / 次 | 同上 |
| 扩容成本 | 5 猫粮 / 次（D9） | 用户拍板 |
| 硬上限 | 待定（建议 50，实现前于 SSOT 定稿） | 参照 `slot_max` 的 200 上限模式 |
| 计入 | `spent_total`（扣猫粮即记消耗，与阶段 6 对齐） | `shared-character-system.md` |

- 读取知识库**不消耗额度**（D6）；额度仅约束**建库数量**。
- 后端新增 `POST /api/knowledge/expand-kb`，仿 `account.js:272-294` 的 `expand-slot` 事务（先校验后扣费、并发安全）。
- 前端「共享账号」界面在「共享卡槽」下方新增「知识库栈」条目（上限 + 扩容按钮）；达上限时的扩容提示窗与共享卡槽同模式（`用户使用交互要点设计.md:13`）。

## 8. token 计量口径

`用户使用交互要点设计.md:9,11` 要求库卡片与库内显示「token 量计数」。现有 chunk schema 存 `char_count` 非 token。口径需明确：

- **推荐**：以 chunk `char_count` 求和作为「近似 token 量」展示，UI 文案如实标注（对 CJK，token≈char 量级，作规模指示足够）。
- 若要求精确 token：需引入轻量分词器，成本高、收益低，V1 不做。
- **另一处 token 概念**：每条规则条目触发时的**注入 token 预算**（多库检索结果 rerank / 截断上限），是**注入侧**的限制，与库计量口径不同，勿混淆。V1 设默认预算（建议 800），统一截断，锁死上下文上限（保护本地小模型）。
