# 修复计划：FTS5 稀疏检索静默失效

状态：**已修复并验证（25/25）**，已提交 `6a45cb3`，已部署（镜像 `ab46f3a`，2026-07-27）。
关联：`修复计划-getVecDim跨用户向量表冲突.md`（同批发现，互相独立）

## 缺陷

`nyaachat-knowledge/src/services/retrieval.js` 的稀疏分支有两个独立缺陷，
合并后的效果是：**混合检索在很多常见输入下静默退化为纯 dense，无日志、无用户可见信号。**

### 缺陷 1：FTS5 特殊字符导致 MATCH 抛错，被空 catch 吞掉

原代码把用户 query 原文直接交给 `MATCH`，FTS5 会把它当**查询表达式**解析。
query 含任何保留字符（`#` `\` `"` `*` `:` `-` `(` `)` `` ` `` 等）就抛解析错误：

```js
} catch {
  // FTS MATCH can throw on certain query syntax; ignore and rely on dense.
}
```

catch 为空 → `sparseRanks` 保持空 → RRF 只有 dense 一路参与。

实测（真库副本）：

| query | 旧行为 |
|---|---|
| `* \# 《守望先锋》"` | THREW `unknown special query: \#` |
| `克苏鲁 # 神话` | THREW |
| `foo:bar` | THREW |
| `C:\Users\test\path` | THREW |
| `(paren) [bracket] {brace}` | THREW |
| `**加粗** \`code\`` | THREW |

Markdown、代码、路径、引号在聊天文本里极常见，命中率很高。

### 缺陷 2（更严重）：CJK 自然语句在稀疏路径上召回为 0

中文没有空格分隔，**整句会作为单一 FTS5 phrase**，只有该句原文连续出现在正文里才匹配 —— 实际几乎永不成立。

实测（真库副本，全局无 kb 过滤）：

| query | 旧行为命中 |
|---|---|
| `守望先锋的英雄有哪些` | **0** |
| `我想查克苏鲁神话的调查员规则` | **0** |
| `调查员规则` | **0** |
| `克苏鲁神话` | 10 |

即：稀疏检索对中文自然语句**本来就基本无效**，只是一直被 dense 兜住，看不出来。

### 为什么必须在记忆系统前修

SSOT 决策 ②（纯稀疏）意味着记忆系统 V1 **没有 dense 兜底**，
且记忆内容以中文为主。这两个缺陷不修，记忆召回率接近 0，且不报错。

## 排除项：发现 B 是测试假象

前一轮交接文档记的「trigram 可能不认 CJK」**已确证为假**：

```
"克苏鲁"  → FTS 123 行
LIKE '%克苏鲁%' → 123 行   （完全吻合）
```

trigram 对 CJK 正常。之前的 0 行是 probe 脚本的 kb_id 用 `LIMIT 1` 随手取到了
不含该词的知识库所致。**SSOT 决策 ② 不受影响，无需修订。**

## 修复设计

只改 `src/services/retrieval.js`，单文件。

### 1. 永不把原文交给解析器

按空白 + FTS5 保留字符切成 fragment，每个 fragment 重新发射为**带引号的 phrase**
（phrase 内唯一有意义的字符是 `"`，用双写转义）。

选择"切分"而非"整体转义"：trigram 索引存的是正文的重叠 3 字序列，
去掉标点后的片段只要在正文中连续出现就仍能命中，语义损失可接受。

### 2. 丢弃 <3 字符片段

trigram 无法匹配短于 3 字符的词（产生不出 trigram）。
若保留，AND 查询会因为一个 `的` / `AI` 直接全表不命中。
全部片段都被丢弃时跳过稀疏并打日志。

### 3. 两趟：strict AND → loose OR

| 趟 | term 集 | 目的 |
|---|---|---|
| AND | `strict` = fragment 原样 | 与旧实现语义一致，**已能工作的 query 排序不变** |
| OR | `loose` = 长 CJK 串切成窗口 + 保留拉丁部分 | 仅在 AND 零命中时补召回 |

AND 优先保证这是**纯增量**修复：原本有结果的 query 走 AND，结果与修复前相同；
原本 0 结果的才落到 OR。

### 4. CJK 长串切窗口（缺陷 2 的解法）

长度 ≥4 的 CJK 串按 **窗口 3 / 步长 2** 切重叠窗口，仅进 `loose`（OR 趟）。

步长 2 而非 3：让跨切口的词仍可达。
只进 OR：若要求全部窗口同时命中（AND），会比原来的整句 phrase 更严格。

```
守望先锋的英雄 → ["守望先", "先锋的", "的英雄"]
```

### 5. 上限

- `MAX_TERMS = 24` —— 防止长粘贴消息炸成巨型布尔表达式，按首现顺序保留（偏向 query 头部，通常是意图所在）
- `MAX_WINDOWS_PER_RUN = 8` —— 单个 CJK 长串的窗口数上限

### 6. catch 不再静默

保留 catch 作为兜底（理论上已不可达，因为每个 term 都是带引号 phrase），
但必须 `console.warn`。原始缺陷的根因就是静默失败。

## 验证结果（真库副本，25/25 通过）

- **8 个原本抛错的 query 全部不再抛错**
- **CJK 自然语句召回从 0 变为有结果**：

| query | 旧 | 新 |
|---|---|---|
| `守望先锋的英雄有哪些` | 0 | 50（via OR） |
| `我想查克苏鲁神话的调查员规则` | 0 | 16（via OR） |
| `调查员规则` | 0 | 5（via OR） |
| `克苏鲁神话` | 10 | 10（via **AND**，未退化） |

最后一行是关键回归项：原本能工作的 query 仍走 AND，结果数不变。

- 单元项：引号转义、短片段丢弃、去重、term 上限、窗口重叠与覆盖串尾、
  窗口数上限、CJK+拉丁混排保留拉丁部分（`克苏鲁神话COC7版` → `coc7版`）、
  短 CJK 串(<4) 不切窗口
- `grep` 确认全仓只有一处 FTS `MATCH` 调用点，无遗漏
