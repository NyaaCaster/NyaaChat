## 1. 架构与链路分析

在 NyaaChat 中引入符合 SillyTavern 规范的多开场白（Alternate Greetings）功能，需要打通 **数据层（导入/导出/类型定义）**、**角色编辑层（UI 管理与排序）** 和 **对话运行层（开场白构建、翻页切换、纯净度判断、宏展开与上下文注入）** 全链路。

```
[角色卡 JSON / PNG (ST Spec v2/v3)]
      │
      ▼ (sillyTavernImport.ts)
[Character.alternateGreetings: string[]]
      │
      ├─────────────────────────────────────────────┐
      ▼ (CharacterEditModal.tsx)                    ▼ (ChatInterface.tsx)
[管理弹窗: 列表增删改排序]                     [初始化生成第一条 Message]
      │                                             │
      ▼ (sillyTavernExport.ts)                      ▼
[导出 ST 规范角色卡]                    [Message.swipes: string[]]
                                        [Message.swipeId: number]
                                                    │
                                                    ▼ (MessageItem.tsx)
                                        [首条消息翻页器: < 1 / 3 >]
                                                    │ 切换
                                                    ▼
                                        [切换 content，重算 {{user}} 等宏]
                                        [仅纯净状态允许翻页 (未输入后续消息)]
```

## 2. 关键技术对标与决策点（待用户确认/拍板）

### 决策点 1：消息模型的存储结构与向下兼容（P1）
* **现状分析**：
  * NyaaChat 当前 `Message`（`src/types.ts`）结构为单文本：`content: string`。
  * 历史上在插件系统 MVU 规范中，`Message.variables` 为按 swipe 索引的数组（目前为 `variables[0]` 单元素）。
  * SillyTavern 会话数据中，开场白消息包含 `swipes: string[]`（包含 `first_mes` 与所有 `alternate_greetings`）以及当前选中的 `swipe_id: number`。
* **推荐方案（推荐）**：
  * 在 `Message` 接口中扩展可选字段：
    ```typescript
    export interface Message {
      // ... 既有字段
      /** 开场白备选分支列表（首条消息生效）。包含主开场白与额外问候语。 */
      swipes?: string[];
      /** 当前选中的开局索引（0-based，默认为 0）。 */
      swipeId?: number;
    }
    ```
  * **持久化安全性**：IndexedDB 存储的会话 `ChatSession` 天然支持 JSON 序列化，且不会被 `RETIRED_SESSION_KEYS` 清理（`sessionStorage.ts` 目前只剥离 session 级的 `metadata`，消息级属性完全安全）。
  * **旧会话兼容**：没有 `swipes` 的历史开场白，`swipes` 为空或 undefined，UI 自动回退为普通消息，完全平滑。

---

### 决策点 2：开场白切换条件与「纯净状态（Pristine）」定义（P2）
* **现状与 ST 对标**：
  * 在 ST 中，开局翻页受 `isPristine`（纯净状态）保护：一旦对话产生了用户回复（或后续对话），开场白立即被固定为常规对话历史，不可再随意翻页替换。
  * 用户如果在后续对话中翻页开场白，会导致整个上下文前言不搭后语、甚至破坏已有剧情一致性。
* **推荐方案（推荐）**：
  * **翻页器显示门禁**：仅在满足以下全部条件时允许翻页开场白：
    1. 当前消息为**首条消息**（`mesid === 0` 或首个非系统角色消息）。
    2. 当前会话处于**纯净状态**：`messages.length === 1`（即仅有且只有这一条开场白，用户尚未输入任何对话）。
    3. `message.swipes` 存在且数量大于 1。
  * 一旦用户发送了第一条对话，开场白翻页控件自动隐藏，当前选中的开场文本永久固定在上下文中。

---

### 决策点 3：开场白翻页时的宏替换与响应式（P3）
* **现状分析**：
  * ST 的角色卡开场白中常常包含 `{{user}}`, `{{char}}` 等动态宏。
  * 角色卡在导入时，`firstMes` 和 `alternateGreetings` 存储的是**未求值的原始文本**。
  * NyaaChat 在 `ChatInterface.tsx` 的 `buildFirstMes` 中将开场白文本放入 `Message.content`。
* **推荐方案（推荐）**：
  * `swipes` 中持久化存储**原始模板文本**（保留 `{{user}}` 等标记），切换翻页时动态调用 NyaaChat 既有的 `substituteParams` 或渲染管道计算出展示文本，并写入 `message.content`。
  * 或者，在创建会话时将 `swipes` 各项统一预展开为对应当前用户的文本，切换时直接将 `swipes[newId]` 赋予 `message.content`。
  * **推荐**：在首条消息中 `swipes` 保存经由当前用户名展开后的文本，保证离线保存与查看的一致性；若角色/用户别名切换时重新同步。

---

### 决策点 4：角色编辑界面的交互方式（P4）
* **UI 考量**：
  * 在 `CharacterEditModal.tsx`（角色卡编辑抽屉/弹窗）的「首条消息（开场白）」输入框旁边，参考 ST 增加「其它开场」按钮。
  * 点击打开二级弹窗（`AlternateGreetingsModal`）：
    1. 列表展示当前已配置的所有额外问候语，显示序号及简要预览/完整编辑。
    2. 支持「新增问候语」、「编辑正文」、「删除」、「上移/下移排序」。
    3. 确认后同步回 `Character.alternateGreetings` 并在编辑弹窗显示计数 Badge（例如 `额外开场: 2条`）。
  * 保持既有 NyaaChat 的 UI 风格（Tailwind + Lucide 图标 + 深色模式兼容）。

---

### 决策点 5：角色卡导入与导出规范（ST Spec v2 / v3 对齐）（P5）
* **导入（`sillyTavernImport.ts`）**：
  * 解析 `data.alternate_greetings`（以及根层 `alternate_greetings` 兼容）为 `string[]`。
  * 清理空字符串和无意义空项，赋给 `Character.alternateGreetings`。
* **导出（`sillyTavernExport.ts`）**：
  * 在导出的 ST v2/v3 JSON 及 PNG 元数据中，将 `character.alternateGreetings` 写入 `data.alternate_greetings` 及根目录兼容层。

## 3. 潜在风险与跨模块耦合自查

1. **会话导出/备份一致性**：
   * `ChatHistoryModal.tsx` 中的 JSON 导出、云端同步如果导出 `Message`，新加的 `swipes` 与 `swipeId` 为可选字段，完全向下兼容。
2. **插件系统 / MVU 状态耦合**：
   * NyaaChat 插件系统（JS-Slash-Runner）中的 `variables[swipe_id]` 设计已预留了 `swipe_id` 的位置。首条开场白切换时，若存在 MVU 插件，需确保 `variables[0]` 正常工作且不越界。
3. **上下文发送（Prompt Building）透明性**：
   * NyaaChat 的 `chatPipeline.ts` 组装给 LLM 的 messages 是直接读取 `message.content`。因此只要翻页切换时正确更新了 `messages[0].content`，Prompt 注入机制**零风险、零侵入、100% 透明**！

## 4. 审核结论

方案技术路线清晰，与 NyaaChat 当前架构深度契合，完全遵循 SillyTavern Spec v2/v3 规范，无破坏性风险。接下来已就此方案编撰 SSOT 开发计划。
